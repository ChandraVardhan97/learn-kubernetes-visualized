# Intermediate curriculum technical audit

Reviewed on 2026-10-27 against live primary documentation. Scope: all 21 MDX lessons in `src/content/lessons/intermediate`, all 21 corresponding JSON files in `src/content/scenes/intermediate`, and the baseline examples in `public/labs/m07` through `m13` for alignment. The JSON scope contains 42 scenes, 168 base frames, 42 variants and 126 variant frames. Scene assumptions, narration, labels, details and example commands were reviewed, including the failure variants. IDs and lesson depth were preserved.

This is a documentation and content-consistency audit, not certification of every runtime or provider. No clusters were changed, labs executed, controllers installed, storage restored, Helm releases installed, or sites published during this audit. The main task separately verified the Kubernetes 1.37 / kind 0.33 release baseline; this audit retained that metadata and did not change the lab version pins. Kubernetes documentation currently identifies its main branch as 1.37. External projects have independent versions and capability requirements.

## Baseline lab alignment and suggestions passed to the main task

Lab files were inspected but not edited here, because the main task owns synchronization with canonical lab data.

- `m07`: the baseline demonstrates an impossible selector and reports Burstable QoS. It does not generate CPU pressure or install quota, LimitRange, taint or topology-spread exercises. Lesson claims were narrowed accordingly.
- `m08/run.sh`: delete only this module's existing allow policy before the baseline/deny sequence, so reruns cannot leave an additive permission that defeats the intended denial. Replace fixed three-second propagation assumptions with bounded probes. A single failed request establishes an observation, not attribution to policy; retain baseline/deny/allow comparison and label unexpected results clearly. The main task should synchronize any script changes with canonical data.
- `m09`: baseline Pod replacement and same-PV checks align with the persistence claim. Its local-path storage does not demonstrate CSI snapshotting, CSI attachment or node-loss recovery.
- `m10`: baseline has one StatefulSet replica, a headless Service, a DaemonSet, a finite Job, a suspended CronJob and a PDB. It has no volumeClaimTemplates, file writer or three-member ledger. Lesson l01 now identifies the fuller example as optional.
- `m11`: baseline contains no application Secret or Secret rotation workflow; lesson wording now makes that an extension. The negative can-i assertion was checked with a local shell-only stand-in returning stdout `no` and exit 1 under `set -euo pipefail`; its command-substitution assertion pattern behaves correctly. No correction was requested for that pattern.
- `m12/run.sh`: capture an expected negative client probe while the selector is deliberately wrong; after repair, poll the ready endpoint/client transition within a bound instead of depending on a two-second sleep. Preserve useful crash evidence without claiming the baseline installs telemetry backends.
- `m13/kustomization.yaml`: name hashing is disabled and the generated ConfigMap is not referenced by the Deployment. Either describe it as a render-only artifact, or add a separate hash-enabled reference exercise before claiming a configuration change triggers rollout. The HPA requests are already present; metrics availability remains the missing baseline prerequisite.

## Validation and limits

The final audit checked JSON/frontmatter parsing, every referenced scene ID, unique frame node IDs, edge endpoint references and preservation of scene/variant/frame identifiers. Repository content validation was run after the edits; the result is recorded by the main task alongside its final build checks. These checks do not execute the manifests or establish provider conformance. Any later content or dependency change should rerun structural checks and revisit the affected primary documentation.
