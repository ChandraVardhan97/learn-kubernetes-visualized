## <span id="mental-model-leadership-is-an-agreement-among-participants" aria-hidden="true" />How controller replicas elect a leader

Suppose you run two copies of a controller for availability. Both are ready, but you only want one reconciling at a time. Kubernetes supports coordination through a **Lease**, an API object that can record the current holder and renewal information. A participating controller acquires leadership and regularly renews it. Other candidates wait or attempt to take over if the current holder stops renewing. The API’s update conflict handling helps ensure two candidates racing to update the same Lease cannot both write the same version successfully.

In the election scene, stop renewal from controller A and watch when controller B can take over. The delay gives A a chance to recover from transient problems while bounding how long the system waits for a failed candidate. A leader election library handles renewal timing and calls the local start and stop functions when leadership changes.

## <span id="walkthrough-renewal-is-different-from-a-node-heartbeat" aria-hidden="true" />Read election Leases and node heartbeats

Leases also support Kubernetes node heartbeats. A node lease in `kube-node-lease` records that the kubelet has renewed contact with the API. A controller election Lease records coordination over who should perform a particular role. The two uses share an API type. Interpreting a holder and renewal requires knowing which component maintains that Lease.

The sample Lease names a holder and duration but has no process renewing it. Save it as `lease.yaml` and treat it as a record to inspect. A real election library also maintains acquisition and renewal fields.

```yaml
apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: m15-example
  namespace: kv-lab
  labels:
    lab: m15
spec:
  holderIdentity: training-controller-a
  leaseDurationSeconds: 30
# A real election library maintains acquisition and renewal fields.
```

## <span id="practice-explain-what-each-observation-proves" aria-hidden="true" />Compare a sample Lease with a live one

Look at the sample record, then inspect available system Leases without editing them. Depending on the cluster, an election record can show a holder, renew time, and transition count. Repeated reads can show renewals over time. Use the [coordination lab](/labs/#m15) to practice reading these objects alongside the scene.

```bash
kubectl --context kind-kv-lab -n kv-lab apply -f lease.yaml
kubectl --context kind-kv-lab -n kv-lab get lease m15-example -o yaml
kubectl --context kind-kv-lab -n kube-system get leases
kubectl --context kind-kv-lab -n kube-node-lease get leases
# This is inspection, not an instruction to edit system leadership records.
kubectl --context kind-kv-lab -n kube-system get lease kube-scheduler -o yaml
```

## <span id="practice-observe-a-live-lease-handoff" aria-hidden="true" />Observe a live scheduler handoff

Create the [separate HA kind cluster](/learn/advanced/m18-l01/#practice-test-quorum-in-disposable-kind) using only its cluster creation block. Keep all three members running at the start. Record the Lease holder, transition count, and renewal timestamp. This exercise stops the holder’s Docker node in that named cluster.

```bash
ha=(kubectl --kubeconfig ./kv-quorum.kubeconfig --request-timeout=10s)
"${ha[@]}" -n kube-system get lease kube-scheduler \
  -o 'custom-columns=HOLDER:.spec.holderIdentity,TRANSITIONS:.spec.leaseTransitions,RENEWED:.spec.renewTime'
holder=$("${ha[@]}" -n kube-system get lease kube-scheduler -o jsonpath='{.spec.holderIdentity}')
node=${holder%%_*}
case "$node" in
  kv-quorum-trace-control-plane|kv-quorum-trace-control-plane2|kv-quorum-trace-control-plane3)
    docker stop "$node" ;;
  *) printf 'Unexpected scheduler node: %s\n' "$node" >&2 ;;
esac
```

Repeat the read until another scheduler holds the Lease. Compare the transition count and see whether the new holder renews again. Restore the node after observing the handoff, then remove the practice cluster.

```bash
"${ha[@]}" -n kube-system get lease kube-scheduler \
  -o 'custom-columns=HOLDER:.spec.holderIdentity,TRANSITIONS:.spec.leaseTransitions,RENEWED:.spec.renewTime'
```

```bash

```

## <span id="pitfalls-shortening-timeouts-changes-failure-behavior" aria-hidden="true" />Protect external data from a former leader

A former leader can pause and later resume after a replacement has started. Its delayed write might still reach an external database. To protect that system, it needs **fencing**, a way for the destination to recognize and reject stale writers. For example, the destination could require an increasing leadership epoch and reject writes carrying an older one. The fencing scene illustrates the extra decision at the destination.

Shorter election times can reduce takeover delay and make temporary API slowdown cause more leadership changes. Evaluate renewal timing and monitoring together.
