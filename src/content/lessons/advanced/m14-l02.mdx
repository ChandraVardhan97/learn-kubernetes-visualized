## <span id="mental-model-observation-and-ownership-solve-different-problems" aria-hidden="true" />How a client keeps its object view current

A controller needs to know which ConfigMaps exist and keep track of changes. It can **list** the relevant objects to build an initial view, then **watch** for later additions, modifications, and deletions. A list response includes a `resourceVersion` the client can use to request changes after that snapshot. This gives the client a way to avoid missing a change between its initial read and the start of the watch.

If the connection drops, the client can resume from a suitable recent version. If the API server has discarded too much history, a `410 Gone` response tells the client to list again and rebuild its view before watching further. A resource version is a cursor for API state and should be passed back as provided; use the API’s documented comparison guarantees only where they apply. It is distinct from a wall-clock time or a count of application changes.

## <span id="walkthrough-watch-current-state-negotiate-field-changes" aria-hidden="true" />What happens when field managers disagree

Now imagine two writers setting the ConfigMap’s `data.release` field. One declares `git-declared` from a repository and another applies a manual change. **Server-side apply** tracks each writer’s declared fields under a field manager in `metadata.managedFields`. Applying a different value to a field owned by another manager can cause a conflict. A different manager can apply the same value and share ownership. Compare both outcomes in the scene.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: m14-ownership
  namespace: kv-lab
  labels:
    lab: m14
# Only this key is part of this manager's intention.
data:
  release: git-declared
```

## <span id="practice-capture-a-conflict-instead-of-suppressing-it" aria-hidden="true" />Reproduce and inspect an apply conflict

Save the ConfigMap as `ownership.yaml` and start with the `kv-gitops` manager. Inspect managed fields. Watch the object in a second terminal, and in the first terminal change `data.release` in the file. Apply as `kv-human` and read which manager and path the conflict names. A rejected change gives the watch no successful object update for that attempt.

```bash
kubectl --context kind-kv-lab -n kv-lab apply --server-side --field-manager=kv-gitops -f ownership.yaml
kubectl --context kind-kv-lab -n kv-lab get configmap m14-ownership -o yaml --show-managed-fields
# Keep a second terminal watching while you edit and reapply the file.
kubectl --context kind-kv-lab -n kv-lab get configmap m14-ownership --watch
# After changing data.release locally, expect a field conflict here.
kubectl --context kind-kv-lab -n kv-lab apply --server-side --field-manager=kv-human -f ownership.yaml
```

Try this in the [API mechanics lab](/labs/#m14). For a shared cluster, resolve a conflict by deciding who should manage the field. Remove the field from a manager’s declared configuration where appropriate, coordinate an update through the owner, or take ownership deliberately with a reviewed force apply. Transferring ownership changes what other reconcilers may be able to apply.

## <span id="pitfalls-persistence-is-not-cache-synchronization" aria-hidden="true" />Check whether the controller saw the write

A watch observes API writes. A controller may still need to process the update and report its progress. Compare object status and values produced by reconciliation separately. After a relist, evaluate current state instead of assuming every intermediate change was available to the client.
