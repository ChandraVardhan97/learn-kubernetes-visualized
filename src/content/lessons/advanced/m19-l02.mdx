## <span id="mental-model-isolation-is-a-set-of-enforced-boundaries" aria-hidden="true" />Choose how to isolate tenants

Two teams share a cluster. Each should manage its own apps. One team also wants to ensure that only builds from its approved pipeline reach production. A **namespace** scopes objects such as Pods and Roles. It gives you a place to apply namespaced access rules and resource budgets. Tenant isolation also needs to cover network traffic, privileged workloads, cluster-scoped configuration, and the degree of trust teams place in the same nodes and control plane.

In the tenant scene, try an API request, a network connection, and a privileged Pod proposal. RBAC, network policy enforcement, and admission each answer a different part of the question. A quota limits use of a shared resource. Stronger isolation requirements may call for separate nodes, control planes, or clusters, depending on the threat model.

## <span id="walkthrough-an-artifact-digest-identifies-bytes-not-intent" aria-hidden="true" />Verify who built a pinned image

An image **tag** is a human-readable name that can be moved. A **digest** identifies particular image manifest contents or an image index. Pinning by digest protects against silently pulling different bytes when the tag moves. A **signature** can tie the artifact to a signer trusted by your policy, and **provenance** can record which source and build process produced it. A verification policy can require specific identities or build conditions, then accept or reject a workload at admission. Test these distinctions in the artifact scene.

## <span id="practice-trace-one-denied-action-to-its-enforcement-point" aria-hidden="true" />Test each enforcement layer

This optional NetworkPolicy isolates selected Pods in both directions without adding any allow rules. It only takes effect with supporting network enforcement, and other policies can still permit traffic. Apply it to a labeled disposable Pod and compare a fresh connection before and after. Then use a tenant identity to inspect an intended grant and an action it should lack. The registry command shows the manifest information for a training image. It does not verify a signature or assert a provenance policy.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: m19-isolate
  namespace: kv-lab
  labels:
    lab: m19
spec:
  podSelector:
    matchLabels:
      tenant-experiment: isolated
  policyTypes: [Ingress, Egress]
  ingress: []
  egress: []
```

```bash
kubectl --context kind-kv-lab auth can-i create clusterrolebindings
kubectl --context kind-kv-lab -n kv-lab get roles,rolebindings,resourcequotas,networkpolicies
# Read the actual registry manifest information; do not invent a digest.
docker buildx imagetools inspect nginx:1.28.0-alpine
# Remove the optional policy after its isolated experiment.
kubectl --context kind-kv-lab -n kv-lab delete networkpolicy m19-isolate --ignore-not-found
```

Use the [platform operations lab](/labs/#m19) for the permissions and drift baseline. Test network blocking or image signature enforcement only in an environment configured for those controls.

## <span id="pitfalls-security-controls-can-be-bypassed-by-a-broader-permission" aria-hidden="true" />Check what the tenant is actually allowed to do

Broad rights to create privileged Pods or change cluster-scoped bindings can undermine tenant boundaries. Test permissions with the actual tenant identity, not a cluster administrator. Even an image with an approved signature can contain defects. Maintain the checks relevant to the threat, such as reviewing build provenance, scanning the artifact, and restricting runtime access.
