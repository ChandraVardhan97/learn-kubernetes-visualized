## Mental model: write a comparison, not an installation script

The teaching operator reads WebApps in the named disposable namespace and derives a ConfigMap plus a Deployment for each one. The ConfigMap contains `index.html` from spec.message; the Deployment uses spec.replicas and mounts that ConfigMap into nginx's document directory. Stable child names come from the WebApp name. A second reconcile pass finds the same intended children rather than creating another uniquely named web server.

Idempotence means repeated reconciliation converges to the same intended resource relationships despite retries and partial success. It does not require every HTTP request to be absent or every resourceVersion to remain unchanged. The useful identity check is that a Deployment UID stays stable when no replacement is required. Status updates and field-management metadata can still change. A controller should avoid unnecessary writes where practical, but correctness cannot depend on receiving exactly one trigger.

## Walkthrough: each write is its own commit boundary

Read `webapp-reconciler.py` from the m16 download before running it. It calls kubectl with an explicit context and namespace, verifies the disposable cluster, lists WebApps, computes desired child objects, refuses to adopt an existing unrelated child, and applies each child using manager `kv-webapp-operator`. It then reads the Deployment and patches the WebApp status subresource with observedGeneration and readyReplicas. Authentication and TLS are delegated to kubectl rather than reimplemented in Python.

These operations are not one transaction. A crash can leave the ConfigMap created before the Deployment exists, or both children present before status is updated. The next pass must reuse the successful partial work. When a child exists under the expected name, the operator checks owner identity before applying it; equal names do not establish permission to take over somebody else's resource. SSA conflicts also remain visible because the example deliberately does not force ownership.

The custom resource is a compact API for desired behavior. Normal Kubernetes controllers still implement Deployment rollout, replica replacement and Pod startup. This is why the operator can stay small while the application lifecycle remains asynchronous.

```yaml
apiVersion: labs.kv.example/v1alpha1
kind: WebApp
metadata:
  name: m16
  namespace: kv-lab
  labels:
    lab: m16
spec:
  replicas: 2
  message: repeated-reconcile-is-safe
```

```bash
# Run after installing the m16 CRD and resources.
python3 webapp-reconciler.py --once
kubectl --context kind-kv-lab -n kv-lab rollout status deployment/m16 --timeout=180s
kubectl --context kind-kv-lab -n kv-lab get deployment m16 -o jsonpath='{.metadata.uid}{"\n"}'
python3 webapp-reconciler.py --iterations 3 --interval 1
kubectl --context kind-kv-lab -n kv-lab get deployment m16 -o jsonpath='{.metadata.uid}{"\n"}'
kubectl --context kind-kv-lab -n kv-lab get webapp m16 -o yaml
```

## Practice: observe convergence twice

Run the [m16 local exercise](/labs/#m16). Expect a ConfigMap and Deployment owned by the WebApp, then ready nginx Pods after normal rollout. Compare the child UID before and after repeated reconciliation. Change spec.replicas to two, run the operator again, and wait for the Deployment's rollout before checking WebApp status. Because status is sampled during a reconcile pass, run one more pass after readiness if you want its readyReplicas observation to catch up.

Inspect the actual mounted page with a request from a Pod or a local port-forward. ConfigMap volume updates propagate asynchronously; this example does not restart Pods by hashing the ConfigMap into the Pod template. A successful API patch therefore does not prove every server has already observed new content. Document the intended refresh behavior if you extend the API to applications that read configuration only once at startup.

## Pitfalls: understand the deliberate omissions

This operator is a host-run, dependency-free polling demonstration. It does not provide informer caches, a rate-limited workqueue, multi-replica leader election, rich conditions, admission defaulting or external-resource finalizers. It uses the host's Kubernetes credentials, so its safety checks are not a substitute for production least-privilege RBAC. It exits on an error rather than isolating every resource failure into a robust queue. These boundaries make the mechanism inspectable and identify the engineering needed before operating a shared platform.

Inspect status after the final reconcile pass rather than treating the first printed success line as a readiness assertion. The process can successfully apply both children while the Deployment controller is still starting its first Pod. Its sampled readyReplicas can also describe Pods from an earlier Deployment generation. A production Ready condition must check the child's observed generation and relevant rollout conditions as well as the parent generation; this minimal status does not prove current-revision readiness.
