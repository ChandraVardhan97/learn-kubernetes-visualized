## <span id="mental-model-write-a-comparison-not-an-installation-script" aria-hidden="true" />How a WebApp becomes running resources

A user changes a WebApp from one replica to two. They expect that edit to become a Deployment change, and they expect recovery if a managed child is deleted. An **operator** combines Kubernetes APIs and controller logic to manage an application or operational process. Its **reconcile loop** reads desired and observed state and makes changes that move the system toward the goal.

In this lab the WebApp holds a replica count and a message. The reconciler derives a Deployment, Service, and ConfigMap from those fields and its conventions. A **repeatable or idempotent** reconciliation can run again and reach the same intended state. It can find an existing object, check ownership, and update the relevant fields instead of creating duplicates. The scene shows which child changes when you edit the parent’s specification.

## <span id="walkthrough-each-write-is-its-own-commit-boundary" aria-hidden="true" />Recover after writing only some children

Each Kubernetes object write has its own outcome. Suppose the reconciler writes the ConfigMap and Deployment, then exits before writing the Service. The next pass can discover both surviving children and complete the missing write. Status tells the reader what the reconciler observed at a point in time. A successful change to desired replicas can precede the availability of the new Pods.

```yaml
apiVersion: labs.kv.example/v1alpha1
kind: WebApp
metadata:
  name: m16
  namespace: kv-lab
  labels:
    lab: m16
spec:
  replicas: 2
  message: repeated-reconcile-is-safe
```

## <span id="practice-observe-convergence-twice" aria-hidden="true" />Run reconciliation again and compare UIDs

Start with the module resources applied. Use the example WebApp spec for a change to two replicas. Run the lab script once and wait for the generated Deployment. Record its UID. Then run three more passes and read the UID and WebApp status again. An unchanged UID supports that the Deployment was kept in place during reconciliation. Inspect the replica count and the child resources too, since UID alone cannot establish that every desired field was applied.

```bash
# Run after installing the m16 CRD and resources.
python3 webapp-reconciler.py --once
kubectl --context kind-kv-lab -n kv-lab rollout status deployment/m16 --timeout=180s
kubectl --context kind-kv-lab -n kv-lab get deployment m16 -o jsonpath='{.metadata.uid}{"\n"}'
python3 webapp-reconciler.py --iterations 3 --interval 1
kubectl --context kind-kv-lab -n kv-lab get deployment m16 -o jsonpath='{.metadata.uid}{"\n"}'
kubectl --context kind-kv-lab -n kv-lab get webapp m16 -o yaml
```

In the [operator lab](/labs/#m16), deliberately remove a generated object after a good run. Run the reconciler again to check that the missing child returns while existing children stay owned and intact.

## <span id="pitfalls-understand-the-deliberate-omissions" aria-hidden="true" />What a deployed operator needs beyond the lab

The lab script is a polling exercise you run from your machine. A deployed operator usually needs stable API permissions, proper watches, retries, pacing, concurrent update handling, and observable conditions. If it calls an external service, test what happens when the service fulfills a request but the controller times out before seeing the reply. Stable ownership and idempotent operations matter more than the number of loop iterations.
