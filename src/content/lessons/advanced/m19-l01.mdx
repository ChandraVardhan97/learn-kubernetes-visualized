## <span id="mental-model-the-source-of-intent-is-another-dependency" aria-hidden="true" />How a Git change reaches Kubernetes

A teammate changes a live ConfigMap to troubleshoot checkout. The fix works for today, but the repository still declares the old value. The live object and the source disagree. **GitOps** uses versioned, declarative configuration as the source of desired state and a controller to compare and reconcile that state with the environment. Someone reviewing a change can see the proposed configuration, and someone responding to an incident can identify the revision the controller last observed.

Follow one revision in the scene. The controller fetches the source, renders manifests if needed, compares them with live resources, and attempts a sync when configured to do so. It then evaluates health using its knowledge of the resources. Fetching a revision, applying its manifests, and verifying that an app works are separate checkpoints. A green diff can coexist with a broken backend.

## <span id="walkthrough-automatic-sync-has-independent-controls" aria-hidden="true" />Decide when to sync, repair drift, and prune

In Argo CD, for example, automated sync, self-healing of live drift, and automatic pruning are distinct controls. A manual change can remain until another sync if self-healing is disabled. Pruning authorizes removal of resources that the source no longer declares, subject to the application’s settings. Before allowing that behavior, inspect what the controller tracks and how it handles resources whose state must be retained. Check compatibility with your Kubernetes version before installing a production controller.

## <span id="practice-observe-state-and-ownership-before-restoring-it" aria-hidden="true" />Inspect a manual change before restoring it

Use the ConfigMap as a small declaration. The module’s commands apply it with field manager `kv-gitops`, then change the live value with a manual patch. Inspect the declared value, the live value, and the managers. The final command deliberately takes ownership of the changed field in the disposable lab. In a shared environment, choose whether to keep the emergency value by committing it, undo it through the repository, or coordinate an intentional change in ownership.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: m19
  namespace: kv-lab
  labels:
    lab: m19
data:
  release: git-declared
```

```bash
# Run from the downloaded m19 directory.
kubectl --context kind-kv-lab -n kv-lab apply --server-side --field-manager=kv-gitops -f resources.yaml
kubectl --context kind-kv-lab -n kv-lab patch configmap m19 --type=merge -p '{"data":{"release":"manual-drift"}}'
kubectl --context kind-kv-lab -n kv-lab get configmap m19 -o yaml --show-managed-fields
# Intentional takeover of this disposable lab field only.
kubectl --context kind-kv-lab -n kv-lab apply --server-side --field-manager=kv-gitops --force-conflicts -f resources.yaml
```

## <span id="pitfalls-emergency-changes-need-a-return-path" aria-hidden="true" />Keep emergency changes reviewable

A controller depends on its source, credentials, rendering tools, and cluster permissions. Diagnose a failed fetch differently from a sync rejected by admission. For emergency edits, document who made the edit, how long it should remain, and how the team will restore a single source of intent.
