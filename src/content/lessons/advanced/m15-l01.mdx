## <span id="mental-model-events-schedule-a-question-not-a-command" aria-hidden="true" />How a watch feeds the controller’s cache

You maintain a controller that generates a ConfigMap for each application. Three changes to the same app arrive while a worker is busy. Processing each event as an instruction can lead to unnecessary intermediate writes. Instead, controllers usually arrange to reconcile one object key, then read the current state when a worker takes it. The key commonly contains a namespace and name. The worker can compare the latest requested config with what already exists.

A **shared informer** uses API lists and watches to maintain a local cache of selected objects and notify handlers about changes. Multiple consumers in a controller can use the same cache and watch. A controller can wait for the initial cache sync before starting workers. The view can still lag a fresh API read, so the worker should tolerate missing objects and updates made since its read. Step through the cache scene to see the gap between an API write and the local update.

## <span id="walkthrough-one-key-may-represent-many-changes" aria-hidden="true" />Why a queue can combine multiple changes

A **workqueue** holds keys that need attention. If a key is already waiting, later changes can be combined with it. A change while the same key is being processed can mark it for another pass. When the worker completes, it clears the processing state and handles any queued repeat. If processing fails, a rate-limited queue can delay retries so a persistent problem does not keep the worker hammering the API. Common queue state is in memory, so a restarted controller rebuilds work from current objects and its watches.

## <span id="practice-reason-about-the-crash-boundary" aria-hidden="true" />Recover when a write survives a crash

Ask what happens if the controller writes the generated ConfigMap, then crashes before reporting success. On restart it can reconcile the source again. A safe worker finds the surviving object and decides whether it needs another change. It should avoid replacing it or producing a second external result solely because the earlier status update was missed.

Save the example as `repeat.yaml`. Apply it twice and compare UIDs. Same-account repeated apply demonstrates updating or leaving an object in place under the same identity. The commands do not run an informer. Use them as an API-side practice step in the [controller internals lab](/labs/#m15).

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: m15-repeat
  namespace: kv-lab
  labels:
    lab: m15
data:
  desired: stable
```

```bash
kubectl --context kind-kv-lab -n kv-lab apply -f repeat.yaml
kubectl --context kind-kv-lab -n kv-lab get configmap m15-repeat -o jsonpath='{.metadata.uid}{"\n"}'
# Apply again; the object UID should remain the same.
kubectl --context kind-kv-lab -n kv-lab apply -f repeat.yaml
kubectl --context kind-kv-lab -n kv-lab get configmap m15-repeat -o jsonpath='{.metadata.uid}{"\n"}'
kubectl --context kind-kv-lab -n kv-lab get configmap m15-repeat --watch --request-timeout=5s
```

## <span id="pitfalls-retries-are-a-load-generator" aria-hidden="true" />Avoid repeating unsafe operations on retry

A retry expected to succeed after a transient timeout is different from endlessly retrying invalid input. Record the failure and use backoff where another attempt may help. If the controller writes to an external system, use that system’s support for idempotency or record a stable operation identity so retries do not repeat irreversible work.
