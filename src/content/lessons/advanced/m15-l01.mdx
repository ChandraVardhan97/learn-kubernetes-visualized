## Mental model: events schedule a question, not a command

An informer combines list/watch observation with a local object cache and event handlers. A shared informer lets multiple consumers share that observation machinery. Handlers usually enqueue a resource key such as `kv-lab/m16`, rather than perform long network calls immediately. A worker later asks: given the desired object and observed dependents now, what must change? This separates API event delivery from expensive reconciliation and keeps the system responsive during bursts.

The cache is eventually consistent with the API server. A worker may successfully create a child and then briefly read a cached parent or child that predates that write. Reconciliation must tolerate that window. It should also tolerate an object disappearing between enqueue and processing. A missing parent often means no creation work is needed; it is not automatically a retryable outage. Do not derive correctness from receiving exactly one event in exactly the sequence you expected.

## Walkthrough: one key may represent many changes

A workqueue can deduplicate pending keys and coordinate processing of a key so workers do not repeatedly execute the same pending item concurrently. If another change arrives while a key is being processed, the queue can arrange another pass after the current one finishes. This reduces unnecessary work but means an event stream is not a transaction log. Reconcile the current object's desired replica count, rather than attempting to replay every historical increase and decrease.

Rate-limited queues let failures re-enter with delay. On success, a typical client-go worker forgets accumulated failure history; it always marks the item done after processing. On transient errors it adds the key with rate limiting. On permanent invalid input it records a useful condition and waits for a relevant change rather than retrying rapidly forever. Per-item backoff and overall throughput limits reduce pressure, but neither grants capacity to an overloaded downstream API.

## Practice: reason about the crash boundary

Run the [m15 local exercise](/labs/#m15), then connect it to the polling operator in m16. Draw a reconcile attempt that creates a ConfigMap, creates a Deployment, and updates status. Place a process crash after each write. The next attempt must discover and reuse an already-created object, finish missing work, and avoid inventing a new child name on every attempt. This is idempotence across partial progress, not merely making a function return the same string twice.

Inspect the example operator's deliberately limited polling loop. Polling is useful for exposing the state comparison, but it does not provide shared informer efficiency, queue fairness or rate-limited retry machinery. A production conversion would use maintained client libraries, wait for required caches to synchronize, handle deleted objects, and measure queue depth, queue wait time, reconcile duration and error categories. Choose observations that distinguish a slow worker from an unhealthy API dependency.

## Pitfalls: retries are a load generator

Do not retry every exception with no delay. A rejected schema, missing authorization, exhausted quota and temporary timeout require different remedies. If an external request timed out after the external system committed it, retrying a blind create can duplicate resources. Use a stable external identity, an idempotency key where available, and discovery before replacement. Cap concurrency so a short API outage does not produce an uncontrolled recovery surge. Logging every retry at maximum detail can itself consume storage and hide the first useful failure.
