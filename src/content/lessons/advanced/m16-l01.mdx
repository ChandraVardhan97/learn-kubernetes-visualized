## <span id="mental-model-adding-an-api-does-not-add-behavior" aria-hidden="true" />Add a new object type to the API

A platform team wants app authors to ask for a web app with a message and replica count. The lab reconciler supplies a Deployment and a ConfigMap for the page content. A **CustomResourceDefinition (CRD)** registers a new type with the Kubernetes API. After registering `WebApp`, clients can create and watch WebApp objects. Each saved WebApp is an instance of that custom type. A separate controller has to read the object and create the application resources.

Register the type, apply the WebApp, and start the demo reconciler in the scene. Before registration, the API cannot find that resource endpoint. Afterwards, the API can validate and store a WebApp even if no Deployment is created yet. This lets you diagnose the API definition and the controller independently.

## <span id="walkthrough-a-schema-is-a-compatibility-contract" aria-hidden="true" />Validate input and manage API versions

The CRD has a schema specifying the fields, types, and validation rules it accepts. The example WebApp requests one replica and a string message. The teaching CRD accepts values from one to five. In a CRD schema, marking fields inside `spec` as required checks them when `spec` exists. To require `spec` itself, add that requirement at the object root. Try an out-of-range replica count using server-side dry run and look for the field the API rejects.

```yaml
apiVersion: labs.kv.example/v1alpha1
kind: WebApp
metadata:
  name: m16
  namespace: kv-lab
  labels:
    lab: m16
spec:
  replicas: 1 # CRD accepts 1 through 5 in this teaching API.
  message: hello-from-webapp
```

A CRD can serve multiple API versions while choosing one as the storage version. Conversion translates different served representations. When representations meaningfully differ, the conversion must preserve the data clients need. Before retiring an old storage version, migrate stored objects and verify the supported versions.

Controllers write **status** to describe what they observed. The API’s `metadata.generation` changes when desired state changes for the resource. A controller can report an `observedGeneration` in status or conditions to indicate which spec it evaluated. Look at the scene and ask whether a previously healthy condition describes the most recent edit.

## <span id="practice-test-the-api-before-the-controller" aria-hidden="true" />Test acceptance before running the controller

Run the commands from the downloaded module directory in the disposable cluster. The `Established` condition means the CRD has been registered. `kubectl explain` reads schema information, and `get` confirms an instance was stored. Verify both successful and rejected dry-run payloads in the [custom resource lab](/labs/#m16) before moving on to the reconciler.

```bash
# Run from the downloaded m16 directory.
kubectl --context kind-kv-lab apply -f crd.yaml
kubectl --context kind-kv-lab wait --for=condition=Established crd/webapps.labs.kv.example --timeout=60s
kubectl --context kind-kv-lab -n kv-lab apply -f resources.yaml
kubectl --context kind-kv-lab explain webapp.spec
kubectl --context kind-kv-lab -n kv-lab get webapp m16 -o yaml
```

## <span id="pitfalls-api-deletion-is-data-deletion" aria-hidden="true" />Protect stored data when changing an API

Deleting a CRD deletes the custom objects it manages. For a real API, plan migration and document its data ownership before replacing or retiring it. When making a schema change, test both existing objects and new inputs.
