## Mental model: adding an API does not add behavior

A CustomResourceDefinition registers a resource type with the Kubernetes API server. Clients can discover it, validate instances against its schema, and store those instances through normal API mechanisms. The CRD does not itself create Deployments, provision databases or run cleanup code. An operator supplies that behavior by reconciling custom resources. Keeping those responsibilities separate makes it possible to diagnose a rejected specification independently from a controller that cannot fulfill an accepted specification.

The local API is `WebApp` in group `labs.kv.example`, version `v1alpha1`, with namespaced instances addressed as `webapps`. Its spec has a replica count and a page message. The downloadable CRD constrains replicas to a small positive range and limits message length. These checks reject invalid input early; they do not prove enough node capacity exists or that the message is suitable for every possible production application.

## Walkthrough: a schema is a compatibility contract

A structural OpenAPI schema describes known fields, types and list/map behavior. Unknown fields are generally pruned unless preservation is explicitly configured for the relevant subtree. This can surprise a client that sends a misspelled field and then assumes it was retained. Use strict server-side validation where appropriate and read the stored object back. A nested `required` list applies when its parent exists; require `spec` at the schema root if the controller cannot handle its absence. Defaults and validation rules become part of the API contract, so changing them can alter future writes and the controller's interpretation of existing objects.

The status subresource separates observed state from desired spec. The lab status reports observedGeneration and readyReplicas. observedGeneration tells you which desired generation was processed; it is not automatically a Ready condition. If the controller updates observedGeneration immediately after inspecting an unready Deployment, readiness can still be zero. Production APIs often add conditions with reason, message, status and transition time to describe blocked or progressing states precisely.

Versioning requires a second distinction. Multiple versions may be served, while exactly one version is designated for storage. Conversion maps representations; it does not execute an upgrade of the user's external database. A conversion webhook must preserve information needed to round-trip safely and be available whenever conversion is required. Setting a new storage version does not rewrite all existing stored objects by itself. Plan storage migration and verify storedVersions before removing an old version.

This instance is valid only after applying the lab's complete CRD. The bounds belong to the CRD schema, not to comments in an instance manifest.

```yaml
apiVersion: labs.kv.example/v1alpha1
kind: WebApp
metadata:
  name: m16
  namespace: kv-lab
  labels:
    lab: m16
spec:
  replicas: 1 # CRD accepts 1 through 5 in this teaching API.
  message: hello-from-webapp
```

```bash
# Run from the downloaded m16 directory.
kubectl --context kind-kv-lab apply -f crd.yaml
kubectl --context kind-kv-lab wait --for=condition=Established crd/webapps.labs.kv.example --timeout=60s
kubectl --context kind-kv-lab -n kv-lab apply -f resources.yaml
kubectl --context kind-kv-lab explain webapp.spec
kubectl --context kind-kv-lab -n kv-lab get webapp m16 -o yaml
```

## Practice: test the API before the controller

Open the [m16 local exercise](/labs/#m16). Read `crd.yaml`, then apply only the CRD and custom resource before running the Python operator. Expect the WebApp to exist without a generated Deployment until reconciliation runs. This is direct evidence that API registration and behavior are separate. Try an out-of-range replica count using server-side dry run and expect schema rejection. Restore the valid input before continuing to the next lesson.

Compare the submitted manifest with the object returned by the API. Note apiVersion, generation, UID and the absence or presence of status. Inspect the CRD's versions and storedVersions fields. This single-version example has no conversion webhook and proves no multi-version migration behavior. A production migration needs old-client fixtures and round-trip tests as well as a schema that accepts the new fields.

## Pitfalls: API deletion is data deletion

Removing the operator Deployment leaves custom resources stored but unreconciled. Deleting the CRD removes the API and can delete its stored instances. Treat that as a separate destructive action, not routine controller restart cleanup. Overly broad preserve-unknown-fields settings make validation and field ownership less predictable. Conversely, tightening a schema without examining stored objects can make legitimate updates fail. Review the behavior of both old and new clients before changing a shared API.
