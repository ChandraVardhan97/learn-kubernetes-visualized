## Mental model: rank only nodes that can run the Pod

The scheduler observes Pods without a node assignment and attempts placement. Filtering asks whether a node is feasible under hard constraints: resource requests, required affinity, taints and tolerations, topology, volumes and other configured checks. Scoring then compares feasible nodes using preferences and weighted plugin results. A node with a very attractive score cannot win if it failed a required filter. This distinction is the foundation of useful Pending-Pod diagnosis.

Scheduling uses resource requests and scheduler accounting, not merely a live CPU utilization graph. A node can look quiet while its requested capacity is allocated. Conversely, a node can be busy because applications exceed their requests. The scheduler must also account for Pods assumed during scheduling while their bindings are still being completed. Placement decisions coordinate with concurrent activity; they are not an instantaneous global optimization of every Pod in the cluster.

## Walkthrough: scheduling and binding have separate failure points

The scheduling framework exposes extension points. PreFilter and Filter establish feasibility, then scoring-related plugins rank candidates. Reserve can hold provisional state; Permit can delay or reject progress. PreBind performs required work before binding, and Bind assigns the Pod through the API. If later work fails, Unreserve releases reservations so an abandoned attempt does not permanently consume plugin state. PostBind is notification after a successful bind, not a second scheduling decision.

Scheduling cycles and binding cycles have different concurrency characteristics: the scheduling cycle selects a node, while subsequent binding work can overlap for different Pods. Volume binding is a common reason a placement path includes coordination beyond CPU and memory. A selected node still needs a functioning kubelet, image access, mounted volumes and readiness success. The `PodScheduled` condition proves a scheduling boundary, not an application health boundary.

<Scene id="m15-l02-bind-cycle" />

This small Pod is intentionally unschedulable on an ordinary kind cluster unless you add the matching node label. The label represents a hard requirement rather than a preference. Save it as `placement.yaml`; changing the label key is safer than changing arbitrary node configuration during diagnosis.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: m15-placement
  namespace: kv-lab
  labels:
    lab: m15
spec:
  nodeSelector:
    training.kv.example/accelerator: present # Hard feasibility rule.
  containers:
    - name: app
      image: busybox:1.37.0
      command: [sleep, "3600"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
```

```bash
kubectl --context kind-kv-lab -n kv-lab apply -f placement.yaml
kubectl --context kind-kv-lab -n kv-lab describe pod m15-placement
kubectl --context kind-kv-lab -n kv-lab get pod m15-placement -o jsonpath='{.status.conditions}{"\n"}'
# Remove only the intentionally impossible selector to retry placement.
kubectl --context kind-kv-lab -n kv-lab delete pod m15-placement
```

## Practice: separate a failed filter from a low score

Use the [m15 local exercise](/labs/#m15) to inspect control-loop behavior, and optionally apply the isolated Pod above. Expect Pending with FailedScheduling evidence mentioning the selector mismatch. There is no winning feasible node to score in this case. A lower CPU request would not repair a missing required label. Rewrite the manifest without the selector and reapply if you want to observe scheduling; inspect `spec.nodeName` and the PodScheduled condition before checking container readiness.

Now predict preemption. If insufficient requested capacity is the obstacle and suitable lower-priority victims exist, preemption may create room. If every node fails an incompatible node selector or required topology constraint, removing other Pods does not make those nodes satisfy the selector. A nominated node is an intermediate scheduling intention and does not guarantee the eventual binding succeeds.

## Pitfalls: configuration can encode impossible combinations

Required anti-affinity, a single available zone, a restrictive volume topology and a small node pool can leave no feasible placement. Adding replicas may then increase Pending count without increasing service capacity. Soft preferences are appropriate when violating the preference is better than remaining unavailable; hard requirements are appropriate when placement would be invalid. Document that product decision before converting constraints. Avoid setting `spec.nodeName` merely to bypass a confusing scheduler event: direct assignment changes which scheduler checks execute and can place the Pod somewhere the intended policy would have rejected.

When reading FailedScheduling events, separate each reported filter failure. The event summarizes rejected candidates; its counts do not establish that every node failed for the same reason. Compare node labels, taints and requested resources before choosing a configuration change.
