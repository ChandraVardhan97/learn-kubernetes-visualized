## <span id="mental-model-ownership-must-survive-name-reuse" aria-hidden="true" />Verify which WebApp owns a child

The WebApp operator expects a ConfigMap called `m16`. It finds an object with that name. Before updating it, the operator needs to know whether it created the object for the current WebApp. It could belong to another workload, or to an older WebApp that used the same name. An **owner reference** includes the parent’s UID, so the operator can check ownership of this exact object lifetime.

If ownership matches, the operator can repair fields it manages. If there is no child, it can create one using the parent’s current UID. If the name belongs to somebody else, report the conflict and let an operator decide how to handle it. Step through these cases in the owner-check scene and see what changes when a parent is replaced under the same name.

## <span id="walkthrough-repair-and-deletion-are-different-reconciliations" aria-hidden="true" />Compare child repair and parent deletion

Recreating a missing child serves a parent that still exists and wants that child. When the parent is being deleted, the intended outcome changes. Kubernetes garbage collection can remove API dependents whose owner reference points to the deleted parent. An object in an external system needs its own cleanup policy, often implemented with a finalizer when cleanup should complete before parent deletion. In the scene, compare deleting the generated ConfigMap with deleting the WebApp.

## <span id="practice-collect-evidence-at-each-boundary" aria-hidden="true" />Recreate a child and inspect its owner

Start with the example WebApp and generated children from the disposable lab. Record the WebApp UID and the ConfigMap’s owner reference. Delete only the lab’s generated ConfigMap and run one reconcile pass. The new ConfigMap gets a fresh UID and should point to the same parent UID. Read its data and owner reference to verify recovery. To complete the deletion exercise, follow the [operator lab](/labs/#m16) cleanup sequence and confirm the expected children are collected.

```yaml
apiVersion: labs.kv.example/v1alpha1
kind: WebApp
metadata:
  name: m16
  namespace: kv-lab
  labels:
    lab: m16
spec:
  replicas: 1
  message: repaired-by-reconciliation
```

```bash
kubectl --context kind-kv-lab -n kv-lab get webapp m16 -o jsonpath='{.metadata.uid}{"\n"}'
kubectl --context kind-kv-lab -n kv-lab get configmap m16 -o jsonpath='{.metadata.ownerReferences}{"\n"}'
# Delete only this generated, disposable ConfigMap.
kubectl --context kind-kv-lab -n kv-lab delete configmap m16
python3 webapp-reconciler.py --once
kubectl --context kind-kv-lab -n kv-lab get configmap m16 -o yaml
```

## <span id="pitfalls-cleanup-policy-belongs-in-the-api-design" aria-hidden="true" />Choose which resources should survive deletion

Some objects should survive parent deletion. A database backup or persistent data volume may need a retention policy independent of the controller’s app objects. Document which resources the API owns and whether deletion retains or removes them. Allow time for asynchronous garbage collection before investigating a child that still exists, and verify the exact owning UID before considering manual removal.
