## Mental model: ownership must survive name reuse

A controller manages a relationship between a parent intention and dependent resources. In this lab, the generated Deployment and ConfigMap carry ownerReferences naming the WebApp's UID and identifying it as controller owner. The UID matters because a WebApp can be deleted and recreated with the same name. The replacement is a new parent identity. A controller that adopts any child with the expected name could overwrite a resource belonging to someone else or a previous lifecycle.

The Python operator checks existing child ownership and refuses unrelated objects. This is a useful safety property even in a tiny controller. Labels such as `app=m16` help find resources, but labels are mutable selection metadata, not proof of ownership. If an operator reports an adoption refusal, inspect both the current parent UID and the child's complete ownerReferences before considering any repair. Do not remove the check simply to make a demonstration proceed.

## Walkthrough: repair and deletion are different reconciliations

When the ConfigMap is accidentally deleted while the WebApp still exists, the next pass computes the same desired child and recreates it. Its new UID proves replacement; the parent's UID remains unchanged. When a Deployment is deleted, the next pass recreates that child too, but application availability may be disrupted while Pods return. Reconciliation provides a route back toward desired state, not instantaneous immunity from destructive changes.

Deleting the parent is different. The teaching operator skips resources with deletionTimestamp and relies on Kubernetes garbage collection for its Kubernetes children. No external system is provisioned, so there is no external cleanup finalizer in this example. A production operator managing a cloud database might need a finalizer to coordinate retention or deletion before the parent disappears. Such cleanup must be idempotent and must handle the external resource already being absent. A finalizer cannot turn a nontransactional pair of systems into one atomic transaction.

This manifest illustrates the parent relationship through the real WebApp API. Owner references on the children are generated by the controller; do not copy a UID from documentation into a hand-written dependent manifest.

```yaml
apiVersion: labs.kv.example/v1alpha1
kind: WebApp
metadata:
  name: m16
  namespace: kv-lab
  labels:
    lab: m16
spec:
  replicas: 1
  message: repaired-by-reconciliation
```

```bash
kubectl --context kind-kv-lab -n kv-lab get webapp m16 -o jsonpath='{.metadata.uid}{"\n"}'
kubectl --context kind-kv-lab -n kv-lab get configmap m16 -o jsonpath='{.metadata.ownerReferences}{"\n"}'
# Delete only this generated, disposable ConfigMap.
kubectl --context kind-kv-lab -n kv-lab delete configmap m16
python3 operator.py --once
kubectl --context kind-kv-lab -n kv-lab get configmap m16 -o yaml
```

## Practice: collect evidence at each boundary

Use the [m16 local exercise](/labs/#m16). Record the parent UID, child UID and child owner UID before failure. Delete the generated ConfigMap, run one reconcile pass, and record them again. Expect the child UID to change, its owner UID to match the unchanged WebApp UID, and the page content to match current spec.message. This proves repair toward current intention rather than restoration of a particular old object identity.

Parent deletion is demonstrated again in the m20 platform capstone. Before trying it manually, save the desired manifest and ensure the objects contain no data you need to preserve. Delete the WebApp, wait for dependent removal, and inspect events if deletion stalls. Background garbage collection is asynchronous. A child can remain briefly visible after the parent's delete request returns. Do not immediately declare ownership broken because two terminal reads caught different points in the deletion sequence.

## Pitfalls: cleanup policy belongs in the API design

A database operator needs a documented retention decision: should deleting the custom resource preserve data, require a separate approval, or remove storage? ownerReferences alone cannot express every data policy. A broken finalizer controller can block deletion, while a missing finalizer can leak an external resource. Repeated cleanup attempts must not delete a newly recreated external object with the old name; carry and verify external identity as well as Kubernetes UID. Conditions should identify the failed cleanup step without placing credentials or sensitive data in status messages.

For recovery, pause destructive automation when necessary and understand what will reconcile next. Restoring an old custom resource into a live environment can cause the operator to enact old intent immediately. A backup procedure must include a plan for controller startup and ownership reconciliation, not just an API import.
