## <span id="mental-model-the-signal-has-a-denominator" aria-hidden="true" />Calculate the first replica recommendation

An API runs four replicas. Each requests `200m` of CPU and uses about `150m` during a spike. Its average utilization is 75%, and its HPA target is 50%. The basic recommendation is the current count times observed divided by target, rounded up. Here that gives `ceil(4 × 75 / 50) = 6`. The scene lets you change usage and requests separately to see which number drives the recommendation.

The **Horizontal Pod Autoscaler** reads metrics periodically and writes a desired scale when the recommendation passes its rules. CPU utilization is measured relative to requested CPU. If the requests double while actual usage stays the same, utilization falls. A workload with missing CPU requests or an unavailable Metrics API may provide no usable utilization signal for that metric.

## <span id="walkthrough-recommendations-pass-through-guardrails" aria-hidden="true" />How HPA rules change the recommendation

The formula is the starting point. The HPA uses a tolerance around the target, handles missing metrics conservatively, and treats not-yet-ready Pods specially when evaluating CPU. If you use multiple metrics, the controller computes recommendations for them and generally chooses the largest valid one. Metric errors can prevent a scale-down even if another metric suggests one. Scaling policies limit changes over time, and a stabilization window can keep a recent higher recommendation during scale-down.

In the example, the replica bounds are two and eight and scale-down looks back five minutes. A short drop in demand can leave the count high while the window still contains a recent larger recommendation.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: m17-web
  namespace: kv-lab
  labels:
    lab: m17
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: m17-web
  minReplicas: 2
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50 # Percent of requested CPU, not CPU limit.
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
```

## <span id="practice-predict-a-recommendation-before-changing-configuration" aria-hidden="true" />Follow scale-up from demand to readiness

Estimate a desired count before changing requests or load. Check the metrics API, the HPA target and conditions, then the Deployment and ready Pods. Newly created Pods still need placement, image pulls, and readiness. If capacity must grow, an infrastructure autoscaler may need time to add suitable nodes. In the scene, follow the demand spike all the way to the point when new Pods can serve requests.

## <span id="pitfalls-more-replicas-can-amplify-dependencies" aria-hidden="true" />See how load affects shared dependencies

Extra replicas can increase connections and contention on a shared dependency. Use a metric that reflects what you want to improve. Queue depth can help a worker fleet when work is divisible, while CPU may tell you little about a workload blocked on a saturated database. Measure the end result, such as queue age or request latency.
