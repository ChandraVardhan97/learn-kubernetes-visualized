## <span id="mental-model-different-limits-fail-differently" aria-hidden="true" />Why CPU pressure and memory limits look different

During a traffic spike, some API requests slow down and one worker stops entirely. The resource numbers tell different stories. **CPU throttling** delays a runnable process after it consumes the CPU time allowed for the current interval. Requests may queue up even while the container keeps running. Compare request latency with CPU usage and throttling counters when available. Check whether the workload could run faster with more CPU or is waiting on something else.

A container can also hit its **memory limit**. The kernel can reclaim some memory, but if it cannot satisfy demand within the memory boundary it can kill a process. Kubernetes may report `OOMKilled` when the container terminates. The Pod’s restart policy then controls what happens to that container. Compare the traces in the first scene. A CPU throttle can explain latency without a restart, while a memory kill can explain a termination.

## <span id="walkthrough-pressure-can-remove-a-whole-pod" aria-hidden="true" />When the kubelet evicts a Pod

**Node pressure eviction** happens when the kubelet needs to reclaim a scarce resource on the whole node. It may first attempt cleanup such as deleting unused images, then evict Pods if pressure persists. For memory, it ranks candidates using whether usage exceeds requests, priority, and relative usage. The Pod can be marked `Failed` with reason `Evicted` even when its containers were below their individual limits. Its controller may create a replacement with a different UID.

## <span id="practice-explain-the-observed-termination" aria-hidden="true" />Inspect a container killed under its memory limit

Start with the CPU comparison in the [disposable kind lab](/labs/#setup). On a cgroup v2 node, read `nr_throttled` twice. The count can rise while the Pod still reports Running. Then run the existing memory exercise below to compare its termination evidence.

```bash
kubectl --context kind-kv-lab get namespace kv-lab >/dev/null 2>&1 || \
  kubectl --context kind-kv-lab create namespace kv-lab
kubectl --context kind-kv-lab -n kv-lab apply -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: trace-cpu-limit
spec:
  terminationGracePeriodSeconds: 1
  restartPolicy: Never
  containers:
    - name: busy
      image: busybox:1.37.0
      command: ["sh", "-c", "while true; do :; done"]
      resources:
        limits:
          cpu: 50m
          memory: 16Mi
YAML
kubectl --context kind-kv-lab -n kv-lab wait --for=condition=Ready pod/trace-cpu-limit --timeout=90s
kubectl --context kind-kv-lab -n kv-lab exec trace-cpu-limit -- grep '^nr_throttled ' /sys/fs/cgroup/cpu.stat
sleep 3
kubectl --context kind-kv-lab -n kv-lab exec trace-cpu-limit -- grep '^nr_throttled ' /sys/fs/cgroup/cpu.stat
kubectl --context kind-kv-lab -n kv-lab get pod trace-cpu-limit
kubectl --context kind-kv-lab -n kv-lab delete pod trace-cpu-limit
```

The teaching example mounts an in-memory `emptyDir` at `/memory`. The writer attempts to place 96 MiB in it with a 32 MiB container memory limit. Those file contents count toward memory use, so even a process writing to a filesystem can hit the memory boundary. Treat this as a small disposable experiment. The snippet names the Pod `m17-memory`. The inspection commands use `m17-oom`, the separate scenario supplied by the lab. Use the name that matches the exercise you ran.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: m17-memory
  namespace: kv-lab
  labels:
    lab: m17
spec:
  restartPolicy: Never
  containers:
    - name: fill
      image: busybox:1.37.0
      command: [dd, if=/dev/zero, of=/memory/blob, bs=1M, count=96]
      resources:
        requests:
          memory: 16Mi
          cpu: 10m
        limits:
          memory: 32Mi
          cpu: 100m
      volumeMounts:
        - name: memory
          mountPath: /memory
  volumes:
    - name: memory
      emptyDir:
        medium: Memory
```

```bash
kubectl --context kind-kv-lab -n kv-lab get pod m17-oom -o yaml
kubectl --context kind-kv-lab -n kv-lab describe pod m17-oom
kubectl --context kind-kv-lab get nodes
kubectl --context kind-kv-lab -n kv-lab get events --sort-by=.metadata.creationTimestamp
```

In the [performance lab](/labs/#m17), check the actual termination reason, exit code, and node conditions. Compare a container that was killed with the entire Pod being evicted. The exit code alone may be ambiguous.

## <span id="pitfalls-bigger-limits-can-move-the-bottleneck" aria-hidden="true" />Check the bottleneck before raising limits

Raising a limit can buy time for a legitimate workload, or move the pressure to the node if the process keeps growing. Observe memory over time, inspect allocations and cache behavior, and read container and node evidence before tuning. Keep runtime limits and placement requests in view together.
