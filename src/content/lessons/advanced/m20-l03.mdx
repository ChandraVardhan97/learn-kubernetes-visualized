## <span id="mental-model-each-controller-needs-a-clear-declaration-boundary" aria-hidden="true" />Declare a WebApp and derive its children

A platform user requests a web page called `m20-platform` with a message and one replica. The user needs a small declaration. The platform supplies a Deployment, Service, and ConfigMap. In this capstone, an apply manager called `kv-gitops` owns the WebApp specification. The operator reads the WebApp and derives the implementation resources. It manages their configuration and uses owner references to link them to that particular WebApp.

Trace the two responsibilities in the first scene. If the message changes, update the WebApp and let the operator propagate it. If a generated ConfigMap is deleted while the WebApp stays present, the operator can recreate it. This keeps the source of intent in a place the platform user can read and change.

## <span id="walkthrough-the-conflict-is-an-expected-result" aria-hidden="true" />Reproduce a field ownership conflict

The WebApp manifest is the declaration for this exercise. After applying it with `kv-gitops`, another apply manager called `kv-human` attempts to set a different value in an owned field. It should get a conflict. Inspect the management record and locate the field and owner. The chosen policy is to leave the original declaration in place.

```yaml
apiVersion: labs.kv.example/v1alpha1
kind: WebApp
metadata:
  name: m20-platform
  namespace: kv-lab
  labels:
    lab: m20
spec:
  replicas: 1
  message: gitops-declared-page
```

## <span id="practice-report-four-independent-observations" aria-hidden="true" />Verify repeated reconciliation, repair, and deletion

Use a disposable cluster. The [platform capstone](/labs/#m20-platform) script installs the CRD, applies the WebApp, runs the reconciler, checks the conflict and stable Deployment UID, deletes and repairs the ConfigMap, and finally deletes the parent. If you want to inspect the live resources, run the manual early steps after installing the CRD and before the script’s final delete. Record four observations: the conflict, stable UID during repeated passes, the recreated ConfigMap’s content, and disappearance of generated dependents after parent deletion.

```bash
# Run only the platform investigation from the downloaded m20 directory.
bash capstone-platform.sh
# To inspect before the script's final parent deletion, run its early steps manually:
kubectl --context kind-kv-lab -n kv-lab apply --server-side --field-manager=kv-gitops -f platform.yaml
python3 webapp-reconciler.py --iterations 2 --interval 1
kubectl --context kind-kv-lab -n kv-lab get webapp m20-platform -o yaml --show-managed-fields
kubectl --context kind-kv-lab -n kv-lab get deployment m20-platform -o yaml --show-managed-fields
```

## <span id="pitfalls-this-is-not-a-hidden-production-platform" aria-hidden="true" />Connect the exercise to production controllers

This capstone runs server-side apply and a local script. A production GitOps controller adds repository monitoring and policy, and a deployed operator needs watches, reliable retries, scoped permissions, and observability. The lab lets you verify the ownership model without needing either production component. Before adding persistent storage or external services, decide which parts of application state should remain when the WebApp is removed.
