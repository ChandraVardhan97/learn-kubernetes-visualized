## <span id="mental-model-a-mesh-introduces-another-control-and-data-path" aria-hidden="true" />Where a service mesh processes traffic

Checkout calls inventory and you want both sides to prove their workload identity while encrypting the connection. A **service mesh** manages selected application-to-application traffic using a control plane and traffic-handling components. A mesh control plane distributes configuration and often coordinates identity and certificates. Its data plane processes the covered connections using proxies. Depending on the mesh and its mode, those proxies can run alongside Pods or at the node or workload waypoint level.

With **mutual TLS (mTLS)**, both participants present credentials. On a mesh-managed hop, the traffic handlers can verify identities and encrypt transport. Authorization policy can then decide whether the calling identity may use the destination. Inspect the first scene to see where traffic goes when only one workload is enrolled or policy selects a different path.

## <span id="walkthrough-traffic-features-change-application-failure-behavior" aria-hidden="true" />How retries change request behavior

A mesh can also add timeouts, retries, traffic splitting, and telemetry where it understands the protocol. Those features change failures the application sees. If the mesh retries a request to charge a card after a timeout, the first attempt may already have succeeded. Only retry operations with suitable safety guarantees and give the overall request a sensible time budget.

## <span id="practice-write-an-ownership-map-before-installing-an-add-on" aria-hidden="true" />Identify which layer owns a policy

The sample NetworkPolicy permits ingress on port 80 from selected Pods in `kv-lab`. A compatible CNI enforces it at the network layer. An example mesh rule could make a different decision using a workload certificate or HTTP route if the traffic actually passes through the mesh. Meanwhile an infrastructure load balancer can control traffic before either policy sees it. Identify which layer owns each decision and how you would prove it.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: m19-web-ingress
  namespace: kv-lab
  labels:
    lab: m19
spec:
  podSelector:
    matchLabels:
      app: m19-web
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: m19-client
      ports:
        - protocol: TCP
          port: 80
```

## <span id="pitfalls-extra-machinery-has-costs-and-blind-spots" aria-hidden="true" />Verify where mesh coverage ends

Extra proxies can affect latency and resource use. Check certificate renewal, traffic coverage, and behavior when the control plane is temporarily unreachable. Existing proxies may keep prior configuration during an outage, while new workloads or updated policies need fresh state. The exact guarantees depend on the mesh implementation.
