## Mental model: a successful HTTP request is only the beginning

An API write passes several distinct boundaries. Authentication establishes the caller's identity from a credential; authorization decides whether that identity may perform this verb on this resource. Admission then evaluates the proposed operation. Mutating admission can supply or change fields, while validating admission can reject the resulting object. Successful persistence makes desired state visible; it does not prove a scheduler, controller, or kubelet has fulfilled it. A Deployment can be admitted successfully while all of its Pods remain Pending.

This separation makes incident evidence useful. A forbidden response points toward authorization or a policy rejection whose message explains the denial. An invalid object points toward schema or validation. A webhook timeout names a dependency on the write path. A stored Deployment with unavailable replicas requires downstream investigation. Do not restart application Pods to fix an API admission outage: the rejected desired state may never have reached storage at all.

## Walkthrough: mutation has consequences for validation

Consider an organization that requires every new Deployment to carry a team label. A mutating webhook could inject a default label; a validating rule then checks the final proposal. Mutation occurs before validating admission, but the complete API pipeline also includes decoding, defaulting, conversion and validation associated with the resource. The diagram deliberately summarizes these implementation details. Mutating webhook reinvocation is configurable; implementations must tolerate repeated calls and must not assume a durable ordering between independent mutators.

A webhook is an external HTTPS service with certificate trust, availability, latency and timeout concerns. Its admission review response permits, rejects, or mutates the request; it should not perform irreversible external work as though admission already committed. A ValidatingAdmissionPolicy instead evaluates CEL inside the API server. It is useful for expression-based object rules without an external round trip. A policy needs a binding to select enforcement scope and validation actions. Neither mechanism replaces RBAC: permission to request an operation and permission for the proposed contents are different decisions.

<Scene id="m14-l01-admission-mechanisms" />

The following complete example is an optional cluster-scoped exercise. Save it as `team-policy.yaml`; it targets only Deployments in namespaces labeled `training-policy=enabled`. Label a separate disposable namespace before experimenting. The binding is what enables denial.

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: kv-team-label
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: [apps]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [deployments]
  validations:
    - expression: "has(object.metadata.labels) && 'team' in object.metadata.labels"
      message: "metadata.labels.team is required"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: kv-team-label
spec:
  policyName: kv-team-label
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        training-policy: enabled
```

```bash
kubectl --context kind-kv-lab apply -f team-policy.yaml
# An authorization check does not execute this admission policy.
kubectl --context kind-kv-lab auth can-i create deployments -n kv-lab
# Clean up the optional cluster-scoped objects explicitly.
kubectl --context kind-kv-lab delete validatingadmissionpolicybinding kv-team-label
kubectl --context kind-kv-lab delete validatingadmissionpolicy kv-team-label
```

## Practice: predict the boundary before inspecting the result

Use the [m14 local exercise](/labs/#m14) for safe API ownership and deletion experiments. The optional policy above extends that investigation; the downloadable lab does not install a highly available webhook service. Compare a server-side dry run with a real apply in a disposable selected namespace. A server-side dry run still traverses applicable admission. Matching webhooks must declare `sideEffects: None` or `NoneOnDryRun` and suppress any side effects for the dry run; an incompatible declaration makes the dry-run request fail. Expect the missing-label request to fail before a new Deployment is stored. Add the label and expect admission success, then independently inspect rollout status.

Record the verb, resource, namespace, response message and whether an object with the expected UID exists. These facts distinguish a rejected request from a controller that has not converged. Existing objects are not automatically scanned and deleted when a new validation policy is introduced; its matching operations govern subsequent requests.

## Pitfalls: protect the write path

A fail-closed webhook can prevent matching writes when its service, DNS, certificate, or endpoints fail. A fail-open configuration trades availability against policy enforcement when calling the webhook fails; `failurePolicy: Ignore` does not override an explicit `allowed: false` response. Select narrowly, use short timeouts, monitor rejection and latency, and design an emergency recovery route that still respects the organization's approval boundary. Excluding a webhook's own dependencies can prevent circular recovery failures. Do not interpret a healthy webhook Pod as proof that the API server can reach its HTTPS endpoint or validate its certificate.
