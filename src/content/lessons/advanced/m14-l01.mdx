## <span id="mental-model-a-successful-http-request-is-only-the-beginning" aria-hidden="true" />Where the API can reject a write

A deployer submits a Deployment in a team namespace. The deployer has permission to create Deployments, but the request omits the label required for ownership. Kubernetes evaluates the request through several gates. **Authentication** establishes the caller’s identity. **Authorization** evaluates the operation, resource, and namespace for that identity. **Admission** acts on the proposed change after those checks. The API server also validates the object and, for an accepted ordinary write, persists the result to storage. Controllers learn about it and work on it afterwards.

A bad credential can yield an authentication error. A correctly identified identity may get a forbidden response from authorization. A permitted writer can get a denial from admission. Identify the gate using the API’s status and message. In the scene, try the same Deployment with different callers and labels.

## <span id="walkthrough-mutation-has-consequences-for-validation" aria-hidden="true" />Add and validate a required team label

**Mutating admission** can change an incoming object. A webhook might add labels or defaults before **validating admission** checks what would be written. A **ValidatingAdmissionPolicy** uses CEL, the Common Expression Language, for in-process validation. It needs a matching binding to apply. In the example, the policy checks for the `team` label on a Deployment’s own metadata during create or update. The `Deny` binding applies in namespaces labeled `training-policy=enabled`. A team label only on the Pod template does not satisfy that expression.

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: kv-team-label
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: [apps]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [deployments]
  validations:
    - expression: "has(object.metadata.labels) && 'team' in object.metadata.labels"
      message: "metadata.labels.team is required"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: kv-team-label
spec:
  policyName: kv-team-label
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        training-policy: enabled
```

## <span id="practice-predict-the-boundary-before-inspecting-the-result" aria-hidden="true" />Test authorization and admission separately

Save the manifest as `team-policy.yaml`. Use a disposable `kind-kv-lab` cluster and an authorized account before applying the cluster-scoped objects. Label only the target training namespace for the policy. Run `kubectl auth can-i` to check the verb. Then submit a Deployment with and without the label using server-side dry run. The dry run exercises admission without storing the Deployment, subject to admission support. When finished, remove the binding and policy using the cleanup commands.

```bash
kubectl --context kind-kv-lab apply -f team-policy.yaml
# An authorization check does not execute this admission policy.
kubectl --context kind-kv-lab auth can-i create deployments -n kv-lab
# Clean up the optional cluster-scoped objects explicitly.
kubectl --context kind-kv-lab delete validatingadmissionpolicybinding kv-team-label
kubectl --context kind-kv-lab delete validatingadmissionpolicy kv-team-label
```

## <span id="pitfalls-protect-the-write-path" aria-hidden="true" />Plan for admission failures

A webhook runs in the critical path of affected requests. Its timeout and availability matter. A webhook’s `failurePolicy` controls how invocation errors such as timeouts are handled. An explicit denial from a successfully called webhook still rejects the request. Keep matching scopes tight and decide how operators can recover if admission blocks an important change.
