## Mental model: capacity is a constrained budget

Node capacity and node allocatable are different quantities. The operating system, kubelet and other reserved functions consume resources, leaving allocatable capacity for Pods. DaemonSets then occupy part of that budget on each eligible node. The scheduler compares Pod requests with available accounting and placement constraints. Summing physical CPU cores and dividing by a container's observed average CPU use therefore overstates what you can safely promise a workload.

A simple planning estimate starts with allocatable resources after required system workloads, then checks both CPU and memory requests. The tighter resource sets a rough upper bound, but fragmentation, topology, ports, Pod limits and volumes can lower it further. A Pod requiring one large memory allocation cannot use small free fragments distributed across several nodes. ResourceQuota limits namespace consumption; it does not manufacture feasible capacity or reserve a replacement node during a failure.

## Walkthrough: the spare capacity has a job

Capacity must cover more than the steady-state replica count. A rolling Deployment may temporarily run surge Pods while old replicas remain. Draining a node moves demand onto the remaining pool. Losing a zone can concentrate replicas in fewer failure domains. Startup probes, image pulls, cache warming and storage attachment delay the point when replacements serve traffic. Headroom is the explicit budget for these transitions, rather than an unexplained percentage chosen after an outage.

Horizontal workload scaling and node autoscaling form separate feedback loops. HPA changes desired replicas from metrics, while node autoscaling typically reacts to unschedulable demand and provider-specific signals. New node provisioning may fail because of cloud quota, unavailable instance types, subnet limits or required-zone constraints. A local kind cluster cannot reproduce those provider contracts by creating more Pods. Treat its resource behavior as mechanism practice and validate real capacity decisions in the target environment.

The following quota is a complete example of a namespace budget. It intentionally does not promise where those requests fit. Save as `capacity-quota.yaml` only if you want an isolated optional quota experiment; quotas can reject later requests in the namespace until removed.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: m17-budget
  namespace: kv-lab
  labels:
    lab: m17
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.memory: 4Gi
    pods: "20"
```

```bash
kubectl --context kind-kv-lab get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory
kubectl --context kind-kv-lab describe node kv-lab-control-plane
kubectl --context kind-kv-lab -n kv-lab get pods -o wide
kubectl --context kind-kv-lab -n kv-lab get resourcequota
# If the optional example was applied, remove just that budget afterward.
kubectl --context kind-kv-lab -n kv-lab delete resourcequota m17-budget --ignore-not-found
```

## Practice: plan for one failure and one rollout

Use the [m17 local exercise](/labs/#m17) to connect a container's request and limit to observed behavior. Then sketch three identical nodes with one CPU allocatable each after required system workloads. A service has six replicas requesting 250 millicores each. The aggregate request fits, but ask whether it also fits after one node fails and while a rollout creates two surge Pods. Include memory and placement constraints before claiming the plan works.

Compare the sketch with `describe node` allocated-resource output. That output reflects declared requests and limits, not a complete history of actual resource contention. For production planning, combine declarations with measured distribution, startup peaks and a failure drill. Record the assumptions behind any calculated replica ceiling. A capacity model is useful because it identifies what must be measured and tested; it is not evidence that an untested failure will meet an availability objective.

## Pitfalls: more objects also load the control plane

Many short-lived Pods increase API writes, watch events, scheduling work, admission calls and etcd churn. More controller workers can increase throughput until the API, admission dependency or external service becomes the bottleneck. High-cardinality metrics and verbose logs can strain observability systems before CPU becomes the limiting application resource. Use backoff, bounded concurrency, event aggregation and sensible object lifetimes. Avoid treating published scalability envelopes as guarantees for your object mix and add-ons.

A service can have spare Kubernetes capacity while its database, connection pool or upstream quota is exhausted. Inspect latency, errors, queue length and dependency saturation together. Scaling one layer should be an experiment with an expected bottleneck change, not an automatic response to every slowdown.
