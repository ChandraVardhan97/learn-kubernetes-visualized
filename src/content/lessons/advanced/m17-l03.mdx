## <span id="mental-model-capacity-is-a-constrained-budget" aria-hidden="true" />Find room for each Pod on an eligible node

Six API replicas each request half a CPU and 512 MiB of memory. They need at least three allocatable CPUs and 3 GiB of memory in total. Kubernetes schedules one Pod at a time on one viable node, though. Half a CPU spare across the cluster might be split into small amounts no single new Pod can use. If the workload also needs a particular zone or storage topology, only nodes in suitable locations count.

**Allocatable capacity** is what a node reports as available for Pods after applicable reservations. Subtract requests already assigned, including node agents, and consider Pod overhead where a RuntimeClass specifies it. Check both CPU and memory alongside other constraints such as Pod count, taints, and device availability. Use the budget scene to see why a single total can hide a placement failure.

## <span id="walkthrough-the-spare-capacity-has-a-job" aria-hidden="true" />Plan for a failure during a rollout

**Headroom** means capacity left for events you expect, such as a rollout, drain, or sudden increase in demand. Imagine three eligible nodes each carrying two replicas at half a CPU apiece. Lose one node and the remaining nodes need room for two replacement Pods. If a rolling update also permits one surge replica, you need space for three additional placements on those remaining nodes to handle that overlap. Observe how the answer changes if the replacements need to spread across failure domains.

## <span id="practice-plan-for-one-failure-and-one-rollout" aria-hidden="true" />Compare the namespace and node budgets

Read both physical and namespace budgets. The illustrative quota allows two CPUs in requests. In the six-replica example, the quota would reject some Pods even if every node had spare CPU. Five 400m replicas also use the full two-CPU budget and leave nothing for a rollout surge. Review quota usage, then inspect node allocatable and assigned requests. The example quota is optional in the disposable lab and the cleanup removes only that quota.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: m17-budget
  namespace: kv-lab
  labels:
    lab: m17
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.memory: 4Gi
    pods: "20"
```

```bash
kubectl --context kind-kv-lab get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory
kubectl --context kind-kv-lab describe node kv-lab-control-plane
kubectl --context kind-kv-lab -n kv-lab get pods -o wide
kubectl --context kind-kv-lab -n kv-lab get resourcequota
# If the optional example was applied, remove just that budget afterward.
kubectl --context kind-kv-lab -n kv-lab delete resourcequota m17-budget --ignore-not-found
```

Use the [capacity lab](/labs/#m17) to calculate which placement or admission requirement is limiting you. Name the event you want to tolerate and verify that spare capacity remains on eligible nodes after that event.

## <span id="pitfalls-more-objects-also-load-the-control-plane" aria-hidden="true" />Check control-plane load as the cluster grows

Cluster growth affects the control plane too. More Pods generate more API objects, watch events, leases, and status changes. When expanding a cluster, observe scheduling latency and API server and etcd performance alongside node utilization. Resource availability for workload Pods and capacity to coordinate them can become separate bottlenecks.
