## <span id="mental-model-a-healthy-pod-is-one-link-in-the-request-path" aria-hidden="true" />Investigate a healthy app that clients cannot reach

You are on call for a small web app. The Deployment reports ready Pods, but a client in the same namespace cannot load the page. Your task is to find the first failed link in the request path, change only what is needed, and prove the page is reachable again. You will use the Pod and Service concepts from foundations together with the evidence-gathering workflow from the debugging modules.

Start by checking that you are in the disposable cluster and using the `kv-lab` namespace. Use the failure scene to predict which evidence shows whether the Pods are ready and whether the Service routes to them. In this incident, a DNS answer can succeed because the Service exists. The request can still fail because its backend set is empty.

## <span id="walkthrough-narrow-the-investigation-before-changing-state" aria-hidden="true" />Find and repair the selector mismatch

The example Service is intentionally broken. It selects `app: broken-selector`. The Deployment’s Pods carry `app: m20-web`. Inspect the labels and the Service selector together, and use EndpointSlices to check which eligible addresses are actually published. Try the request from `m20-client` using `http://m20-web`. Note the result rather than relying only on status columns.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: m20-web
  namespace: kv-lab
  labels:
    lab: m20
spec:
  selector:
    app: broken-selector # Deployment Pods actually use app=m20-web.
  ports:
    - port: 80
      targetPort: 80
```

Predict what will change after replacing the Service selector with `app: m20-web`. The Service name and existing healthy Pods can stay in place. The endpoint controller can publish matching backend addresses. Wait for those endpoints to be eligible, then repeat the original request. Trace the change in the recovery scene.

## <span id="practice-produce-a-short-recovery-record" aria-hidden="true" />Record the recovered request path

Download all module files and follow the [stateless capstone](/labs/#m20-stateless). This script sets up the deliberate failure, proves the request fails, repairs the selector, and verifies the response. Pause to predict before following the solution, or run the guided stages described in the lab. Keep a short record of the original symptom, the Pods’ actual labels, the correction, the EndpointSlice evidence, and the response seen by the same client.

```bash
# Download all m20 files first, then run only this investigation.
bash capstone-stateless.sh
# Read-only follow-up evidence after the script's repair.
kubectl --context kind-kv-lab -n kv-lab get pods -l app=m20-web --show-labels
kubectl --context kind-kv-lab -n kv-lab get service m20-web -o yaml
kubectl --context kind-kv-lab -n kv-lab get endpointslices -l kubernetes.io/service-name=m20-web -o yaml
kubectl --context kind-kv-lab -n kv-lab exec m20-client -- wget -qO- -T 3 http://m20-web
```

## <span id="pitfalls-avoid-fixing-the-symptom-by-changing-unrelated-layers" aria-hidden="true" />Fix the resource that owns the setting

Restarting already-ready Pods would leave the wrong selector in place. Relabeling those Pods by hand could produce a temporary match and leave the Deployment template wrong for future Pods. Fix the configuration relationship that caused the incident, and check that it still works after a healthy copy is replaced if you want to go further.
