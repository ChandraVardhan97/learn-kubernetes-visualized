## <span id="mental-model-trust-has-several-directions" aria-hidden="true" />Which identity each TLS connection verifies

Your kubeconfig points to the cluster API, but the client refuses the TLS connection. Before examining RBAC, ask whose identity failed to verify. A server certificate lets the client confirm it reached the expected endpoint and that the certificate chains to a trusted authority. Its subject alternative names must include the hostname or IP the client uses. The API server separately authenticates the caller, which can present a client certificate, a token, or another supported credential. Control-plane components and etcd have additional connections with their own trust and credentials.

**Public key infrastructure (PKI)** is how a cluster issues, trusts, and renews those certificates and protects their private keys. In the scene, distinguish the API serving identity, the client used for authentication, and an internal connection to another component.

## <span id="walkthrough-renewal-is-not-guaranteed-process-reload" aria-hidden="true" />Renew certificates and verify the served certificate

On a kubeadm-managed node, `kubeadm certs check-expiration` can help inspect locally managed credential lifetimes. The owner of an externally managed certificate follows its own renewal process. A certificate file can be renewed while a running process still has the previous certificate loaded. Identify how each component reloads credentials and confirm it presents or uses the renewed certificate afterwards. Keep private keys and kubeconfigs out of ConfigMaps, logs, and shared source directories.

apiVersion: v1

## <span id="practice-plan-an-intermediate-state-explicitly" aria-hidden="true" />Check every stage of an upgrade

A cluster upgrade temporarily runs components at different versions. The **version skew policy** defines supported differences, and kubeadm and other distributions can impose further ordering constraints. Plan one supported minor upgrade at a time according to your tool’s guidance. Make an inventory of API servers, kubelets, kubectl, and add-ons. Check CNI, CSI, admissions, and controllers for compatibility. On a multi-control-plane cluster, verify that the intermediate versions of API servers behind the load balancer are also supported.

```bash
kubectl --context kind-kv-lab version
kubectl --context kind-kv-lab get nodes -o custom-columns=NAME:.metadata.name,KUBELET:.status.nodeInfo.kubeletVersion
kubectl --context kind-kv-lab get --raw='/readyz?verbose'
# Host-side commands below are read-only checks on a kubeadm-managed node.
# They are not instructions to upgrade the kind node image in place.
# sudo kubeadm certs check-expiration
# sudo kubeadm upgrade plan
```

The [control-plane recovery lab](/labs/#m18) provides read-only checks on the local environment. Practice by writing down a current version, next intermediate state, and health checks. Running `kubeadm upgrade plan` belongs on an appropriate kubeadm-managed node. Upgrading a kind teaching cluster in place is outside that exercise.

## <span id="pitfalls-the-rollback-boundary-may-be-a-restore" aria-hidden="true" />Plan recovery before changing versions

An upgrade can affect storage formats, removed APIs, and add-on behavior. A viable recovery may require restoring a backup rather than installing old binaries. Verify API readiness, node readiness, and representative workload requests after each stage, and establish how to recover before starting the next stage.
