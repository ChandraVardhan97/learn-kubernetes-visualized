## Mental model: trust has several directions

Kubernetes PKI includes server identities, client identities and signing authorities with different purposes. A kubelet or administrator verifies the API server's serving certificate; the API server authenticates a client credential; API-to-kubelet and etcd communication have their own trust relationships. Service-account token signing keys and encryption-at-rest keys are additional assets with separate rotation and recovery requirements. Calling all of these files the cluster certificate hides which communication path actually failed.

An expired certificate, an untrusted issuer and a hostname or IP missing from a serving certificate's subject alternative names produce different evidence. Inventory issuer, subject, SANs, expiry, file location and which process reads the file. External-CA deployments have different responsibilities from kubeadm-managed defaults. A healthy clock matters because certificate validity uses time. Do not solve an identity error by disabling verification; repair the intended trust relationship and endpoint identity.

## Walkthrough: renewal is not guaranteed process reload

kubeadm provides certificate inspection and renewal workflows, but generating a renewed file is only one step. Components must actually begin using the new credential. Static control-plane Pods may require controlled restart according to the documented procedure, and copied administrative kubeconfigs may still hold old embedded client data. In an HA topology, work through control-plane nodes deliberately and preserve quorum and a reachable API endpoint throughout the maintenance.

An upgrade plan starts with exact current and target versions, API removals, add-on compatibility, verified backups and a recovery strategy. Follow the release-specific kubeadm guide rather than skipping arbitrary minor versions. The Kubernetes skew policy constrains component combinations: kubelets must not be newer than the API servers they use, kubectl has its own supported skew window, and HA API server versions affect the permissible range of other components. Consult the current table for every intermediate state rather than memorizing one broad statement that all components may differ by several releases.

## Practice: plan an intermediate state explicitly

Use the [m18 local exercise](/labs/#m18) for recovery assets and read-only control-plane inspection. The site's version baseline is Kubernetes 1.37, reviewed on 2026-10-27. This lesson deliberately does not provide a blanket command to upgrade a live cluster to that version. kind node images, managed services and self-managed kubeadm clusters have different lifecycle procedures. Use the relevant provider or release-specific documentation for the actual environment.

Write an upgrade table with rows for each API server, scheduler/controller-manager, kubelet, kube-proxy, kubectl and critical add-on. For each maintenance step, record the before and after version and check the supported overlap. Include drain behavior, disruption budgets, spare worker capacity and verification before proceeding. A blocked drain is evidence to investigate, not an automatic reason to bypass every disruption budget. Test admission webhooks and CRD conversion paths against the new API behavior before making the intermediate state production reality.

## Pitfalls: the rollback boundary may be a restore

Downgrading binaries is not a universal rollback strategy after storage formats, APIs or add-ons change. Define whether recovery means rolling back an application manifest, replacing a node, restoring a control-plane snapshot or following a provider-supported procedure. Keep compatible binaries, PKI, signing keys, encryption configuration and external data backups available under appropriate access controls. A backup taken after a bad migration may preserve the bad state very reliably.

Certificate renewal can cause outages when a component continues using the old file or a client receives a new CA without trust propagation. CA rotation is more complex than renewing a leaf certificate under the same CA. Avoid copying private keys into a lesson ConfigMap, support ticket or shell history. Record fingerprints and expiry metadata instead.
