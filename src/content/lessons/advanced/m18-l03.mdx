## <span id="mental-model-back-up-the-state-you-intend-to-recover" aria-hidden="true" />Choose what to back up separately

A cluster is lost after a storage failure. You need to recover Deployment and Service definitions, the credentials saved through the API, and the files written by a stateful workload. An **etcd snapshot** captures persisted Kubernetes API records at a point in time. It can restore a PVC object and information about a workload. The volume bytes are in a separate storage system and need their own backup. Include network and cloud resources, cluster configuration, and keys needed to decrypt encrypted API data in the recovery inventory.

In the scene, classify what can be recovered from the API snapshot and what must come from another source. Decide how much recent data you can afford to lose and how long a recovery can take, then choose how often to capture each source.

## <span id="walkthrough-restore-is-an-isolated-reconstruction" aria-hidden="true" />Restore an isolated etcd cluster

An etcd snapshot restore builds new member data directories. It needs deliberate cluster membership and separation from the original members. A snapshot may also be behind the revisions Kubernetes watchers have already seen. Upstream etcd guidance for Kubernetes recommends a revision bump and marking history compacted so clients with stale watches are forced to relist. Review the procedure for your etcd version and rehearse on a separate target.

## <span id="practice-verify-the-boundary-of-the-rehearsal" aria-hidden="true" />Verify the restored objects

The disposable lab creates a known ConfigMap before taking its backup. From the downloaded module directory, the script writes recovery material to a private host directory. Inspect the runbook before starting the optional offline restore. Use the separate recovery kubeconfig to verify the marker in `kv-recovery`, compare its value to the captured state, and discard only the isolated cluster when finished.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: m18
  namespace: kv-lab
  labels:
    lab: m18
data:
  marker: captured-before-disaster
```

```bash
# In the downloaded m18 directory: captures to a private host directory.
bash run.sh
backup_dir=$(python3 backup-path.py m18)
# Inspect RECOVERY.md and restore-offline.sh before this optional step.
bash restore-offline.sh
# Use the separate file produced by the recovery script, never your active context.
KUBECONFIG="$backup_dir/recovery.kubeconfig" kubectl -n kv-lab get configmap m18 -o yaml
# Discard only the isolated rehearsal target after inspection.
KUBECONFIG="$backup_dir/recovery.kubeconfig" kind delete cluster --name kv-recovery
```

The [backup and recovery lab](/labs/#m18) demonstrates a single-member snapshot restore. That lets you verify API state and the separation of targets. A production plan must also test restored certificates, decryption, adequate etcd membership, storage reattachment or data recovery, and application health with real dependencies.

## <span id="pitfalls-restored-intent-can-immediately-act" aria-hidden="true" />Keep restored controllers away from live systems

Restored controllers can act on old intent. They might see a Job ready to run or a cloud resource that the primary environment still manages. Isolate credentials and external connections while verifying the restored API. Check backup age and integrity, compare expected object records, and verify application data separately.
