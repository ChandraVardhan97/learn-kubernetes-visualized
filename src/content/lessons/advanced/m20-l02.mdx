## <span id="mental-model-persistence-also-preserves-mistakes" aria-hidden="true" />Distinguish Pod replacement from a deleted file

A worker writes an order record to `/data/orders.csv` on a persistent volume. Later the file is deleted by mistake. Recreating the Pod with the same claim leaves the data in its current state, including the missing file. Your task is to take a small backup before the loss, restore the data, and prove that a new Pod sees the recovered bytes. Crash and replacement recovery exercise different mechanisms from recovering an application record deleted on disk.

The PVC below requests 64 MiB. The lab’s writer mounts that claim and writes a known fixture. The first scene lets you compare replacement with deletion inside the volume. Before running the loss step, record the expected value and the backup’s checksum.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: m20
  namespace: kv-lab
  labels:
    lab: m20
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 64Mi
```

## <span id="walkthrough-consistency-is-an-explicit-assumption" aria-hidden="true" />Restore known bytes from a host backup

The lab uses a single small fixture with no concurrent writer while the backup is captured. The script copies it out to a private host directory and checks the exact expected bytes. It deletes the file only after that check. A real database can have open transactions and internal buffers, so choose a database-supported backup procedure and test the recovery point before relying on it.

The restore uses `kubectl cp` with a container image that has `tar`. It verifies the copied bytes against the host backup before removing the original Pod. The replacement mounts the same PVC, and the script reads the file again from inside that Pod, comparing length and checksum. Follow both checkpoints in the restore scene.

## <span id="practice-make-each-recovery-claim-testable" aria-hidden="true" />Verify the file before and after replacement

Use all files from the [stateful capstone](/labs/#m20-stateful). Run the staged procedure if you want to observe and diagnose each boundary. Record the original Pod UID and the recovered Pod UID, confirm the claim stayed bound, and compare file bytes at both checkpoints. The read-only follow-up commands display the synthetic fixture. In a real incident, prefer integrity evidence you can safely share over exposing private records.

```bash
# Run in the downloaded m20 directory.
bash capstone-stateful.sh
# Verify the backup is retained on the host and the restored value is mounted.
backup_dir=$(python3 backup-path.py m20)
cat "$backup_dir/orders.csv"
kubectl --context kind-kv-lab -n kv-lab exec m20-data -- cat /data/orders.csv
kubectl --context kind-kv-lab -n kv-lab get pvc m20 -o wide
kubectl --context kind-kv-lab -n kv-lab get pod m20-data -o jsonpath='{.metadata.uid}{"\n"}'
```

## <span id="pitfalls-data-integrity-needs-application-knowledge" aria-hidden="true" />Test the recovery your application needs

A new Pod name or a ready status does not tell you whether it restored the intended data. Verify records that matter to the application and the time period you need. This exercise gives direct evidence for file recovery and persistence on the same claim. Recovering from a lost node, a lost volume, or an inconsistent database requires additional scenarios.
