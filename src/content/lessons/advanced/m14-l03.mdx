## <span id="mental-model-deletion-is-a-protocol" aria-hidden="true" />What can hold up object deletion

An object represents a volume that lives outside Kubernetes. Deleting the API record immediately could leave that storage running with nobody responsible for it. A **finalizer** is a key on an object that keeps it present during deletion. The API server sets `deletionTimestamp`. A controller that understands the finalizer observes the request, performs or verifies external cleanup, and removes its key. The API can finish deleting the object when the finalizers are cleared.

In the scene, delete an object with a finalizer, then follow the controller that removes it. The key is a barrier, and actual cleanup depends on a working controller. If the controller has lost permissions or the external system is unavailable, the object may remain in a deleting state.

## <span id="walkthrough-ownership-identifies-the-dependent-not-a-name-match" aria-hidden="true" />How Kubernetes finds dependents

**Garbage collection** deals with dependencies between Kubernetes objects. An owner reference records the owning object’s identity, including its UID. A ReplicaSet can disappear and another object can be created under the same name, but the replacement has a different UID. The old dependents do not acquire a new owner just by matching its name. Deletion propagation controls whether dependents are cleaned up in the background, deleted before a foreground owner deletion completes when they block it, or left as orphans.

## <span id="practice-prove-which-lifecycle-is-active" aria-hidden="true" />Inspect an object held by a finalizer

Save the ConfigMap as `held.yaml` and try it only in the disposable cluster. The exercise adds a finalizer deliberately left without a controller. With `--wait=false`, the delete command returns while the finalizer still holds the object. Inspect the timestamp and key. The final patch removes the artificial hold. In a real cluster, identify which cleanup the controller owes before considering manual removal.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: m14-held
  namespace: kv-lab
  labels:
    lab: m14
  finalizers:
    - labs.kv.example/hold # No controller implements this training key.
data:
  purpose: inspect-deletion
```

```bash
kubectl --context kind-kv-lab -n kv-lab apply -f held.yaml
kubectl --context kind-kv-lab -n kv-lab delete configmap m14-held --wait=false
kubectl --context kind-kv-lab -n kv-lab get configmap m14-held -o yaml
# Only the artificial hold is removed in this isolated exercise.
kubectl --context kind-kv-lab -n kv-lab patch configmap m14-held --type=merge -p '{"metadata":{"finalizers":[]}}'
kubectl --context kind-kv-lab -n kv-lab wait --for=delete configmap/m14-held --timeout=30s
```

Use the [API mechanics lab](/labs/#m14) to inspect the delete request, then confirm the object has actually gone.

## <span id="pitfalls-a-shorter-object-list-can-hide-damage" aria-hidden="true" />Prepare to retire an API version

An API version also has a lifecycle. A newer version can serve objects under a different representation while old clients still send requests to the old endpoint. Before removing a version, identify manifests, scripts, and controllers using it. Update their requests and check how existing objects are stored. For a custom resource, migrate persistence and check the CRD’s stored versions as part of retiring a storage version. Follow the API evolution scene to distinguish serving a version from storing data in that version.
