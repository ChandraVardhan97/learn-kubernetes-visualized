## <span id="mental-model-three-questions-with-different-consequences" aria-hidden="true" />Which probe answers which question

Imagine an application with a long startup, an occasional failed connection to a dependency, and a bug that can freeze its request handler. The kubelet uses a **probe** to test a container. Each probe has a different consequence, so decide what should happen after a check fails before you decide what the check should test.

A **startup probe** gives an application time to initialize. While this probe has yet to succeed, the kubelet holds back readiness and liveness probing. If startup failures reach the configured threshold, the kubelet terminates the container and the restart policy applies.

A **readiness probe** asks whether the application can accept traffic now. After repeated failures, the Pod becomes unready and normal Service routing excludes it. The container can continue running and regain readiness. A **liveness probe** asks whether the container should be restarted to recover. If liveness fails repeatedly, the kubelet stops the container and handles restart according to policy. Try each failure in the scene and watch which state changes.

## <span id="walkthrough-configure-real-paths" aria-hidden="true" />Configure the three HTTP checks

Save this example as `probes-demo.yaml`. All three probes use the same HTTP path here so you can focus on how their timing and consequences differ. The named port `http` resolves to port 80. The startup probe’s two-second period and 30-failure threshold give the process roughly a minute to start. In a real application, separate endpoints may check different things. For example, an app might report unready while a required backend is down but still report live because restarting it would achieve nothing.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: probes-demo
spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: web
      image: nginx:1.27.5
      ports:
        - name: http
          containerPort: 80
      startupProbe:
        httpGet:
          path: /
          port: http
        periodSeconds: 2
        failureThreshold: 30 # Roughly a 60-second startup window, not an SLA.
      readinessProbe:
        httpGet:
          path: /
          port: http
        periodSeconds: 5
        failureThreshold: 2
      livenessProbe:
        httpGet:
          path: /
          port: http
        periodSeconds: 10
        failureThreshold: 3
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "nginx -s quit"]
```

After applying the file, note `READY` and `RESTARTS` in the watch. The describe output reports failed probes in Events when failures occur. Record the restart count as a baseline for a later failure.

```bash
kubectl apply -f probes-demo.yaml
kubectl get pod probes-demo -w
kubectl describe pod probes-demo
kubectl get pod probes-demo -o jsonpath='{.status.containerStatuses[0].restartCount}'
```

## <span id="practice-trace-a-deliberate-shutdown" aria-hidden="true" />Follow a Pod through shutdown

When you delete the Pod, graceful termination gives the application a bounded time to stop. The kubelet runs the `preStop` hook in this example, which asks nginx to shut down gracefully. The hook uses part of the 30-second period. During termination, the endpoint is marked terminating and stops receiving normal new Service traffic as the change propagates. Connections already established can continue until the application closes them or the grace period expires. Step through both routing and process shutdown in the scene.

## <span id="pitfalls" aria-hidden="true" />Choose failures that justify a restart

A service with a failing shared dependency can lose every replica if the liveness check restarts all the containers. Give slow startup its own budget and scope liveness to failures a restart can fix. A long-lived connection can outlast an endpoint’s readiness change, so the application still needs a plan for finishing or closing active requests.
