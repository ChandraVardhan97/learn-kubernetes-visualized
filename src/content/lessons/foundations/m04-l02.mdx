## Mental model: setup versus continued cooperation

A regular init container runs before ordinary app containers and must complete successfully before the next regular initialization step proceeds. Multiple regular init containers run in their specified sequence. They can perform setup using a different image from the main application, such as preparing a configuration file or checking a prerequisite. They are not permanent background workers. A regular init command that sleeps forever prevents the application from starting.

A sidecar is a helper that remains active alongside the main application. Kubernetes supports a restartable sidecar as an entry in `initContainers` with container-level `restartPolicy: Always`. It starts as part of initialization and keeps running, with independent restart supervision. An older pattern uses two ordinary app containers in `containers`; that can still be useful, but it does not express the same ordered sidecar lifecycle. Identify which pattern a manifest actually uses.

A sidecar is not a remote dependency made local by naming it a sidecar. It shares the Pod's placement, network namespace, and lifecycle boundary. It consumes resources and can affect readiness and termination. If it needs independent scaling or release cadence, a separate workload may fit better. Shared placement is a coupling decision, not a default way to assemble every service.

## Walkthrough: create content before serving it

The following complete Pod uses a regular init container to write one file into an emptyDir. nginx then serves that shared file. A restartable sidecar watches the same file and writes only training content to its own stdout. Save it as `collaboration-demo.yaml` in your disposable lab namespace.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: collaboration-demo
spec:
  initContainers:
    - name: prepare
      image: busybox:1.36.1
      command: ["sh", "-c", "printf 'prepared by init\n' > /work/index.html"]
      volumeMounts:
        - name: page
          mountPath: /work
    - name: observer
      image: busybox:1.36.1
      restartPolicy: Always # Restartable init sidecar: keep running.
      command: ["sh", "-c", "while true; do cat /work/index.html; sleep 10; done"]
      volumeMounts:
        - name: page
          mountPath: /work
          readOnly: true
  containers:
    - name: web
      image: nginx:1.27.5
      volumeMounts:
        - name: page
          mountPath: /usr/share/nginx/html
          readOnly: true
  volumes:
    - name: page
      emptyDir: {} # Pod lifetime, not persistent storage.
```

The mount paths differ between containers but refer to the same volume. `/work/index.html` in the initializer becomes `/usr/share/nginx/html/index.html` in nginx. Root filesystems remain separate. The init image's shell does not somehow become installed in the nginx image.

```bash
kubectl apply -f collaboration-demo.yaml
kubectl describe pod collaboration-demo
kubectl logs collaboration-demo -c prepare
kubectl logs collaboration-demo -c observer --tail=10
kubectl port-forward pod/collaboration-demo 8080:80
```

Request `http://127.0.0.1:8080/` while the forward runs. Expect the prepared text if startup succeeds. The prepare container may emit no stdout because its command writes to a file. Its successful termination state, rather than a nonempty log, shows completion. Inspect `status.initContainerStatuses` to distinguish completed setup from the still-running observer sidecar.

## Practice: predict a blocked initializer

In a new disposable Pod, make the regular initializer exit 1. Under the basic Always Pod restart policy, the kubelet retries failed initialization, and the ordinary application waits. Inspect init status and `kubectl logs ... -c prepare`, not only the nginx log. If a regular initializer waits for the web process in that same Pod, it can create a circular dependency: the web process cannot start until initialization finishes.

Initialization should be safe to retry. A script that appends duplicate configuration or performs an irreversible database migration on every restart needs a stronger design. Keep setup idempotent, bound external waits, and make failures observable. For changes requiring coordination across many replicas, a Pod-local initializer is not a global deployment lock or a transactional migration controller.

## Pitfalls

Starting a sidecar process does not necessarily mean it is ready to accept connections. Where startup ordering depends on actual readiness, use an appropriate startup probe and verify the sidecar lifecycle semantics. Merely placing a proxy first in YAML is not a health contract. A readiness probe on a sidecar can also contribute to Pod readiness, so test the effect of helper failure on traffic eligibility.

The shared emptyDir survives an individual container restart in this Pod, but replacement of the Pod creates a new emptyDir and reruns initialization. Keep durable business data outside this training volume. Also consider permissions: sharing a volume does not guarantee both images' users can read or write the same files.
