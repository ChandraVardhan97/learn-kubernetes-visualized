## <span id="mental-model-every-command-has-a-destination" aria-hidden="true" />Where kubectl sends your command

You have two Kubernetes clusters open on your laptop, one for practice and one at work. Both have a namespace called `default`. A command like `kubectl get pods` only makes sense once you know which cluster and namespace it targets, and which identity will make the request.

A **kubeconfig** is a client configuration file. Its **cluster** entries describe API endpoints and trust settings. Its **user** entries specify how the client obtains credentials. A **context** pairs a cluster with a user and can set a default namespace. The current context is the one `kubectl` uses unless you supply a different one. The `KUBECONFIG` environment variable can direct the client to other files; a command can also provide a specific file with `--kubeconfig`.

The Workbench activates a dedicated kubeconfig by sourcing its `lab-env.sh`. A context name such as `kind-kv-lab` is a useful cue. Verify where it points if there is any doubt. A context called `test` is only a local name, so it is worth checking the endpoint before using it.

## <span id="walkthrough-inspect-without-spilling-credentials" aria-hidden="true" />Check your context and namespace

Read the current context and server address before practice commands. The JSONPath expression below prints only the address and namespace. A blank namespace means the context has no namespace set; it normally falls back to `default` for namespaced commands without `-n`. Avoid printing a kubeconfig with credentials included, especially in a shared terminal or support ticket.

```bash
kubectl config get-contexts
kubectl config current-context
# Show only the chosen endpoint and default namespace, not credential data.
kubectl config view --minify \
  -o jsonpath='{.clusters[0].cluster.server}{"\n"}{.contexts[0].context.namespace}{"\n"}'
kubectl cluster-info
kubectl get namespaces
```

In the next block, replace `YOUR_LAB_CONTEXT` with the name you verified. `--context` selects the context for one command and `-n` chooses the namespace for that operation. The last example changes the namespace preference recorded for the context in your local config. It neither creates a namespace nor sends an application change.

```bash
kubectl --context YOUR_LAB_CONTEXT -n selection-lab get pods
kubectl --context YOUR_LAB_CONTEXT -n selection-lab describe pod catalog-demo
kubectl --context YOUR_LAB_CONTEXT auth can-i get pods -n selection-lab
# A local preference change, not a server-side namespace creation:
kubectl config set-context YOUR_LAB_CONTEXT --namespace=selection-lab
```

## <span id="choose-evidence-by-question" aria-hidden="true" />Choose an inspection command

Choose the command that answers your question. `get` lists matching objects and summarizes their state. `describe` gives a human-readable description and often shows relevant recent events. `logs` reads a container's output. For a resource field such as `spec.containers`, `explain` reads schema information. `diff` previews the difference between a manifest and the current API state, and returns code 1 when it sees changes.

## <span id="practice-make-a-command-reviewable" aria-hidden="true" />Make the target explicit

If you created `catalog-demo` in the previous lesson, inspect it again with an explicit destination. If it is missing, check the namespace and permissions before creating a second copy. `auth can-i` answers whether the caller is authorized for the requested action. A permitted write can still be rejected later by validation or admission.

```bash
kubectl --context YOUR_LAB_CONTEXT -n selection-lab get pod catalog-demo -o yaml
kubectl --context YOUR_LAB_CONTEXT -n selection-lab logs catalog-demo -c web --tail=20
kubectl explain pod.spec.containers
# Preview an existing local manifest before its next write.
kubectl --context YOUR_LAB_CONTEXT -n selection-lab diff -f catalog-demo.yaml
```

## <span id="pitfalls" aria-hidden="true" />Look here when your query returns nothing

A successful command proves that the operation worked in the context you sent it to. It tells you nothing about a different cluster. Before running a write, read the context, namespace, resource type, and name aloud or from the command line. The [module lab](/labs/#m03) uses explicit scope so you can practice on a dedicated cluster.
