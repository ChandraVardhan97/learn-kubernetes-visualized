## <span id="mental-model-two-release-recipes-one-controlled-transition" aria-hidden="true" />How a rolling update replaces Pods

A catalog service has three healthy copies. You want to release a new container image while those copies keep answering requests. A **rolling update** changes the Pod template and switches traffic gradually as replacement Pods become ready. The Deployment keeps the old and new copies in separate ReplicaSets. You can watch their counts change as the rollout proceeds.

With `maxSurge: 1` and `maxUnavailable: 0`, the Deployment can ask for a fourth replica while the three old ones are still available. It waits until the first new Pod becomes available before it scales down an old copy. The spare slot can then hold the next new Pod. The rule works as long as the cluster has room to schedule the extra copy and the updated application passes its checks.

## <span id="walkthrough-state-the-update-budget" aria-hidden="true" />Choose how much capacity to keep available

Save the example as `rollout-demo.yaml`. The readiness probe asks nginx for `/`. Once a new Pod is ready, `minReadySeconds: 5` makes it stay ready for at least five seconds before the Deployment counts it as available. `progressDeadlineSeconds` gives the controller a threshold for reporting a lack of progress. If that threshold expires, inspect the conditions before choosing a recovery.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rollout-demo
spec:
  replicas: 3
  minReadySeconds: 5 # Stay ready before counting as available.
  progressDeadlineSeconds: 120 # Report a stalled rollout; not auto-rollback.
  revisionHistoryLimit: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: rollout-demo
  template:
    metadata:
      labels:
        app: rollout-demo
    spec:
      containers:
        - name: web
          image: nginx:1.27.5
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
```

Apply the original version and wait for it to complete. Record its revision from the history. Update the image and watch the two ReplicaSets. Their desired and ready counts can differ while Pods are starting. Stop the watch when you have seen the update finish or have enough evidence to investigate a stall.

```bash
kubectl apply -f rollout-demo.yaml
kubectl rollout status deployment/rollout-demo --timeout=180s
kubectl rollout history deployment/rollout-demo
# Inspect a controlled image update in your disposable lab.
kubectl set image deployment/rollout-demo web=nginx:1.28.0
kubectl get rs -l app=rollout-demo -w
```

## <span id="practice-stall-deliberately-then-restore-a-template" aria-hidden="true" />Recover a release that gets stuck

In a disposable lab, try changing the image to a tag that does not exist. The new Pod can remain in `ImagePullBackOff` while the three old Pods stay up. Check the Deployment conditions and the new Pod’s events. Pick the known-good revision you recorded and use `rollout undo` to restore its Pod template. The controller reconciles toward that template and you can wait again for rollout status. Watch the same sequence in the recovery scene.

```bash
kubectl describe deployment rollout-demo
kubectl get pods -l app=rollout-demo
kubectl rollout history deployment/rollout-demo
# Choose the actual known-good revision from your own history.
kubectl rollout undo deployment/rollout-demo --to-revision=ACTUAL_GOOD_REVISION
kubectl rollout status deployment/rollout-demo --timeout=180s
```

## <span id="pitfalls" aria-hidden="true" />Check what rollback can restore

A revision tracks changes to the Pod template. Undoing a Deployment cannot restore a separate ConfigMap, undo a database migration, or put previously deleted data back. Budget spare capacity before choosing a surge strategy. Terminating Pods can also use resources while shutting down. Check whether your readiness probe really proves a Pod can serve the requests the release is meant to handle.
