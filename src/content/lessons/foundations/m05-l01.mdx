## <span id="mental-model-a-release-recipe-above-a-replica-counter" aria-hidden="true" />How Deployments, ReplicaSets, and Pods fit together

Suppose a small shop serves its product catalog from one web Pod. The shop wants three copies so a single Pod can disappear without removing every backend. It also needs somewhere to record which image the next copy should run. A **Deployment** manages interchangeable copies of an application. Its Pod template describes each copy, and its replica count states how many copies the shop wants.

A Deployment creates a **ReplicaSet** for a version of that template. The ReplicaSet creates and removes Pods to reach its assigned count. In a stable Deployment with three replicas, one ReplicaSet normally manages three Pods. During an update the Deployment can divide the desired copies between two ReplicaSets. Each ReplicaSet keeps track of the Pods it controls, while the Deployment coordinates the release.

## <span id="walkthrough-author-the-parent-workload" aria-hidden="true" />Write a Deployment for three copies

Save the YAML as `replicas-demo.yaml`. The top-level `metadata.name` names the Deployment. Under `spec.template` is a recipe for each Pod, including the nginx container image and its port. The template label `app: replicas-demo` matches `spec.selector.matchLabels`. The API rejects a Deployment when its selector and its template labels disagree. Choose a label that identifies this workload so that separate controllers do not match the same Pods.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: replicas-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: replicas-demo
  template:
    metadata:
      labels:
        app: replicas-demo
    spec:
      containers:
        - name: web
          image: nginx:1.27.5
          ports:
            - name: http
              containerPort: 80
```

Apply the manifest in your lab namespace. The rollout command waits for the Deployment to report success, so give it time to download the image and start the copies. Look for three ready Pods. The ReplicaSet and Pod names include generated suffixes. Record two of the Pod names before experimenting.

```bash
kubectl apply -f replicas-demo.yaml
kubectl rollout status deployment/replicas-demo --timeout=120s
kubectl get deployment replicas-demo
kubectl get rs -l app=replicas-demo
kubectl get pods -l app=replicas-demo -o wide
```

## <span id="practice-scale-delete-and-observe-the-right-repair" aria-hidden="true" />Scale the Deployment and delete a Pod

Read one Pod’s owner reference. It identifies a ReplicaSet. On the ReplicaSet, look for `Controlled By` to find the Deployment. Scale the Deployment to four in the scene and see which object creates the extra Pod. Deleting a managed Pod leaves the assigned count at four, so the ReplicaSet makes a replacement. The replacement has its own name and UID.

```bash
# Replace the placeholder with one real Pod name from the listing above.
kubectl get pod ACTUAL_POD_NAME -o jsonpath='{.metadata.ownerReferences}'
# Inspect the owning ReplicaSet found in that output.
kubectl describe rs ACTUAL_REPLICASET_NAME
```

## <span id="pitfalls" aria-hidden="true" />Count ready replicas and check their placement

Three Pods in the list can include a Pod waiting for a node or one failing to pull its image. To understand what can handle requests, look at readiness and verify the Service endpoints as well. Three copies can also land on the same node unless you configure placement. They protect against some Pod failures but still share that node as a possible point of failure.

After changing the replica count interactively, update the manifest if you want that count to persist the next time somebody applies the file.

## Check your understanding

<details>

<summary>One of three Pods is stuck in ImagePullBackOff. Will its ReplicaSet create a fourth Pod to replace it?</summary>

The stuck Pod still counts as an active Pod controlled by the ReplicaSet. The kubelet retries pulling the image for that Pod. The Deployment can have three replicas and only two ready copies, so investigate the image reference or pull credentials before expecting the ready count to rise.

</details>
