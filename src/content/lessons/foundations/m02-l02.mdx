## <span id="mental-model-compare-act-observe-again" aria-hidden="true" />How a controller replaces a missing Pod

You need three copies of a small web server running. A one-time command could start three processes, but your real requirement lasts all afternoon. If someone deletes a copy at lunch, you still want three. Kubernetes lets you declare that durable target and uses controllers to keep working toward it.

**Desired state** is what you ask the system to maintain, such as `spec.replicas: 3`. **Observed state** is what Kubernetes can see or report at the moment, such as three Pod objects with only two ready. **Reconciliation** is the controller loop that reads the target and the current state, acts on the difference, and checks again. An event can prompt the next check. The check uses the state the controller can read, which may already be newer than the event.

The example is a Deployment. Its controller manages a ReplicaSet for the Pod template. The ReplicaSet maintains the count of active Pods it manages. When a managed Pod is deleted, the ReplicaSet can create another one. Each time a replacement is created, it still needs scheduling, an image, container startup, and readiness.

## <span id="walkthrough-write-an-enduring-intention" aria-hidden="true" />Declare how many Pods you need

Save the Deployment as `reconcile-demo.yaml` in a disposable lab directory. `replicas: 3` describes the quantity. The template describes each Pod. The label in the template gives the selector something to match. Apply the description and watch the resulting Pods to see these different steps happen.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reconcile-demo
spec:
  replicas: 3 # Enduring desired Pod count.
  selector:
    matchLabels:
      app: reconcile-demo
  template:
    metadata:
      labels:
        app: reconcile-demo # Must match the selector.
    spec:
      containers:
        - name: web
          image: nginx:1.27.5
```

```bash
kubectl apply -f reconcile-demo.yaml
kubectl get deployment reconcile-demo
kubectl get rs -l app=reconcile-demo
kubectl get pods -l app=reconcile-demo -w
```

The Deployment appears after the API accepts the write. During the watch, the desired count may already be three while the ready count is zero. Over time, the observed state can move toward the target. That is **convergence**. It takes work after the write returns, and the work can get stuck. Stop the watch with Ctrl+C when the Pods are ready.

## <span id="practice-repair-intention-versus-fight-it" aria-hidden="true" />Try deleting and scaling a workload

Now delete one actual Pod in the demo. List the names first and substitute one of yours. Look for a new Pod name and watch it become ready. At the start of the replacement, the total number of objects you see may include a terminating object. Inspect the status as well as the count.

```bash
kubectl get pods -l app=reconcile-demo
# Replace the example name with one actual Pod name from that listing.
kubectl delete pod ACTUAL_POD_NAME
kubectl get pods -l app=reconcile-demo -o wide
```

Deleting a Pod tests what the controller does when a member disappears. To ask for two copies permanently, change the Deployment's desired replica count. The controller now tries to maintain two. The [module lab](/labs/#m02) repeats the experiment and checks that a deleted Pod's UID disappears.

## <span id="pitfalls" aria-hidden="true" />Read replicas and readiness separately

The ReplicaSet counts active managed Pods. A Pod whose image pull is failing can still count toward that total. Creating additional Pods with the same bad image would reproduce the same issue. If a cluster keeps reporting fewer Ready Pods than desired, examine the failed stage by reading Pod conditions or events. Examples include a node that cannot fit the request, an unavailable registry, or a readiness probe that keeps failing.
