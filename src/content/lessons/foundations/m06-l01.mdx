## <span id="mental-model-stable-address-replaceable-backends" aria-hidden="true" />How a Service finds replaceable backends

A catalog frontend needs to call a catalog API. The API runs in a Pod today, and its replacement could have a different IP tomorrow. A **Service** gives clients a stable name and a way to reach the current backends. A Service of type `ClusterIP` gets a virtual IP for use inside the cluster. A client connects to that IP and the Service port. The network implementation forwards the connection to an eligible backend.

For a Service with a selector, Kubernetes looks for Pods in the same namespace whose labels match. The EndpointSlice controller records matching backend addresses, ports, and conditions in objects called **EndpointSlices**. You can think of the Service as the address clients use and the slices as the list the network implementation uses to learn where traffic can go. Toggle a backend’s readiness in the first scene and compare the selected Pods with the eligible endpoints.

## <span id="walkthrough-expose-an-existing-listener" aria-hidden="true" />Connect a Service port to the app’s listener

Save the example as `service-demo.yaml` and apply it in a disposable namespace. The Deployment starts nginx on port 80 and gives the Pod the label `app: service-demo`. The Service selects that label and accepts TCP connections on port `8080`. Its `targetPort: http` refers to the port named `http` in each selected Pod. That name resolves to 80 in this example. Setting `containerPort` documents and names a port. The process in the container still has to listen there.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: service-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: service-demo
  template:
    metadata:
      labels:
        app: service-demo
    spec:
      containers:
        - name: web
          image: nginx:1.27.5
          ports:
            - name: http
              containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: http
---
apiVersion: v1
kind: Service
metadata:
  name: service-demo
spec:
  type: ClusterIP
  selector:
    app: service-demo
  ports:
    - name: http
      protocol: TCP
      port: 8080 # Client-facing Service port.
      targetPort: http # Resolves to the Pod's named port 80.
```

```bash
kubectl apply -f service-demo.yaml
kubectl get service service-demo
kubectl get pods -l app=service-demo --show-labels
kubectl get endpointslices -l kubernetes.io/service-name=service-demo -o yaml
```

Check the Service address and compare the Pod IP with the addresses in its slices. Look for `conditions.ready` beside the backend. Send a request in the forwarding scene. Follow it from the client to the ready Pod and watch the response return. On a cluster using kube-proxy, it updates rules used to handle Service traffic. Some network implementations handle that job differently.

Open **Inspect the request** to follow one iptables example. Compare the destination before and after forwarding, then check what source address the client sees on the reply.

## <span id="practice-test-from-the-callers-network" aria-hidden="true" />Test from a Pod inside the cluster

Run the sample client in the same namespace. The short name `service-demo` resolves there, and the request goes to port 8080. The client exits after fetching the page, so the wait looks for `Succeeded`. Read its logs to see the nginx response, then remove the client Pod.

```bash
kubectl run service-client --image=busybox:1.36.1 --restart=Never \
  --command -- sh -c 'wget -qO- http://service-demo:8080/'
# This finite client can finish before a Ready condition is observed.
kubectl wait --for=jsonpath='{.status.phase}'=Succeeded pod/service-client --timeout=90s
kubectl logs service-client
kubectl delete pod service-client
```

Repeat after checking the selector and endpoint addresses in the [Service networking lab](/labs/#m06). If you change a label to break the match, observe which fields change before restoring it.

## <span id="pitfalls" aria-hidden="true" />Read endpoint conditions

An EndpointSlice entry can still show a Pod address while `ready` is false. Inspect conditions as well as the address. Options such as publishing unready addresses and routing behavior during termination affect special cases. When debugging a typical Service, first confirm matching Pods, ready backends, and agreement between the target port and the application listener.
