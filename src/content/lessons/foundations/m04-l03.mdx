## <span id="mental-model-configuration-is-a-separate-input" aria-hidden="true" />How an app gets settings and credentials

You run the same app image in a training cluster and a public service. The training app needs a different color on its page and a different API token. Rebuilding the image just to change those values would mix software releases with environment settings. Kubernetes can supply the values when the app runs.

A **ConfigMap** is an API object for non-confidential configuration, such as a mode flag or the contents of a small settings file. A **Secret** is an API object intended for sensitive data such as credentials. Pods can refer to either kind of object by name and read selected values. References generally need the object in the same namespace.

Using a Secret identifies the data as sensitive so you can put access rules and operational controls around it. The `data` format represents values using base64, a reversible encoding. Anyone authorized to read the Secret can decode it. Protect reads and workload creation permissions with RBAC, manage encryption at rest for stored data, and keep real credentials out of source files, command logs, and screenshots.

## <span id="walkthrough-project-ordinary-settings-and-a-dummy-credential" aria-hidden="true" />Mount a ConfigMap and a Secret

In this example, `MODE` is passed as an environment variable and `settings.ini` is projected as a file. A Secret key is mounted as `/run/token/token`. The training value is fake. The process checks that the token file exists and has content while keeping the value out of its logs.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: application-settings
data:
  MODE: "training"
  settings.ini: |
    color=blue
---
apiVersion: v1
kind: Secret
metadata:
  name: application-token
type: Opaque
stringData:
  token: "dummy-training-value"
---
apiVersion: v1
kind: Pod
metadata:
  name: configuration-demo
spec:
  containers:
    - name: app
      image: busybox:1.36.1
      command: ["sh", "-c", "echo mode=$MODE; test -s /run/token/token && sleep 3600"]
      env:
        - name: MODE
          valueFrom:
            configMapKeyRef:
              name: application-settings
              key: MODE
      volumeMounts:
        - name: settings
          mountPath: /etc/application
          readOnly: true
        - name: token
          mountPath: /run/token
          readOnly: true
  volumes:
    - name: settings
      configMap:
        name: application-settings
    - name: token
      secret:
        secretName: application-token
        defaultMode: 0444 # Training default; choose access for the actual app user.
```

Save the manifest as `configuration-demo.yaml` and run the following in a disposable namespace. Expect the app logs to show its mode and the file read to show `color=blue`. If the container cannot start, read its events for a missing object, missing key, or volume setup error. Changing an image will not create a missing configuration object.

```bash
kubectl apply -f configuration-demo.yaml
kubectl describe pod configuration-demo
kubectl logs configuration-demo -c app
# Inspect non-secret projected configuration only.
kubectl exec configuration-demo -c app -- cat /etc/application/settings.ini
```

## <span id="practice-predict-configuration-refresh" aria-hidden="true" />Observe what happens after a config change

Now change the ConfigMap's `MODE` and `settings.ini` while the Pod keeps running. The environment variable was set when the container started, so the current process keeps the old value. A normal mounted ConfigMap volume can see updated files after the kubelet refreshes the projection. An application may need to re-open the file or reload to use those changes. A single file mounted with `subPath` does not receive those automatic ConfigMap or Secret updates.

## <span id="pitfalls" aria-hidden="true" />Control who can read the credential

Plan how your app will adopt updates. For an environment variable, change or restart the workload's Pods in a controlled way. For a file, check whether the app rereads it and confirm the observed value after the projection updates. A Secret rotation also needs the application and upstream service to agree on when the new credential works. Practice how these inputs appear in a Pod with the [module lab](/labs/#m04).

<details>

<summary>You update a ConfigMap and the file changes, but the app keeps printing its old mode. Why?</summary>

The file and environment variable are separate delivery paths. The kubelet can update the projected file. The running program still has the environment it inherited at startup. Replace the running container through its workload if the change needs to take effect through that variable.
