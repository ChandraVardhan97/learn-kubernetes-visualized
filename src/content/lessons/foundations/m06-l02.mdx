## <span id="mental-model-a-name-is-not-an-exposure-rule" aria-hidden="true" />Which callers can resolve a Service name

The catalog frontend can reach `service-demo` from a Pod, but typing the same name on your laptop does not open the catalog. Those callers are in different networks and use different DNS settings. **Service DNS** gives clients inside the cluster a name for a Service. A typical fully qualified name is `service-demo.default.svc.cluster.local`, with the Service name, namespace, and configured cluster domain. From the same namespace, a client can usually use `service-demo` because the Pod’s resolver searches there.

A normal ClusterIP Service resolves to its cluster IP. Once your client knows the address, it still needs a viable network path, the right port, and a ready backend. Switch the caller in the scene to see how the same Service name is treated from inside and outside the cluster.

Open **Inspect the DNS lookup** to follow a short name from the client’s DNS search list to CoreDNS and then trace the connection to a backend. The final step shows which part breaks when the Service selector stops matching.

## <span id="walkthrough-inspect-the-callers-resolver" aria-hidden="true" />Check DNS from a client Pod

Use the `service-demo` Service and Deployment from the previous lesson. The client created here stays running long enough to execute several commands. Inside it, `/etc/resolv.conf` shows the search suffixes and the resolver address. Compare the result of `nslookup` with `wget`. A DNS answer tells you the name resolved. A successful HTTP response proves that the connection also reached a backend that could answer.

```bash
kubectl run discovery-client --image=busybox:1.36.1 --restart=Never \
  --command -- sleep 3600
kubectl wait --for=condition=Ready pod/discovery-client --timeout=90s
kubectl exec discovery-client -- cat /etc/resolv.conf
kubectl exec discovery-client -- nslookup service-demo
kubectl exec discovery-client -- wget -qO- http://service-demo:8080/
```

## <span id="choose-the-external-entry-point" aria-hidden="true" />Choose an entry point for external callers

A **NodePort** Service opens a chosen port across eligible node addresses in addition to providing an internal ClusterIP. A caller with network access to a node can connect to that node’s IP and the allocated port. A **LoadBalancer** Service requests a front door from a supporting cloud provider or cluster add-on. On a basic kind cluster, that external address can stay pending because no implementation is providing it.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: node-entry-demo
spec:
  type: NodePort
  selector:
    app: service-demo # Existing web Pods from the prior lesson.
  ports:
    - name: http
      port: 8080
      targetPort: http
      # Omit nodePort: the API allocates from its configured range.
```

<Scene id="m06-l02-exposure" />

Save the file as `node-entry-demo.yaml`. Look for the allocated NodePort and the node IPs. In kind, the nodes are containers. Whether your laptop can reach a node address or NodePort depends on its network and any configured host port mappings. For a local debug connection, `kubectl port-forward` listens on your laptop and forwards through the Kubernetes API path to a selected Pod. Leave the command running and try `http://localhost:8080` in another terminal or browser tab.

```bash
kubectl apply -f node-entry-demo.yaml
kubectl get service node-entry-demo
kubectl get nodes -o wide
# A debugging tunnel to a selected backend, without external provisioning:
kubectl port-forward service/service-demo 8080:8080
```

## <span id="practice-and-pitfalls" aria-hidden="true" />Test the actual path your client uses

Compare a request from inside the cluster and a request from your machine in the [local Service networking lab](/labs/#m06). If a port-forward works while in-cluster requests fail, keep debugging the Service and client path. Stop the forward when finished, and clean up `discovery-client` after completing the next lesson or its practice.
