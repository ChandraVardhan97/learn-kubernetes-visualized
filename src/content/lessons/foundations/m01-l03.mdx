## <span id="mental-model-name-address-connection-message" aria-hidden="true" />Where a web request goes

You open a web browser and type `http://127.0.0.1:8080/`. What has to happen before you see a page? First, the operating system needs somewhere to send the packets. The address `127.0.0.1` is IPv4 **loopback**, an address for reaching the same machine from the current network view. A network **interface** is a connection point that can have addresses assigned to it. Loopback is one interface. Wi-Fi and virtual container interfaces are other examples.

A **port** is a number used by a transport protocol, such as TCP, to direct traffic to an application endpoint at an address. When nginx listens on TCP port 80 inside a container, a client needs a network path to that endpoint. In the example, Docker publishes a second endpoint on your machine's loopback at port 8080, then forwards connections there to the container's port 80.

After the connection opens, the client sends an **HTTP request** with a method and a path, such as `GET /`. The server sends back an **HTTP response** with a status, headers, and often a body. A 404 response is useful evidence. Something accepted the connection, understood HTTP, and said the requested path was missing.

## <span id="walkthrough-publish-a-local-training-port" aria-hidden="true" />Connect to a container from your machine

Follow both numbers in the publish option from left to right. `8080` is where the browser connects on your machine. `80` is where nginx listens in its own network view. Binding the host side to loopback keeps this practice endpoint local. Execute the commands in order and compare the response headers for the two paths.

```bash
# Bind only the laptop's IPv4 loopback address for this local exercise.
# Host TCP 8080 forwards to the container's TCP 80.
docker run --rm -d --name network-demo \
  -p 127.0.0.1:8080:80 nginx:1.27.5
# Show HTTP response headers plus the response body.
curl -i http://127.0.0.1:8080/
# Ask for a path nginx does not serve.
curl -i http://127.0.0.1:8080/does-not-exist
# Release the published host port.
docker stop network-demo
```

Expect the first request to return a page. The second normally returns a 404 from nginx. After you stop the container, trying the first command again should fail to connect if no other program is listening there. Those outcomes tell you whether you reached the server, found the requested resource, or failed before sending HTTP.

## <span id="dns-happens-before-the-request" aria-hidden="true" />What DNS does before the request

A URL with a hostname adds a step. The **Domain Name System** (DNS) lets the client look up records for a name. For a web connection, the client typically uses one of the returned IPv4 or IPv6 addresses. Several addresses can be valid. A successful lookup demonstrates name resolution. The client still has to connect to an address and receive an answer from the intended application.

<Scene id="m01-l03-dns" />

```bash
# This requires nslookup on your machine; any legitimate DNS answer may change.
nslookup kubernetes.io
# Verbose output separates connection setup from the HTTP response.
curl -v https://kubernetes.io/ -o /dev/null
```

Read the verbose `curl` output from the beginning. Look for a resolved address, the connection attempt, TLS negotiation for HTTPS, then the HTTP status. In later Kubernetes examples, the same sequence helps you trace requests to a Service from inside a Pod.

## <span id="practice-predict-the-first-broken-boundary" aria-hidden="true" />Find where a request failed

When a request breaks, form a prediction before changing anything. With a misspelled hostname, start at DNS. With the right address and the wrong port, look for a refused connection or timeout. With a real HTTP error, inspect the server, route, or application. Try the first version of this exercise with the [module lab](/labs/#m01).

## <span id="pitfalls" aria-hidden="true" />Check the address from the caller

The meaning of `localhost` follows where the client process runs. From a container it usually refers to that container's network namespace. Connect from the same location as the failing client when testing a path.
