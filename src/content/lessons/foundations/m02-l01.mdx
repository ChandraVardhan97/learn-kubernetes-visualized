## <span id="mental-model-coordination-and-execution" aria-hidden="true" />Who does what in a Kubernetes cluster

Suppose you have three machines and want to run a web server. You could log into one and launch it by hand. With Kubernetes, you submit a description of what should run. Kubernetes needs a place to accept that request, somewhere to save it, a decision about which machine will run it, and a way to do the work on that machine.

A **cluster** is the group of machines and Kubernetes components working together. A **node** is a machine registered with the cluster, physical or virtual. The **control plane** manages cluster-level decisions. Its **API server** is the front door. `kubectl` sends requests there. The server checks the request and uses **etcd**, a distributed key-value store, to store the cluster's API state. Your terminal and the application containers do not have to connect directly to etcd.

A **controller** watches for relevant state and takes action to bring the cluster toward the target. A Deployment controller manages ReplicaSets, and a ReplicaSet controller makes Pods to maintain the requested count. The **scheduler** watches for Pods that still need a node, checks candidate machines against their requirements, and records a placement. Each component solves a part of the problem using the API.

## <span id="walkthrough-distribute-the-responsibilities" aria-hidden="true" />Find the components in your lab cluster

Once the Pod is assigned, the **kubelet** on that node handles the local steps. A kubelet is the agent that keeps the containers for assigned Pods running according to their specs and reports their status. It talks to a **container runtime**, such as containerd, through the **Container Runtime Interface** (CRI). The interface is the agreed way to request work like setting up a Pod sandbox or starting a container.

Try the read-only commands on a practice cluster. `get nodes` tells you which nodes are registered and reporting health. `get pods -n kube-system` shows system Pods the cluster exposes there. Some managed services run control-plane components outside the namespaces you can see. The API inventory answers which kinds of API resources your server currently offers.

```bash
# Read-only inventory; component visibility varies by distribution.
kubectl get nodes -o wide
kubectl get pods -n kube-system
kubectl cluster-info
# Ask the API which resources it serves rather than guessing.
kubectl api-resources
```

The short Pod definition below requests one nginx container. If you submit it in a practice namespace, the API stores the Pod spec, the scheduler assigns the node, and the node's kubelet and runtime start the container. This example creates a Pod directly. With a Deployment, the controllers create the Pod object first and the same node-startup steps follow.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: component-demo
spec:
  containers:
    - name: web
      image: nginx:1.27.5
```

## <span id="practice-explain-partial-failure" aria-hidden="true" />Predict what still works if a component fails

Use the component boundaries to reason about failures. If your client cannot connect to the API server, existing containers can keep running for a time, depending on what they need from the API. New writes and scheduling decisions can stall. If the API accepts the Pod but its image cannot be pulled, start at the node and registry boundary. Find the Pod's assigned node and read the event to learn what the kubelet was attempting. In the [module lab](/labs/#m02), you can see a controller respond when one of its Pods disappears.

## <span id="pitfalls" aria-hidden="true" />Check where your provider runs the control plane

Control-plane availability and application health answer different questions. A healthy API can report an unhealthy workload. A running container can keep answering requests during a control-plane interruption. Check the actual evidence at each boundary before restarting anything.
