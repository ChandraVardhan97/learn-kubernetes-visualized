## Mental model: locate the first failed boundary

“A request failed” is a symptom, not a diagnosis. Start by identifying the caller, exact destination and port, response or error, time window, namespace, and recent change. Then separate the API object path from the application packet path. A successful `kubectl get` proves access to the API, not that the web server works. A successful Pod port-forward tests a selected backend through a debugging tunnel, not necessarily the Service's ordinary forwarding path.

Use the narrowest useful evidence first. Confirm the context and namespace so you do not investigate a different workload with the same name. Inspect the owning Deployment, its ReplicaSets, and current Pods. Check whether Pods exist, have node assignments, started containers, and became ready. Each transition has a responsible component and different failure evidence. Avoid deleting the failing Pod before reading its status and logs; replacement can discard the very observation needed to explain the incident.

## Walkthrough: inspect startup before transport

Use `service-demo` from the preceding lessons in its dedicated lab namespace. Replace `ACTUAL_POD_NAME` with a current Pod name from the first listing. Keep your verified context and namespace explicit when multiple clusters are configured.

```bash
kubectl get deployment service-demo
kubectl get pods -l app=service-demo -o wide
kubectl describe pod ACTUAL_POD_NAME
kubectl logs ACTUAL_POD_NAME -c web --tail=100 --timestamps
# Useful only if that container has a previous terminated instance:
kubectl logs ACTUAL_POD_NAME -c web --previous --tail=100
kubectl get events --sort-by=.metadata.creationTimestamp
```

Events describe observations by components, such as failed scheduling, image pulling, mount preparation, or probe failures. They are not an indefinite audit log and may be aggregated or expire. Container logs are the application's stdout/stderr made available through the runtime and node log path. They are not every file in the container, and they are not durable centralized storage by themselves. A failed image pull has no running application process to emit its startup logs.

An unassigned Pending Pod points toward scheduling evidence. A bound Pod waiting for an image points toward reference, credentials, and registry access. A restarting container points toward termination reason, exit code, logs, probe results, or memory pressure. `CrashLoopBackOff` describes delayed retries after repeated failures; it does not identify the underlying application defect. Read the immediate cause before choosing a repair.

## Follow a broken request one hop at a time

Once a backend runs, inspect the Service selector, ports, and EndpointSlices. Compare endpoint addresses with actual Pod IPs, readiness conditions with probe evidence, and target ports with the actual listener. Test from the same caller network when possible. A probe from your laptop may use a different DNS resolver, network route, firewall policy, or credential path from the failing Pod.

```bash
kubectl get service service-demo -o yaml
kubectl get pods -l app=service-demo --show-labels
kubectl get endpointslices -l kubernetes.io/service-name=service-demo -o yaml
# Use the existing debug client from the prior lesson.
kubectl exec discovery-client -- nslookup service-demo
kubectl exec discovery-client -- wget -qO- http://service-demo:8080/
```

If name lookup fails, inspect the caller's resolver configuration and cluster DNS path. If lookup succeeds, retain that evidence and test address/port reachability. If a direct Pod-IP request works from the same client but the Service request fails, focus on frontend port mapping, endpoint records, and Service forwarding. If both fail, the listener, network reachability, policy, or application becomes more likely. No single test proves every possible path healthy.

## Practice: repair one deliberate mismatch

This valid Service object intentionally selects nothing in the previous workload. Save it as `debug-mismatch.yaml` and apply it only in the disposable lab namespace:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: debug-mismatch
spec:
  selector:
    app: deliberately-unmatched # The intended Pods use app: service-demo.
  ports:
    - port: 8080
      targetPort: http
```

Predict that the Service can receive a ClusterIP and DNS record while lacking usable endpoints. Verify each prediction, change only the selector to `app: service-demo`, apply, and repeat the original client request to `http://debug-mismatch:8080/`. The repair should change the backend evidence and the request result. Merely seeing “configured” after apply is not the success condition.

## Pitfalls

A minimal image may have no shell, nslookup, or curl. Missing debug tools do not establish an application failure. Use an approved client Pod or later an ephemeral-debug-container workflow rather than modifying the production image during an incident. Redact credentials and user data from logs before sharing them. Also avoid assuming every HTTP 500 comes from the Pod you intended; proxies and upstream dependencies can produce their own responses.

<summary>The Pod answers over port-forward, but the Service request fails from a client Pod. Is the Service proven healthy?</summary>

No. Port-forward reaches a selected Pod through a different path. Inspect Service selection, endpoint readiness, client-facing and target ports, DNS, and node forwarding from the failing caller. Preserve the successful backend test as a useful narrowing result, then verify the repaired original path and several representative requests.
