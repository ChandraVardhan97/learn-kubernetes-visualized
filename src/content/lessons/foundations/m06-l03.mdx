## <span id="mental-model-locate-the-first-failed-boundary" aria-hidden="true" />Find the first part that failed

Your frontend reports that the catalog is unavailable. At first, that symptom could mean the catalog did not start, DNS could not resolve its name, or the Service has no backend. Start by finding the first failed part of the path. Write down the caller, namespace, host, and port so you can repeat the exact request after a repair.

**Conditions** describe whether particular states hold for an object, such as whether a Pod is ready. **Events** report recent activity around an object, such as a failed image pull or scheduling attempt. **Container logs** show messages written by the running application to standard output and error. Each answers a different question. Try the startup scene and decide which evidence to check before changing the workload.

## <span id="walkthrough-inspect-startup-before-transport" aria-hidden="true" />Investigate startup before network traffic

Use the `service-demo` Deployment from the previous lessons. First ask if it has any ready Pods. Use a real Pod name from the list in the remaining commands. A pending Pod can have a `FailedScheduling` event explaining why no node is a fit. A running container that restarts can have a useful error in the previous instance’s logs. If the image never started, look at Events because there is no application output from that attempt.

```bash
kubectl get deployment service-demo
kubectl get pods -l app=service-demo -o wide
kubectl describe pod ACTUAL_POD_NAME
kubectl logs ACTUAL_POD_NAME -c web --tail=100 --timestamps
# Useful only if that container has a previous terminated instance:
kubectl logs ACTUAL_POD_NAME -c web --previous --tail=100
kubectl get events --sort-by=.metadata.creationTimestamp
```

## <span id="follow-a-broken-request-one-hop-at-a-time" aria-hidden="true" />Follow the client request

Once a backend is running, follow the request from `discovery-client`. Verify the client can resolve the Service. Inspect its selector and the actual Pod labels side by side. Read the EndpointSlice addresses and readiness conditions, then check that the target port reaches the application’s listener. Finally make the original request from the client. The result tells you whether the path works as a whole.

```bash
kubectl get service service-demo -o yaml
kubectl get pods -l app=service-demo --show-labels
kubectl get endpointslices -l kubernetes.io/service-name=service-demo -o yaml
# Use the existing debug client from the prior lesson.
kubectl exec discovery-client -- nslookup service-demo
kubectl exec discovery-client -- wget -qO- http://service-demo:8080/
```

## <span id="practice-repair-one-deliberate-mismatch" aria-hidden="true" />Repair the Service selector

Save the manifest as `debug-mismatch.yaml` and apply it alongside the working `service-demo` workload. There are two Services now. Make the same request to `debug-mismatch:8080` from the debug client and see where the evidence differs. That Service has a DNS entry, but its selector matches none of the intended Pods. Change its selector to `app: service-demo`, reapply, and check the slices before rerunning the request.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: debug-mismatch
spec:
  selector:
    app: deliberately-unmatched # The intended Pods use app: service-demo.
  ports:
    - port: 8080
      targetPort: http
```

Use the [Service troubleshooting lab](/labs/#m06) to repeat the exercise with its own test names and cleanup steps. Write down the symptom, the observation that explained it, and the result after the fix. That record helps when a later fault produces the same symptom for a different reason.

## <span id="pitfalls" aria-hidden="true" />Collect evidence from the failing caller

Events can expire and repeated failures can be grouped. Capture recent evidence while the failure is happening. A test from a different namespace or container might have different DNS search paths, policy, or networking. Try from the original caller whenever possible. After the exercise delete the deliberately broken Service and the temporary client when they are no longer needed.

## Check your understanding

<details>

<summary>The catalog Pods are ready. The short Service name resolves, but the request times out. What would you check before restarting the Pods?</summary>

Compare the Service selector with the Pod labels, inspect EndpointSlice readiness and ports, and verify the application’s listener. These checks can expose a bad Service mapping while the Pods themselves remain healthy. If the mapping is correct, continue through the caller’s policy and network path.
