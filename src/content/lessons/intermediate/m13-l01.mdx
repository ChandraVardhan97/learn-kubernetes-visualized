## <span id="mental-model-kubernetes-reconciles-rendered-objects-not-your-packaging-intent" aria-hidden="true" />Make environment changes without copying manifests

You run the same API in a training namespace and in production. The two environments share a Deployment and Service, but production needs more replicas and a different approved image. Copying both YAML files starts out easy. Over time, a change may make it into only one copy. **Kustomize** lets you keep shared manifests in a base and apply a set of deliberate differences in each environment’s **overlay**.

Kustomize reads resources and applies transformations such as a namespace change, image substitution, or patch. It produces ordinary Kubernetes manifests. Kubernetes receives those objects after rendering. In the first scene, trace which fields come from the base and which change when you pick the training overlay.

## <span id="walkthrough-express-a-small-environment-change-visibly" aria-hidden="true" />Render and review a Kustomize overlay

This example expects an `api` Deployment in `base` and a training overlay under `overlays/training`. The image transformation changes the `nginx` tag. The patch replaces the existing `spec.replicas` field on the `api` Deployment with three. Render the final result first and inspect the changes. Server-side dry run checks what the API would accept for the current identity and policy. `kubectl diff` compares the proposed configuration with live resources and exits with code 1 when it finds changes.

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
namespace: learning
images:
  - name: nginx
    newTag: 1.27-alpine       # Training tag; pin an approved digest for releases.
patches:
  - target:
      kind: Deployment
      name: api
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 3
```

```bash
kubectl kustomize overlays/training > rendered.yaml
kubectl apply --dry-run=server -f rendered.yaml
kubectl diff -k overlays/training
kubectl apply -k overlays/training
kubectl rollout status deployment/api -n learning --timeout=120s
```

## <span id="practice-make-a-charts-configuration-contract-explicit" aria-hidden="true" />Install a Helm chart and inspect the release

**Helm** packages templates and default values into a **chart**. Environment-specific values fill in parts of the templates, such as the replica count or image. An installed chart instance is a **release**. Helm records release revisions, which you can inspect after an install or upgrade. Try changing a value in the second scene and compare the rendered object with the chart input.

<Scene id="m13-l01-chart-release" />

The optional example needs your own local chart and `values-training.yaml`. `helm lint` checks the chart, `helm template` renders it for inspection, and `helm upgrade --install` creates or updates the release. Look at the rendered manifests as carefully as you would look at handwritten YAML. Examine the effective values and recorded manifest to confirm the release used the configuration you intended.

```bash
# Optional extension: supply a local chart and values file first.
# They are not included in the downloadable Kustomize baseline.
helm lint ./chart
helm template api ./chart -n learning -f values-training.yaml > helm-rendered.yaml
helm upgrade --install api ./chart -n learning \
  -f values-training.yaml --wait --timeout 5m
helm history api -n learning
helm get values api -n learning --all
helm get manifest api -n learning
```

## <span id="pitfalls-multiple-writers-make-reproducibility-fragile" aria-hidden="true" />Track the inputs that produced the release

The [application delivery lab](/labs/#m13) includes a runnable Kustomize baseline. Use a different environment or workload name for Helm practice so the tools do not both manage the same fields on the same objects. Pin the chart and image versions for real releases, and record the base and values used to produce them. A release name by itself cannot tell a teammate what was deployed.
