## <span id="mental-model-distribute-replicas-then-budget-their-promises" aria-hidden="true" />How Kubernetes spreads replicas across zones

Imagine a six-Pod API spread over three zones. If the zones have three, two, and one copy, some callers lose more capacity if the busiest zone fails. A **topology spread constraint** asks the scheduler to balance selected Pods across groups of nodes called topology domains. A node label might identify a zone, or the hostname label could make each node a separate domain. The selector tells the scheduler which Pods belong in the count.

In a simplified three-zone example with counts of two, two, and one, another Pod could bring them to two, two, and two. If the incoming Pod were placed in a zone already at two, its new count of three would differ from the minimum of one by two. A rule with `maxSkew: 1` and `DoNotSchedule` would reject that placement in this example. Look for eligible domains in the scene before doing the arithmetic. Kubernetes accounts for options such as `minDomains` and which domains qualify under the rule.

## <span id="walkthrough-a-spread-rule-belongs-to-the-pod-template" aria-hidden="true" />Add a spread rule to a Deployment

Place the first fragment inside an existing Deployment’s `spec.template.spec`. Its own Pod template should carry `app: api` so that each new copy counts toward the distribution. Check the labels on the actual nodes first. The rule in the example uses zone labels, which may be missing in a small local cluster. For a local exercise, a comparable rule can reason about hostnames instead.

```yaml
# Fragment: spec.template.spec of a Deployment labeled app=api
 topologySpreadConstraints:
   - maxSkew: 1
     topologyKey: topology.kubernetes.io/zone
     whenUnsatisfiable: DoNotSchedule
     labelSelector:
       matchLabels:
         app: api
 containers:
   - name: api
     image: nginx:1.27-alpine
     resources:
       requests: {cpu: 100m, memory: 64Mi}
       limits: {cpu: 500m, memory: 128Mi}
```

## <span id="practice-calculate-a-rollout-before-admitting-it" aria-hidden="true" />Budget for a rollout

A **ResourceQuota** limits aggregate quantities in a namespace. The example allows requests of one CPU and 1 GiB of memory, and up to ten counted Pods. A **LimitRange** can supply defaults and enforce per-object bounds. In this example it adds a request of `100m` and `64Mi` to a container that does not specify them. Apply quota and defaults in a disposable namespace so other workloads do not consume your budget.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-budget
spec:
  hard:
    requests.cpu: "1"
    requests.memory: 1Gi
    pods: "10"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: container-defaults
spec:
  limits:
    - type: Container
      defaultRequest: {cpu: 100m, memory: 64Mi}
      default: {cpu: 500m, memory: 256Mi}
```

Ten copies at `100m` use the full CPU budget. A Deployment trying to add an eleventh copy during a surge can be blocked by admission, even with room left on a node. Check ResourceQuota usage and ReplicaSet events to distinguish a rejected create from a Pod that exists but could not schedule. Try both constraints in the budget scene and the [scheduling and quota lab](/labs/#m07).

## <span id="pitfalls-governance-is-not-physical-isolation" aria-hidden="true" />Check quota and node capacity

Quotas govern the resources admitted in a namespace. Requests still need to fit physical nodes, and spread or affinity rules can further restrict the eligible nodes. Plan capacity for old and new replicas to overlap when a rollout needs a surge. Adjust tight budgets deliberately rather than relying on an idle usage chart.
