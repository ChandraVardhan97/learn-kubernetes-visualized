## <span id="mental-model-the-status-column-is-a-clue-not-a-root-cause" aria-hidden="true" />What each Pod failure status tells you

A deployment dashboard shows an unavailable API. One Pod says `Pending`, another says `ImagePullBackOff`, and a third says `CrashLoopBackOff`. Those words tell you where to begin. `Pending` is a Pod phase and can cover several stages before containers are ready. If the Pod has no node, Events can explain which requests or constraints prevented scheduling. If it has a node, look at container state and volume events to see what setup is waiting for.

`ImagePullBackOff` means a pull failed and the kubelet is delaying further attempts. Look for an earlier event with the image name and the actual error, such as a missing tag or denied access. `CrashLoopBackOff` means a container keeps terminating and Kubernetes is spacing out restarts. Previous logs, the last exit state, and probe events can show whether it crashed, was killed for memory, or was restarted after failed health checks. Try each category in the failure scene.

## <span id="walkthrough-capture-the-evidence-before-changing-the-workload" aria-hidden="true" />Collect startup evidence before changing the workload

Use your actual namespace and Pod name in the commands, and replace `app` with the container you want to inspect. Start with owner objects and Pod placement. In the Pod YAML, check `status.containerStatuses`, including the current and last state, restart count, and readiness. `--previous` asks for logs from the preceding terminated instance of that container. If it never started, there may be no logs to retrieve. Record the exact error before changing fields or deleting the Pod.

```bash
kubectl get deployment,replicaset,pod -n learning -o wide
kubectl describe pod FAILING_POD -n learning
kubectl get events -n learning --sort-by=.metadata.creationTimestamp
kubectl logs FAILING_POD -n learning -c app --tail=100
kubectl logs FAILING_POD -n learning -c app --previous --tail=100
kubectl get pod FAILING_POD -n learning -o yaml
```

## <span id="practice-inspect-a-minimal-image-without-changing-its-production-contents" aria-hidden="true" />Debug a container that lacks a shell

When a running Pod uses a minimal image, `kubectl exec` can fail because there is no shell or diagnostic tool inside it. An **ephemeral debug container** is an extra container you can add for troubleshooting. It can use the Pod network and, with a supporting runtime, target another container’s process namespace. It has its own image and filesystem. Adding it requires the relevant permissions and must pass admission.

```bash
# Use a throwaway Pod and an approved debug image in the local lab.
kubectl debug -it FAILING_POD -n learning \
  --image=busybox:1.36 --target=app
# From the debug shell, inspect connectivity without printing credentials.
# An exit returns to your local shell; it does not delete the application Pod.
```

<Scene id="m12-l01-debug-container" />

Use an approved image in a disposable Pod. Test a hostname and port from within that Pod’s network, then exit. The application Pod continues on its own and the ephemeral container is part of that Pod’s record for the rest of its lifetime. Try the [workload debugging lab](/labs/#m12) to repair an intentional failure and confirm recovery.

## <span id="pitfalls-repeated-restarts-can-hide-the-first-useful-error" aria-hidden="true" />Capture evidence while it is available

Events can expire and `--previous` is limited to the previous instance, so save useful evidence before restarting anything. Many workloads restart continuously after a configuration error. Resolve the first concrete error and rerun the same health check before making more changes.
