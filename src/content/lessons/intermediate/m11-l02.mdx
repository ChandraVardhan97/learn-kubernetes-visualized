## <span id="mental-model-authorization-to-create-a-pod-is-only-the-first-boundary" aria-hidden="true" />Choose what the application process can do

A report worker needs to write a status file to `/work`. It has no reason to alter system files or gain root privileges. A **security context** lets you set the Linux identity and privileges under which a Pod or container runs. The Pod can set defaults such as a user and group ID. Container-level settings govern details such as Linux capabilities and privilege escalation.

The example runs as user and group 1000. It drops all Linux capabilities, which are individual privileges processes can otherwise hold. `allowPrivilegeEscalation: false` prevents the process from gaining more privileges through operations such as running a set-user-ID program. The runtime default `seccompProfile` limits available system calls. Toggle the settings in the scene and watch which parts of the process boundary they change.

## <span id="walkthrough-supply-the-writable-paths-the-application-actually-needs" aria-hidden="true" />Give the process a writable working directory

Save the manifest as `restricted-writer.yaml`. Its root filesystem is read-only, but the container mounts an `emptyDir` volume at `/work`. A writable mount on the right directory lets the process create its status file. `fsGroup: 1000` provides group-related access on supported volumes. It is worth testing the exact process UID and path because a mount that exists can still be inaccessible to the app.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: restricted-writer
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: writer
      image: busybox:1.36
      command: ["sh", "-c", "id; echo ready > /work/status; sleep 3600"]
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: [ALL]
      volumeMounts:
        - name: work
          mountPath: /work
  volumes:
    - name: work
      emptyDir: {}
```

## <span id="practice-reject-an-unsafe-proposal-before-it-reaches-a-node" aria-hidden="true" />Test the namespace’s Pod security policy

**Pod Security Standards** define three levels of constraints called Privileged, Baseline, and Restricted. **Pod Security Admission** enforces, warns, or audits against a chosen level in a namespace. Label a disposable namespace to enforce Restricted at version `v1.37`. Apply the passing example, then read its status file and verify the process identity. To observe an admission denial, try a disposable copy with an unsafe field such as `privileged: true` using server-side dry run. Read the rejection to see which requirement it violated.

```bash
# Use a new disposable namespace with no production workloads.
kubectl create namespace security-practice
kubectl label namespace security-practice \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.37
kubectl apply -n security-practice -f restricted-writer.yaml
kubectl exec -n security-practice restricted-writer -- cat /work/status
kubectl exec -n security-practice restricted-writer -- id
```

## <span id="pitfalls-admission-and-runtime-protection-are-complementary" aria-hidden="true" />Separate admission errors from runtime errors

Passing admission means that the manifest met the selected checks. The application can still fail after it starts if a required cache or temporary directory is read-only. Conversely, a runtime failure writing a file gives you no evidence that Pod Security Admission rejected the Pod. Verify the Pod exists, then check its runtime identity, mounts, and permissions. A namespace’s security labels do not evict previously admitted Pods.
