## <span id="mental-model-stable-logical-identities-over-disposable-processes" aria-hidden="true" />Which parts of a replica’s identity stay stable

Imagine an application with three ledger members. Each writes to its own disk and needs to find two specific peers. If the second member restarts, it needs its previous data and the other members need a familiar address to reconnect. A **StatefulSet** manages Pods with stable ordinal identities. An **ordinal** is the numbered slot in the set. Here the slots are `ledger-0`, `ledger-1`, and `ledger-2`. They share a Pod template, but each slot can represent a distinct application member.

When Kubernetes replaces `ledger-1`, the new Pod gets the same name and can use the same claim. It receives a new UID, runs a new process, and can receive a new IP address. In the identity scene, follow the name through the replacement and spot which state changes. Software using that name still needs to reconnect and recover its own state.

## <span id="walkthrough-identity-and-data-travel-together" aria-hidden="true" />Give each member a name and a claim

A **headless Service** has `clusterIP: None`. With a selector matching the StatefulSet’s Pods, it can publish addresses for the members instead of giving callers one virtual IP. In the same namespace, a client can use a per-Pod name such as `ledger-1.ledger`. A fully qualified example is `ledger-1.ledger.default.svc.cluster.local`, assuming the default namespace and cluster domain. By default, readiness affects which addresses are published. A workload that needs to discover peers during startup can use `publishNotReadyAddresses` deliberately. Clients then need to handle peers that answer DNS but are still initializing. A cached failed lookup can also delay discovery shortly after creation.

The manifest refers to the headless Service through `serviceName: ledger`. Create a matching Service and use a working default StorageClass before trying the three-member example. The claim template named `data` creates one PVC per ordinal, including `data-ledger-1`. The writer mounts that claim at `/data` and records its hostname each time it starts.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: ledger
spec:
  serviceName: ledger        # Matching headless Service must exist.
  replicas: 3
  selector:
    matchLabels: {app: ledger}
  template:
    metadata:
      labels: {app: ledger}
    spec:
      containers:
        - name: writer
          image: busybox:1.36
          command: ["sh", "-c", "hostname >> /data/starts; sleep 3600"]
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 1Gi
```

## <span id="practice-replace-one-member-and-inspect-continuity" aria-hidden="true" />Replace one ledger member and verify its disk

Use the example’s commands after the three Pods are ready. Write down the Pod UID, IP, and claim name for `ledger-1`, then delete the Pod only. Stop the watch after the replacement is ready. The PVC stays bound across this replacement with default retention, and the file should contain the earlier start plus the new one. The [StatefulSet lab](/labs/#m10) demonstrates stable identity with a smaller workload. Use the storage lab for a separate claim persistence exercise.

```bash
kubectl get statefulset ledger
kubectl get pods -l app=ledger -o wide
kubectl get pvc
kubectl exec ledger-1 -- cat /data/starts
kubectl delete pod ledger-1
kubectl get pod ledger-1 -w
kubectl exec ledger-1 -- cat /data/starts
```

## <span id="pitfalls-controller-ordering-is-not-a-database-protocol" aria-hidden="true" />Understand rollout order and application recovery

With the default `OrderedReady` management policy, the controller creates from lowest ordinal upward and scales down in reverse order. The default rolling update works from highest ordinal downward and waits for each updated Pod to become ready before proceeding. In this example, a broken update can stall at `ledger-2`. Check its Pod and events first. If reverting the template leaves a failed update stuck, the supported recovery can require deleting the affected Pod after the revert so it is recreated.

The application remains responsible for copying records to peers, deciding which member accepts writes, and recovering from data loss. The sample writer simply appends a line to its own volume.
