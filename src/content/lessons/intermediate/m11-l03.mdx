## <span id="mental-model-a-secret-is-sensitive-api-data-not-an-automatic-vault" aria-hidden="true" />Where a credential travels

A frontend needs a database password. Putting it directly in a Deployment would copy the value into every manifest and every place the manifest is reviewed. A Kubernetes **Secret** gives the credential its own API object. The workload can refer to the object by name. In a typical manifest, values in `data` use Base64 so binary values can be represented as text. Anyone who can read that field can decode it. Encryption at rest is configured separately at the API server or through the managed cluster service.

Follow the password in the scene. An authorized client or deployment process writes the Secret. Kubernetes stores it as API data. A Pod specification requests it as a volume, and the kubelet writes the selected content into a mount. Every boundary has its own access checks, and every process with access to the mounted file can read it.

## <span id="walkthrough-minimize-every-place-credentials-can-appear" aria-hidden="true" />Mount a Secret and plan its rotation

The snippet goes inside a Pod spec. In the same namespace, create `application-login` with a dummy `password` key. The mount exposes that key as `/credentials/password` and is read-only inside the container. Check that the file’s mode and ownership allow the actual process identity to read it. `automountServiceAccountToken: false` avoids automatically mounting an API token in a workload that uses no API calls.

```yaml
# Fragment: spec of a workload that does not need Kubernetes API access.
automountServiceAccountToken: false
containers:
  - name: application
    image: busybox:1.36
    command: ["sh", "-c", "test -r /credentials/password; sleep 3600"]
    volumeMounts:
      - name: credential
        mountPath: /credentials
        readOnly: true
volumes:
  - name: credential
    secret:
      secretName: application-login
      defaultMode: 0400   # Ensure the configured process UID can read it.
```

If a Secret volume is mounted normally, kubelet updates its files eventually when the Secret changes. The application still needs to reload or reread them. Secret environment variables are set at container startup and changing the source does not change a running process’s environment. A mount using `subPath` does not receive automatic Secret volume updates.

## <span id="practice-verify-access-presence-and-reload-without-revealing-data" aria-hidden="true" />Verify access without revealing the password

In a lab namespace, check whether your identity is allowed to read Secrets. Check file readability with the example command so its actual value never appears in console output. If you exercise rotation, use a dummy credential and verify that the app behaves correctly with the new one. A readable file proves the mount worked. A successful login with the new credential proves the app picked it up.

```bash
kubectl get secret application-login
kubectl describe secret application-login
# Describe lists keys and sizes, not decoded credential contents.
kubectl auth can-i get secrets -n learning
kubectl exec application -- sh -c 'test -r /credentials/password && echo readable'
kubectl get pod application -o yaml
```

Practice with dummy data in the [security lab](/labs/#m11). Try the tenant scene to see which layer controls each path.

## <span id="pitfalls-shared-cluster-trust-is-a-design-decision" aria-hidden="true" />Protect the rest of the tenant boundary

A namespace scopes many resources. Its boundary also depends on who may create workloads, which API permissions they hold, and which connections and runtime settings are allowed. A user who can create arbitrary Pods in a namespace can potentially mount Secrets there. Use scoped RBAC, admission rules, and enforced network policies together. For tenants requiring a stronger trust boundary, dedicated nodes or clusters may be appropriate.

<summary>You rotated a Secret mounted as a file, but the app still tries the old database password. What would you verify?</summary>

Verify whether the file was refreshed and how the app reloads it. An ordinary volume may update after a delay, while a `subPath` mount stays unchanged. An app that reads once at startup needs a supported reload or a controlled restart.
