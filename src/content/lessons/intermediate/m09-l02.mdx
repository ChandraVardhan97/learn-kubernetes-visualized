## <span id="mental-model-the-claim-describes-demand-the-class-selects-a-supply-mechanism" aria-hidden="true" />How Kubernetes provides a volume

A worker in zone A needs a disk, but a disk provisioned in zone B cannot attach there. A **StorageClass** describes how volumes should be provided. It names a provisioner and can set parameters, a reclaim policy for dynamically provisioned volumes, binding behavior, and whether expansion is allowed. When a claim names a class that supports **dynamic provisioning**, Kubernetes and the provisioner can create a matching volume when needed.

With `Immediate` binding, the decision can happen as soon as the claim is created. With **WaitForFirstConsumer**, provisioning or binding waits until a Pod uses the claim so the scheduler can consider both Pod placement rules and storage topology. The class in your cluster may use either behavior. In the scene, change the consumer’s node constraints and see why an early decision could create a disk in the wrong place.

## <span id="walkthrough-delay-a-decision-until-workload-topology-is-known" aria-hidden="true" />Wait for the Pod before choosing storage

Save the example as `report-data.yaml`. Use a real class from `kubectl get storageclass` and record its `volumeBindingMode`. This claim requests 2 GiB and single-node read-write access. A pending claim waiting for a first consumer can be healthy. Inspect its events to distinguish that state from an unknown class or a provisioning error.

```yaml
# Inspect the existing class; do not substitute an invented driver name.
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: report-data
spec:
  storageClassName: standard  # Replace with an actual lab class.
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 2Gi
```

## <span id="practice-read-the-lifecycle-in-order" aria-hidden="true" />Follow provisioning, attachment, and mounting

The **Container Storage Interface (CSI)** standardizes how Kubernetes integrates external storage drivers. Depending on the driver, controller-side operations can create and attach a volume. The node plugin prepares and mounts it for the Pod. Some volumes have no separate attachment operation. This gives you stages to check. An unbound claim points toward binding or provisioning. A bound claim with a Pod still waiting can point toward scheduling, attachment, or mounting. Follow these stages in the scene.

<Scene id="m09-l02-csi-path" />

```bash
kubectl get storageclass
kubectl get storageclass standard -o yaml
kubectl apply -f report-data.yaml
kubectl describe pvc report-data
# After creating the lab consumer Pod:
kubectl get pvc report-data -w
kubectl describe pod report-writer
```

After creating a consumer that references `report-data`, compare its events with the claim’s events. If you bind to a topology-limited volume and later move the consumer, it still needs a compatible node. Use the [persistent storage lab](/labs/#m09) to observe what your local class actually does.

## <span id="pitfalls-local-storage-is-still-local" aria-hidden="true" />Check expansion and node placement

A class can set `allowVolumeExpansion: true`. With a compatible driver you request a larger size on the PVC. The driver may also need to resize the filesystem. Verify reported capacity and conditions before using the extra space. Kubernetes generally supports expanding volumes rather than shrinking them. A local volume can remain tied to its node even when both the PVC and PV are healthy, so persistence through Pod replacement proves little about node loss.

<summary>A new claim is Pending and the event says it is waiting for a first consumer. What should you create or inspect next?</summary>

Create or inspect the Pod that references the claim. Check whether the scheduler can place the Pod on any node that also satisfies the storage constraints. That combined decision is what the binding mode is waiting for.
