## <span id="mental-model-three-actuators-solve-three-different-shortages" aria-hidden="true" />Choose what needs to scale

Traffic doubles and the API gets slower. You could run more copies, give each copy more CPU, or add nodes on which to run copies. Kubernetes has different mechanisms for those decisions. The **Horizontal Pod Autoscaler (HPA)** updates the desired replica count of a scalable workload based on metrics. It needs a working metrics API and application replicas that can share the load.

A **Vertical Pod Autoscaler (VPA)** is an add-on that recommends requests based on observed usage. Its configured mode determines whether it only recommends or also changes what Pods request. Applying a change may involve in-place updates or Pod replacement, depending on the mode and support. A **node autoscaler** adds or removes capacity using provider-specific mechanisms. It can add nodes when pending Pods could fit on one that it is allowed to provision. Follow how these decisions interact in the capacity scene.

## <span id="walkthrough-utilization-has-a-denominator" aria-hidden="true" />Calculate CPU utilization from requests

Save the HPA as `api-hpa.yaml` in the example environment. It targets the `api` Deployment in the same namespace. Each relevant container needs a CPU request for CPU utilization to be calculated. If a replica uses `120m` against a request of `200m`, it is at 60% utilization. If the same usage has a request of `400m`, it reads as 30%. The denominator matters when deciding whether the current replicas appear busy. The HPA also honors the configured bounds of two and eight copies, with a five-minute scale-down stabilization window.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
```

Open **Inspect the scale-down decision** to see why the HPA can keep six replicas after CPU usage falls. The current sample produces a lower recommendation, but the controller considers the highest recommendation still inside the scale-down stabilization window.

## <span id="practice-watch-all-checkpoints-not-just-the-desired-count" aria-hidden="true" />Follow a scale-up through readiness

Check resource metrics before generating traffic. Then watch the HPA’s metric, desired count, and conditions. Compare them with the Deployment’s actual and ready replicas. If the HPA wants six copies but two Pods are pending, their events might reveal a placement constraint or insufficient requested CPU. Adding enough suitable nodes can help the latter case. A conflict in required labels or affinities can make new capacity irrelevant.

```bash
kubectl top pods -n learning
kubectl apply -n learning -f api-hpa.yaml
kubectl get hpa api -n learning -w
kubectl describe hpa api -n learning
kubectl get deployment api -n learning
kubectl get pods -n learning -l app=api -o wide
kubectl get events -n learning --sort-by=.metadata.creationTimestamp
```

In the [application delivery lab](/labs/#m13), the baseline lets you inspect the HPA and its conditions. It does not install the Metrics API. A working CPU-based scaling experiment needs that pipeline, a resource request, and sustained traffic you can observe.

When metrics are available, try reducing load once the replicas are ready. Compare the current CPU metric with the desired replica count. If a higher recommendation is still in the window, `kubectl describe hpa` can report `ScaleDownStabilized` under `AbleToScale`.

## <span id="pitfalls-more-nodes-only-help-satisfiable-demand" aria-hidden="true" />Check whether the new Pods can help

An HPA reading CPU as a percentage of requests can react to VPA changes even when actual requests per second stay flat. Review the metrics and control policies before enabling both on the same workload. Adding nodes also leaves problems such as slow startup or an unavailable dependency untouched. Inspect where new copies stop becoming usable.
