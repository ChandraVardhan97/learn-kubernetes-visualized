## <span id="mental-model-a-release-is-more-than-a-changed-image" aria-hidden="true" />Record what makes up a release

A new API image starts and returns HTTP 200 on `/ready`, but checkout still fails because the image expects a configuration key that staging used and production lacks. A release includes the image, rendered workload, configuration, and external dependencies. Record the versions and references together. An image digest identifies the exact image contents, while a floating tag can refer to different contents later.

A Deployment revision is created when its Pod template changes. Updating an independently referenced ConfigMap does not change that template by itself. A ConfigMap mounted as a normal volume may refresh eventually, but the app must use the refreshed value. Environment variables from it are available at process startup. If your release requires a restart, a versioned config reference or another deliberate Pod template change can trigger it. Inspect the scene to see which inputs belong to a release.

## <span id="walkthrough-trade-surge-capacity-against-unavailable-replicas" aria-hidden="true" />Set the rollout budget and readiness check

The example fragments apply to an existing Deployment and container. The rollout allows one extra Pod and aims to avoid reducing availability due to the update. New Pods have to remain ready for ten seconds before being counted as available. The readiness check must actually exist on port 8080. Give it a meaningful condition for receiving requests, and make sure capacity and quota can accommodate the extra Pod.

```yaml
# Deployment spec fragment.
replicas: 3
minReadySeconds: 10
progressDeadlineSeconds: 300
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

```yaml
# Container probe fragment; the application must implement /ready.
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 2
  periodSeconds: 5
```

## <span id="practice-promote-only-the-behavior-you-actually-checked" aria-hidden="true" />Verify a release before promoting it

Reproduce the intended change with the same rendering inputs you plan to promote. Inspect the diff, watch the rollout, and compare the Service’s ready endpoints with the expected replica count. Run a user-level check for the operation you care about, such as one checkout or report read. Compare error rate and latency with a known baseline if your lab has instrumentation. The scene shows how passing one gate leaves the next verification to do.

<Scene id="m13-l03-delivery-gates" />

```bash
kubectl diff -k overlays/training
kubectl apply -k overlays/training
kubectl rollout status deployment/api -n learning --timeout=300s
kubectl get deployment,replicaset,pod -n learning -l app=api
kubectl get endpointslices -n learning \
  -l kubernetes.io/service-name=api
kubectl rollout history deployment/api -n learning
# Only after choosing a compatible recovery action:
# kubectl rollout undo deployment/api -n learning --to-revision=REVISION
```

Use the [application delivery lab](/labs/#m13) to promote a small change and document the evidence. The local overlay is intended for training. Adapt the probe fragment to a server that implements it before applying that fragment.

## <span id="pitfalls-rollback-has-a-data-and-configuration-compatibility-boundary" aria-hidden="true" />Check old code against new data and settings

Before choosing rollback, ask whether the previous image can run with the current configuration and data format. Restoring an old Pod template cannot reverse a schema migration or restore replaced credentials. For a database column removal, plan a transition that allows both versions to run during the rollout, and keep a separate data recovery procedure.
