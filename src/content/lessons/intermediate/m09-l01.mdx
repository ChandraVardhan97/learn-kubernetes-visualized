## <span id="mental-model-name-the-lifetime-of-every-file" aria-hidden="true" />Which files survive a restart or replacement

A report generator writes a scratch file and a finished report. The scratch file belongs to the current run. The report should still exist if Kubernetes replaces the Pod. Start by picking the lifetime each file needs. A container’s writable image layer can be lost when the container is recreated. An **emptyDir** volume starts with a Pod and is available through container restarts within that Pod. When the Pod goes away, its `emptyDir` goes with it.

A **PersistentVolumeClaim (PVC)** is a request for storage in a namespace. A **PersistentVolume (PV)** represents a specific piece of storage the cluster can provide. A claim binds to a volume that satisfies requirements such as capacity, storage class, and access mode. The Pod refers to the claim by name and mounts the storage in a container. Work through the first scene with both a container restart and a Pod replacement.

## <span id="walkthrough-a-claim-is-a-contract-not-a-directory-copied-between-pods" aria-hidden="true" />Connect a claim to a container directory

The example asks for a 1 GiB volume. The first document is a complete PVC. The second is a fragment for a Pod’s `spec`. The Pod-level volume named `data` refers to claim `app-data`. The container-level mount exposes that volume at `/data`. The writer appends a line every time the container starts, which makes it easy to see whether a later Pod found the old file.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 1Gi
---
# Fragment: a Pod spec mounting the claim in one container.
containers:
  - name: writer
    image: busybox:1.36
    command: ["sh", "-c", "echo marker >> /data/visits; sleep 3600"]
    volumeMounts:
      - name: data
        mountPath: /data
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: app-data
```

**ReadWriteOnce** allows mounting read-write from a single node. Multiple Pods on that one node may share the mount if the driver supports it. **ReadWriteMany** allows read-write mounts from multiple nodes with a compatible provider. **ReadWriteOncePod** restricts read-write use to a single Pod for supported CSI volumes. Access modes constrain placement and binding. Use an explicit read-only mount or appropriate filesystem permissions where the workload must be prevented from writing.

## <span id="practice-replace-the-pod-without-deleting-the-claim" aria-hidden="true" />Replace the Pod and read the old file

In the [persistent storage lab](/labs/#m09), use the supplied writer manifest to create a complete Pod. Inspect the claim and the bound PV. Record the content of `/data/visits`, delete only the writer Pod, and recreate it with the same claim. After it starts, look for both the old and new marker. Compare the claim’s bound volume before and after.

```bash
kubectl get pvc app-data
kubectl describe pvc app-data
kubectl get pv
kubectl exec writer -- cat /data/visits
# Follow the lab instructions to delete and recreate only the writer Pod.
kubectl get pod writer -o wide
kubectl describe pod writer
```

## <span id="pitfalls-persistent-does-not-mean-backed-up" aria-hidden="true" />Check what happens when a claim is deleted

Deleting a claim releases its volume when no object is protecting it from deletion. The PV’s **reclaim policy** controls what happens next. `Delete` normally asks the provisioner to delete the backing storage. `Retain` leaves the storage for manual recovery or cleanup. Before deleting a claim, check the PV policy and verify you can restore important data from an independent copy.
