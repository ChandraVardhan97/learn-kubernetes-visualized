## <span id="mental-model-an-address-is-useful-only-with-a-forwarding-path" aria-hidden="true" />How Pods communicate across nodes

A frontend Pod on one node opens a connection to an API Pod on another. First the Pods need working interfaces and addresses. Then the network needs a route for the packets. A **Container Network Interface (CNI)** plugin follows an interface used by runtimes to configure container networking. In a Kubernetes cluster, the network implementation commonly uses plugins to give Pods addresses and connect them to the node’s network, and may run agents to arrange routes and policy across nodes.

From the frontend’s point of view, the direct connection is addressed to the API Pod’s IP. The packet leaves the frontend’s network namespace and travels through the network to the backend. One implementation might route the Pod IP ranges directly. Another might wrap the packet for transport between nodes and unwrap it on arrival. The Pod-path scene focuses on the visible hops, which you can use to ask where a packet could be lost.

## <span id="walkthrough-a-service-is-an-api-object-plus-a-data-plane" aria-hidden="true" />How a Service forwards a connection

A Service gives the frontend a stable IP and port as the backend Pods come and go. In the manifest, clients connect to port 80 and the service data plane forwards to port 8080 on a selected backend. Pods must already exist with `app: api`, and their app must listen on 8080. EndpointSlices identify the current addresses and include readiness conditions. A backend can still appear in a slice when it is unready.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  ports:
    - name: http
      port: 80           # Client's Service port.
      targetPort: 8080   # Port the selected backend actually listens on.
```

**kube-proxy** watches Services and EndpointSlices and programs forwarding rules on nodes. The packet path typically goes through the rules it installs. Some CNI implementations replace kube-proxy and use **eBPF**, which runs programs at kernel hooks, to handle Service forwarding. The details differ by cluster, but in both cases a client that contacts the Service address needs a route to a usable endpoint. Follow the paths in the second scene.

## <span id="practice-prove-discovery-selection-and-reachability-separately" aria-hidden="true" />Compare direct and Service requests

From your test client, check DNS first. Then compare the selected Pod and EndpointSlice addresses, ports, and conditions. Try the request via the Service and, where policy allows, directly to a known ready Pod’s IP and listening port. A working Pod IP with a failing Service narrows the investigation toward selector, endpoint conditions, or Service forwarding. The example names assume you created `api` and `client`. Use the exercise’s actual names and port in the [networking lab](/labs/#m08).

```bash
kubectl get service api -o wide
kubectl get pods -l app=api -o wide
kubectl get endpointslices -l kubernetes.io/service-name=api -o yaml
# These example names require matching api and client resources.
# The downloadable baseline instead uses m08 and m08-client, port 80.
kubectl exec client -- nslookup api
kubectl exec client -- wget -qO- http://api:80
```

## <span id="pitfalls-local-networks-can-conceal-production-differences" aria-hidden="true" />Test across nodes in the target cluster

Two Pods on one node can communicate even if routing between nodes is broken. Repeat the test from another node when investigating cross-node failures. For a connection that reaches the Service with no ready backend, implementations can differ in whether a caller sees a refusal or timeout. Inspect the objects and run a controlled request before inferring the cause from one error string.
