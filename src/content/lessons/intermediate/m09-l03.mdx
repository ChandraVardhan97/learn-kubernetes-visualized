## <span id="mental-model-a-recovery-point-is-a-separate-resource-with-prerequisites" aria-hidden="true" />What a volume snapshot captures

A report service is about to change its data format. You want a copy of the disk from before the change so you can inspect the old data if needed. A **VolumeSnapshot** is a Kubernetes request for a point-in-time copy of volume data. It names the source PVC and a snapshot class. A snapshot controller and a compatible CSI driver arrange the copy, and a `VolumeSnapshotContent` object represents the snapshot in the cluster. Check that the cluster has the snapshot APIs, a controller, and a driver with snapshot support before running these examples.

A snapshot captures what the storage system can see. If the report process is halfway through writing, the volume might contain a partial result. A database may need its own backup or checkpoint procedure to recover consistently. Choose the moment to capture based on what the application guarantees, then use the scene to walk from the source claim to a ready snapshot.

## <span id="walkthrough-capture-bytes-at-a-meaningful-application-boundary" aria-hidden="true" />Take a snapshot at a known point

Save the example as `app-before-change.yaml`. Replace `lab-snapshots` with a real snapshot class for the PVC’s driver and verify that `app-data` exists in the same namespace. Before taking a test snapshot, write a known value and record its checksum. If the application has more than one volume, determine how it makes its data consistent across those volumes before treating individual snapshots as one recovery point.

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: app-before-change
spec:
  volumeSnapshotClassName: lab-snapshots
  source:
    persistentVolumeClaimName: app-data
```

```bash
kubectl get volumesnapshotclass
kubectl get csidrivers
kubectl apply -f app-before-change.yaml
kubectl get volumesnapshot app-before-change -o yaml
kubectl describe volumesnapshot app-before-change
```

Look for `readyToUse` and the restore size in status. That status tells you the storage system has prepared a copy you can request for a restore.

## <span id="practice-restore-to-a-new-name-and-prove-the-content" aria-hidden="true" />Restore to a fresh claim and verify its contents

Create the restored volume from a separate PVC. The `dataSource` points to the snapshot. Choose a compatible StorageClass and a request at least as large as the required restore size. Mount the fresh claim in a temporary Pod, then compare the saved checksum or run a read-only application check. Keeping the source claim untouched makes it easier to validate both copies.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-restored
spec:
  storageClassName: standard  # Must be compatible with the snapshot driver.
  dataSource:
    name: app-before-change
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 2Gi             # At least the required restore size.
```

## <span id="pitfalls-readiness-is-not-a-restore-rehearsal" aria-hidden="true" />Check what failures your backup can survive

Snapshots can share a storage system, account, or location with the source volume. Check which failures the copy survives before planning to rely on it. A bound restored claim shows that Kubernetes can supply a volume. It takes a content and application check to establish that the restore actually met the recovery goal.
