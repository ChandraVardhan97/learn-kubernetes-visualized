## <span id="mental-model-compare-paths-while-preserving-the-source" aria-hidden="true" />Compare direct and Service connections

An API becomes unreachable after a change. First reproduce the symptom from a client with the same network and policy as the one that fails. Write down the name it looked up, the address it used, the port, and the result. Keep as much of that test fixed as possible while you change one part of the path.

The **Service** selects backends and gives clients a stable address. **EndpointSlices** show the selected addresses, ports, and conditions. A client can get a DNS answer even when there are no ready endpoints. Compare a failing request through the Service with a request to a known ready Pod’s IP and target port. If the direct request works from the same caller, you can focus on Service mapping and forwarding. If both fail, inspect the backend listener, policy, or network route. Use the scene to reason from each pair of results.

## <span id="walkthrough-take-discovery-out-of-the-path-one-step-at-a-time" aria-hidden="true" />Test DNS and the backend from the client

Run the commands with an existing `api` Service, matched Pods, and `client`. The full DNS name assumes namespace `learning` and domain `cluster.local`. Substitute the actual namespace and domain if different. Read search domains inside the client. If the fully qualified name resolves but the short name does not, investigate which namespace the client searches. Where NetworkPolicy applies, check both the caller’s egress and the destination’s ingress, including DNS access.

```bash
kubectl get service api -o yaml
kubectl get pods -l app=api -o wide
kubectl get endpointslices -l kubernetes.io/service-name=api -o yaml
kubectl exec client -- nslookup api.learning.svc.cluster.local
kubectl exec client -- cat /etc/resolv.conf
kubectl exec client -- wget -T 3 -qO- http://api:80
# Substitute a ready endpoint address and its actual target port.
kubectl exec client -- wget -T 3 -qO- http://POD_IP:8080
```

## <span id="practice-storage-has-its-own-checkpoint-ladder" aria-hidden="true" />Find where storage setup or access failed

Now consider a writer that cannot create a file in `/data`. Follow its claim before checking the filesystem. An unbound PVC can mean the class does not exist, no PV fits, provisioning failed, or the class is waiting for a consumer. A bound claim with a pending Pod can point to placement, attachment, or mount trouble. Check the Pod events to see which operation the kubelet or controller reports. CSI drivers that use a distinct attachment step can also publish `VolumeAttachment` objects.

```bash
kubectl get pod writer -o wide
kubectl describe pod writer
kubectl get pvc
kubectl describe pvc app-data
kubectl get pv
kubectl get storageclass
kubectl get volumeattachments
```

<Scene id="m12-l02-storage-ladder" />

If the Pod runs and the mount exists, inspect the actual mount path, the process UID and group, file ownership, and whether the mount is read-only. A healthy claim can be completely unrelated to a permission error in the container. Practice an evidence-led repair in the [debugging lab](/labs/#m12), or reproduce the storage checks with the writer from the persistent storage lesson.

## <span id="pitfalls-repair-the-failed-boundary-rather-than-its-neighbors" aria-hidden="true" />Retest the failing operation after repair

Keep the working state available for comparison. Deleting a claim to test a mount error can release the underlying data. A port-forward can reach a backend while sidestepping the client path you need to diagnose. Retest using the original client or process and verify the precise operation that failed.

<details>

<summary>The writer runs, the claim is Bound, and reading works, but writes return a permission error. Where should you look first?</summary>

Check mount flags and file ownership for the user running the process. These symptoms indicate the app reached mounted data. They give you a better starting point than replacing the volume or modifying the StorageClass.
