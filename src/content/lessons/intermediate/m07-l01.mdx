## Mental model: admission, placement, and runtime answer different questions

A resource **request** is the amount Kubernetes uses when deciding whether a node has room for a Pod. It is not the Pod's current usage. A resource **limit** constrains consumption at runtime through the node's container runtime and operating system. A Pod requesting 250 millicores can use more CPU when capacity and its limit permit. The scheduler does not continually move it because usage changes. This distinction explains why a mostly idle cluster can still have Pending Pods: existing requests may already account for the allocatable capacity on every suitable node.

CPU is divisible execution time. `250m` means one quarter of one CPU unit; it does not pin a thread to a particular core. Memory quantities such as `128Mi` are bytes with binary suffixes. Node **allocatable** capacity excludes reservations and other node overhead from the capacity available for Pods. For ordinary containers, the scheduler considers their requests together, with additional rules for init containers and Pod overhead. Read the admitted Pod because defaults or admission mutation can change the submitted configuration.

## Walkthrough: the same request has two different runtime outcomes

This complete Pod uses one small container. The image is a training convenience; use an approved immutable image identifier for a reproducible release. Apply it in the disposable namespace created by the module lab.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
spec:
  containers:
    - name: web
      image: nginx:1.27-alpine
      resources:
        requests:
          cpu: 100m       # Scheduling accounts for 0.1 CPU.
          memory: 64Mi     # A reservation input, not measured usage.
        limits:
          cpu: 500m       # Runtime may throttle sustained CPU demand.
          memory: 128Mi   # Exceeding available limit can trigger OOM.
```

A CPU limit normally causes throttling when the container exhausts its allowed CPU time over an accounting period. Work slows down; the process is not normally killed merely for requesting additional CPU time. A memory limit cannot make memory reclaimable when an application keeps using it. The kernel may kill a process when the cgroup cannot satisfy an allocation within its memory constraints. A terminated container can report `OOMKilled`; inspect termination reason and events before assuming every exit code 137 is the same failure. A restarting process may recreate caches and repeat the failure indefinitely.

**Quality of Service**, or QoS, groups Pods according to resource configuration. In the standard container resource model, Guaranteed requires CPU and memory requests and limits for every container, with each request equal to its corresponding limit. BestEffort has none of those requests or limits. Burstable includes configurations between those extremes. The example is Burstable. Its class is a classification of configuration, not a measured promise of latency or immunity from failure.

## Practice: observe the admitted object and its boundary

```bash
kubectl apply -f resource-demo.yaml
kubectl get pod resource-demo -o jsonpath='{.status.qosClass}{"\n"}'
kubectl describe pod resource-demo
kubectl get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory
# Requires the separately installed resource metrics pipeline.
kubectl top pod resource-demo
```

Expect the class to be `Burstable`, assuming admission has not changed the Pod. `kubectl top` may fail on a local cluster without Metrics Server; the API object and scheduling events remain useful without that add-on. Compare requested resources to measured consumption without treating either as a substitute for the other. The node description's allocated resources section summarizes requests from assigned Pods, which is closer to scheduler capacity accounting than a single usage sample.

In a disposable namespace, change both resource pairs to equal values in a new Pod manifest and compare its class. Do not expect editing immutable Pod fields in place to perform a replacement automatically. Create a different named Pod or use a Deployment when practicing configuration changes. Remove the examples after recording their admitted settings and observed status.

## Pitfalls: QoS is part of a larger pressure story

Node-pressure eviction considers the scarce resource, whether usage exceeds requests, Pod priority, and usage relative to requests. “BestEffort first, Guaranteed never” is an unsafe universal rule. A Guaranteed Pod can still fail from its own memory limit, infrastructure loss, or severe pressure. A high memory request also reduces placement options, so increasing it without measuring a working set may trade restarts for Pending Pods. CPU requests influence relative CPU allocation under contention; they do not buy a dedicated physical processor by themselves.

<summary>A node has 2 allocatable CPUs, 1.9 CPUs already requested, and only 5 percent actual usage. Can a new 200m request fit?</summary>

No. The remaining scheduling budget is 100m, so this node fails the CPU request check even though current usage is low. Lowering the new Pod's CPU limit would not change that request calculation. Investigate overestimated requests or add appropriate capacity, then evaluate runtime behavior under load before settling on new requests.
