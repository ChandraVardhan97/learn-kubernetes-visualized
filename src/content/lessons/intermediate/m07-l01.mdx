## <span id="mental-model-admission-placement-and-runtime-answer-different-questions" aria-hidden="true" />How requests and limits affect a Pod

A web container uses little CPU between requests and bursts when a page is loaded. A second container holds a large cache in memory. Kubernetes needs to know how much room to plan for before either container starts. A **resource request** is the amount the scheduler accounts for when it places a Pod. It compares requests already assigned to a node, plus those of the incoming Pod, with the node’s allocatable resources. A node can appear idle and still lack room on that calculation.

A **resource limit** constrains what a container can use at runtime. Setting a CPU limit slows the process when it has used its CPU time budget for an interval. This is **throttling**. At a memory limit, the kernel can kill a process that cannot complete an allocation within the memory boundary. The kubelet may restart the container. In the scene, compare the placement decision with the consequences of exceeding the two limits.

## <span id="walkthrough-the-same-request-has-two-different-runtime-outcomes" aria-hidden="true" />Read CPU and memory quantities

Save the manifest as `resource-demo.yaml`. `100m` is 100 millicores, one tenth of a CPU. With a request of `100m` and a limit of `500m`, the scheduler accounts for one tenth and the container can use up to half a CPU on average under its CPU quota. `64Mi` means 64 mebibytes. The memory request affects placement while the `128Mi` limit bounds the container’s memory use.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
spec:
  containers:
    - name: web
      image: nginx:1.27-alpine
      resources:
        requests:
          cpu: 100m       # Scheduling accounts for 0.1 CPU.
          memory: 64Mi     # A reservation input, not measured usage.
        limits:
          cpu: 500m       # Runtime may throttle sustained CPU demand.
          memory: 128Mi   # Exceeding available limit can trigger OOM.
```

Kubernetes assigns a **Quality of Service (QoS) class**. In the container-level model shown here, `Guaranteed` requires all containers to have positive CPU and memory requests equal to their limits for each resource. `BestEffort` applies when containers have neither CPU nor memory requests or limits, and `Burstable` covers this example because the values differ. Change the fields in the second scene and compare the class.

## <span id="practice-observe-the-admitted-object-and-its-boundary" aria-hidden="true" />Inspect what Kubernetes admitted

Apply the example and inspect the class and accepted spec. `kubectl top` reports recent usage through a separately installed metrics pipeline. If the Metrics API is absent, the request and limit values remain visible on the Pod. Compare them with node allocatable capacity and with usage if metrics are available.

```bash
kubectl apply -f resource-demo.yaml
kubectl get pod resource-demo -o jsonpath='{.status.qosClass}{"\n"}'
kubectl describe pod resource-demo
kubectl get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory
# Requires the separately installed resource metrics pipeline.
kubectl top pod resource-demo
```

Follow the [resource and scheduling lab](/labs/#m07) to see how a Pod can stay pending when its request exceeds available capacity.

## <span id="pitfalls-qos-is-part-of-a-larger-pressure-story" aria-hidden="true" />Distinguish a memory limit from node pressure

QoS is one signal for understanding how Pods behave under pressure. Under node memory pressure, the kubelet considers whether usage exceeds requests, Pod Priority, and the amount by which usage exceeds requests. A container can also hit its own memory limit while the node has ample free memory. Use Pod events and the last container state to tell those failures apart.
