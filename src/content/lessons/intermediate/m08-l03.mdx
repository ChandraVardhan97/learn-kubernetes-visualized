## <span id="mental-model-declare-a-route-supply-a-working-implementation" aria-hidden="true" />How incoming HTTP requests find a backend

A shop wants `api.example.test/api` to reach its API Service and `www.example.test/` to reach the storefront. A **routing rule** can share one public address while sending requests to different backends. An **Ingress** declares HTTP routes and can reference TLS certificates. It needs an Ingress controller that implements those routes for the cluster. Applying a route object alone gives you an API record to inspect.

**Gateway API** splits this configuration across roles. A `GatewayClass` names the controller implementation. A `Gateway` configures one or more listeners, such as HTTPS on port 443. An `HTTPRoute` describes how requests reach a backend. A Gateway listener can control which routes it allows to attach. In the first scene, trace a route attachment from the route’s parent reference to a listener that accepts it.

## <span id="walkthrough-follow-acceptance-before-following-packets" aria-hidden="true" />Attach a route to a Gateway

The `HTTPRoute` below refers to a Gateway named `public` and matches host `api.example.test` with path prefix `/api`. It forwards to port 80 on a Service named `api`. The Service may then forward to a different container port. To run the example, install the Gateway API definitions, use a compatible controller, and make sure the referenced Gateway, Service, and endpoints exist. The route status helps you see which parent accepted it and whether references resolved.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api
spec:
  parentRefs:
    - name: public
  hostnames:
    - api.example.test
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api
      backendRefs:
        - name: api
          port: 80        # Service port, not container targetPort.
```

```bash
kubectl get gatewayclass
kubectl get gateways,httproutes
kubectl describe httproute api
kubectl get service api
kubectl get endpointslices -l kubernetes.io/service-name=api
# Replace the address with the lab listener address, if installed.
curl -v -H 'Host: api.example.test' http://127.0.0.1:8080/api
```

A typical HTTPS listener presents a certificate for the requested hostname and **terminates TLS** by decrypting the connection there. It can then match the HTTP hostname and path. Whether the hop to the backend also uses encryption depends on the gateway and backend TLS configuration. The second scene shows the TLS and HTTP decisions in order.

## <span id="practice-vary-one-hostname-and-one-layer-at-a-time" aria-hidden="true" />Test hostname, path, and certificate

Use the curl command against the listener’s real address. With plain HTTP, the `Host` header lets you test hostname routing without adding a DNS record. With HTTPS, set the real hostname in the URL and use DNS or curl’s `--resolve` option to direct it to the test address. That also gives the TLS handshake and certificate check the correct hostname.

First verify a matching request, then change just its host or path. If routes attach but return a backend error, inspect the Service and ready endpoints. The [networking lab](/labs/#m08) builds the Service baseline. Route and certificate tests require the additional controller and listener described above.

## <span id="pitfalls-http-tls-and-tcp-are-different-match-points" aria-hidden="true" />Locate the failed stage of a request

A connection refusal can mean no listener is reachable. A certificate error occurs before an HTTP route can handle the request. A reachable gateway can still return an HTTP error for an unmatched route or unavailable backend. Check these stages in order to avoid editing routing rules to fix a TLS handshake.
