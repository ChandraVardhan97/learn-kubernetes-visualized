## <span id="mental-model-first-eligibility-then-preference" aria-hidden="true" />Which nodes can run this Pod

A cluster shares workers between ordinary web apps and maintenance tools. You want the tools to run on one labeled worker and ordinary apps to stay off it. Kubernetes has a way to express the Pod’s requirements and a separate way for the node to repel workloads.

A **node selector** requires matching node labels. **Node affinity** also evaluates node labels and can express alternatives and preferences. Required rules remove nodes from consideration. Preferred rules influence the scheduler’s scoring of eligible nodes. In the scene, find which nodes are still eligible before the scheduler compares preference scores.

**Pod affinity** evaluates where other Pods with selected labels run. For example, a worker could prefer the same zone as a cache it calls frequently. **Pod anti-affinity** can keep matching web replicas apart by hostname so one node failure affects fewer replicas. The topology key defines what “together” or “apart” means. A hard one-per-node requirement for three replicas needs at least three eligible nodes.

Open **Inspect the placement** to compare three workers. Watch one fail a required label check, then see how the cache’s location breaks the tie between the two eligible workers.

## <span id="walkthrough-dedicate-capacity-with-two-independent-controls" aria-hidden="true" />Reserve one worker for maintenance tools

A **taint** is a node setting that repels Pods without a matching **toleration**. `NoSchedule` blocks new placements that do not tolerate it. It leaves already-running Pods in place. `PreferNoSchedule` is a soft preference. `NoExecute` can also evict existing Pods without a matching toleration. A toleration gives a Pod permission to run on a tainted node when other rules allow it.

Save this manifest as `tools-client.yaml`. The Pod needs a node labeled `workload=tools` and tolerates `dedicated=tools:NoSchedule`. Put both settings on the same disposable worker. The label requirement guides the tools there, and the taint protects the worker from ordinary new Pods. Try each setting on its own in the scene.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: tools-client
  labels:
    app: tools-client
spec:
  nodeSelector:
    workload: tools          # Requires this label on the chosen node.
  tolerations:
    - key: dedicated
      operator: Equal
      value: tools
      effect: NoSchedule    # Allows this taint; does not select the node.
  containers:
    - name: client
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests:
          cpu: 25m
          memory: 16Mi
```

## <span id="practice-prove-every-filter-before-adding-another" aria-hidden="true" />Read the scheduling event

Before applying, confirm the context points to the lab and choose a worker name from the node listing. After scheduling, read the `NODE` column in `kubectl get pod -o wide`. If it stays Pending, inspect the `FailedScheduling` event. It can point to an unmatched selector, an untolerated taint, or insufficient resources. Delete the Pod and remove the training settings after the experiment.

```bash
# Substitute a disposable lab worker name obtained from the first command.
kubectl get nodes --show-labels
kubectl label node LAB_WORKER workload=tools
kubectl taint node LAB_WORKER dedicated=tools:NoSchedule
kubectl apply -f tools-client.yaml
kubectl get pod tools-client -o wide
kubectl describe pod tools-client
# Undo only the training changes after deleting the Pod.
kubectl delete pod tools-client
kubectl taint node LAB_WORKER dedicated=tools:NoSchedule-
kubectl label node LAB_WORKER workload-
```

The [placement lab](/labs/#m07) uses constrained capacity and labels to help you see why a Pod remains pending.

## <span id="pitfalls-hard-constraints-compose-into-an-empty-set" aria-hidden="true" />Check all the hard requirements together

Required constraints apply together. A labeled node can be rejected for a taint or for lack of CPU. A toleration can leave several nodes eligible, and adding a preference still leaves their final scores to the scheduler. Read the event summary and check the actual labels and taints on each candidate before relaxing constraints.
