## Mental model: first eligibility, then preference

The scheduler chooses a node for an unscheduled Pod by filtering unsuitable nodes and scoring the feasible remainder. Resource requests are one filter. Node labels, required affinity, taints, storage topology, and other constraints also contribute. A preferred rule changes scoring but does not make an otherwise invalid node eligible. When every node fails at least one hard rule, the correct result is a Pending Pod with scheduling evidence, not an arbitrary placement that ignores the manifest.

A `nodeSelector` requires matching labels on a node. Node affinity expresses richer conditions: required terms filter nodes, while preferred terms influence scoring. In `requiredDuringSchedulingIgnoredDuringExecution`, “ignored during execution” means changing a matching node label later does not by itself evict an already running Pod. Multiple expressions inside one selector term are combined with AND; alternative node selector terms are combined with OR. This small logical distinction can double the intended set of eligible nodes accidentally.

## Walkthrough: dedicate capacity with two independent controls

Taints repel Pods that lack matching tolerations. They do not identify the node a Pod should seek. A toleration lets a Pod pass a taint check; node affinity can require the intended pool. The following Pod combines both, assuming a lab worker is deliberately labeled `workload=tools` and tainted `dedicated=tools:NoSchedule`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: tools-client
  labels:
    app: tools-client
spec:
  nodeSelector:
    workload: tools          # Requires this label on the chosen node.
  tolerations:
    - key: dedicated
      operator: Equal
      value: tools
      effect: NoSchedule    # Allows this taint; does not select the node.
  containers:
    - name: client
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests:
          cpu: 25m
          memory: 16Mi
```

`NoSchedule` prevents new placement without a toleration but does not evict already assigned Pods. `PreferNoSchedule` is a preference to avoid the node. `NoExecute` can also cause existing Pods without a matching toleration to be evicted; a matching toleration with `tolerationSeconds` can give a bounded stay. These effects are operationally different. Never experiment with cluster-wide worker taints on a shared cluster simply to see which Pods disappear.

**Inter-Pod affinity** uses labels on other Pods and a topology key on nodes. A cache client might prefer to share a zone with cache Pods. **Pod anti-affinity** can avoid placing replicas in the same hostname domain. Required anti-affinity improves separation but can make replicas unschedulable when there are fewer eligible domains than replicas. Preferred anti-affinity can reduce that availability trade-off, at the cost of accepting some co-location. Topology labels must be consistently present; a missing label is not a new physical failure domain.

## Practice: prove every filter before adding another

```bash
# Substitute a disposable lab worker name obtained from the first command.
kubectl get nodes --show-labels
kubectl label node LAB_WORKER workload=tools
kubectl taint node LAB_WORKER dedicated=tools:NoSchedule
kubectl apply -f tools-client.yaml
kubectl get pod tools-client -o wide
kubectl describe pod tools-client
# Undo only the training changes after deleting the Pod.
kubectl delete pod tools-client
kubectl taint node LAB_WORKER dedicated=tools:NoSchedule-
kubectl label node LAB_WORKER workload-
```

Run this exercise only in the module's disposable cluster. If there is no eligible worker, stay with the visual scenario instead of changing a control-plane node's scheduling policy. Expect the Pod to bind only if the labeled node also passes resource and other scheduler checks. Remove its toleration in a separately named copy and predict the scheduling event before applying it. The tainted node should be rejected despite its matching label.

Inspect `FailedScheduling` messages as a list of reasons across nodes. A message mentioning both insufficient memory and untolerated taints does not necessarily mean the same node failed both checks. Inspect each node's labels, taints, allocatable resources and existing requests to build the actual feasible set. Avoid setting `spec.nodeName` as a shortcut: it bypasses normal scheduler selection and hides the mechanism you are learning.

## Pitfalls: hard constraints compose into an empty set

Copying required anti-affinity from a three-node environment into a one-node local cluster often blocks the second replica. Similarly, a toleration broad enough to tolerate every taint can allow access to pools that were intended to remain dedicated. Use narrow keys, values and effects, and apply an admission policy when pool access must be a security or governance rule. Placement configuration alone should not be treated as an authorization boundary against users who can freely change it.

## Check your understanding

<details>
<summary>A Pod tolerates the GPU node's taint but has no selector. Must the scheduler put it on a GPU node?</summary>

No. The toleration only removes one reason to reject GPU nodes. Other untainted nodes may also be feasible and may receive a higher score. Use a resource request for the extended GPU resource and appropriate placement rules when the workload needs that hardware. A matching toleration alone neither reserves nor requests a device.
