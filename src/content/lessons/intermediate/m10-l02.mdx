## <span id="mental-model-a-replica-can-mean-a-node-agent-or-a-unit-of-completed-work" aria-hidden="true" />Match the controller to the work

A cluster needs a log collector on every worker, a report generated once today, and a fresh report every morning. Each is a workload, but success means something different for each.

A **DaemonSet** aims to run a Pod on every eligible node, or on a subset selected by labels and other constraints. A log collector often needs one copy per node because it reads that node’s logs. When a new eligible node joins, the DaemonSet controller creates a Pod for it. Use the node coverage scene to see why adding a node can create a new Pod even though no replica number was edited.

## <span id="walkthrough-completion-needs-a-different-controller" aria-hidden="true" />Run one report to completion

A **Job** runs a task to completion. It creates Pods, tracks their successful completions, and can retry failures within its policy. The following Job runs a command, writes a timestamp and marker, then exits successfully. `restartPolicy: Never` lets you see separate Pods for retry attempts. `backoffLimit` bounds retries, `activeDeadlineSeconds` bounds the Job’s running time, and the TTL cleans up finished work after 600 seconds. For a real report, store the output where it will still be available after the Pod is gone.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: report-once
spec:
  backoffLimit: 2              # Bound retry attempts after failures.
  activeDeadlineSeconds: 120   # Bound total running time.
  ttlSecondsAfterFinished: 600 # Clean up later; export needed evidence first.
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: report
          image: busybox:1.36
          command: ["sh", "-c", "date -u; echo report-complete"]
```

## <span id="practice-inspect-ownership-and-durable-results" aria-hidden="true" />Check Job results and node coverage

Save the file as `report-once.yaml`. Compare the Job’s completion status with the Pod’s phase and read the output. Then list a DaemonSet already in the cluster and compare its assigned Pods with eligible nodes. For an exercise that uses both ownership and workload status, use the [workload management lab](/labs/#m10).

```bash
kubectl apply -f report-once.yaml
kubectl get jobs,pods
kubectl logs job/report-once
kubectl describe job report-once
# Inspect node-local coverage where the cluster already has DaemonSets.
kubectl get daemonsets -A
kubectl get pods -A -o wide
```

## <span id="pitfalls-schedules-are-approximate-triggers" aria-hidden="true" />Plan for missed or overlapping scheduled runs

A **CronJob** creates Jobs according to a schedule. If a new run comes due while the previous one is active, `Allow` permits overlap, `Forbid` skips a concurrent run, and `Replace` replaces the active Job with a new one. These policies apply to Jobs created by the same CronJob. Check the time zone used for the schedule and decide how late a missed run may start.

A CronJob can miss a run or create more than one Job for a scheduled time in some conditions. Job retries can also repeat work after a partial failure. Make the task safe to repeat. One report generator might write to a path keyed by the report’s date and replace the completed file atomically after a successful run.
