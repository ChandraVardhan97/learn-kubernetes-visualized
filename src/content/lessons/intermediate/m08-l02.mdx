## <span id="mental-model-policies-add-allowed-edges-to-an-isolated-direction" aria-hidden="true" />When a NetworkPolicy blocks a connection

An API should accept requests from the shop frontend, but another application in the cluster can currently call it. A **NetworkPolicy** lets you describe allowed connections to or from selected Pods. A compatible network implementation has to enforce the policy. Creating the object alone does not prove traffic changed.

Policies select Pods in their own namespace. A Pod becomes isolated for **ingress** when an ingress policy selects it, and for **egress** when an egress policy selects it. A new connection between two Pods must satisfy the source’s egress rules if it is egress-isolated, and the destination’s ingress rules if it is ingress-isolated. Reply traffic for an allowed connection is implicitly allowed. Toggle each direction in the scene and check both ends before predicting the outcome.

## <span id="walkthrough-select-a-server-then-select-its-clients" aria-hidden="true" />Allow the shop frontend to call the API

The example selects Pods labeled `app: api` in the policy’s namespace. Its one peer entry lists both a `namespaceSelector` and a `podSelector`, so a client must satisfy both. It needs `role: frontend` and its namespace needs `team: shop`. The rule applies to TCP port 8080 on the backend. A separate Service might expose port 80 to the caller and forward it to 8080.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-from-shop-frontend
spec:
  podSelector:
    matchLabels: {app: api}
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: {team: shop}
          podSelector:
            matchLabels: {role: frontend}
      ports:
        - protocol: TCP
          port: 8080
```

Indentation matters. Putting the two selectors in separate list entries would allow either group. A Pod selector by itself refers to Pods in the policy’s namespace. NetworkPolicy permissions are additive across the policies that select a Pod in a direction. A second policy granting broader access can permit a connection excluded by the first policy’s peer list. Inspect the selector scene and predict which clients pass.

## <span id="practice-baseline-deny-then-allow" aria-hidden="true" />Test before and after the policy

Start with a successful request from each test client. Record its namespace labels, Pod labels, and the Service port. Apply the policy, then open a fresh connection from the permitted frontend and another from a client outside the allowed set. A successful baseline helps rule out a bad hostname or a missing endpoint. Enforcement can take time after the API accepts the policy.

```bash
kubectl get networkpolicies
kubectl get namespaces --show-labels
kubectl get pods --show-labels -o wide
# Establish a working baseline from the example client first.
# This assumes a Service exposing port 80 and forwarding to backend 8080.
kubectl exec client -- wget -T 3 -qO- http://api:80
kubectl apply -f api-policy.yaml
kubectl describe networkpolicy api-from-shop-frontend
# Repeat from one permitted and one deliberately unpermitted client.
```

Use the [networking lab](/labs/#m08) to inspect the environment. Follow the policy experiment only after confirming your cluster has a policy-capable network implementation. A basic kind setup may require an additional network setup for enforcement.

## <span id="pitfalls-one-broad-allow-can-defeat-a-careful-default" aria-hidden="true" />Check for other rules and DNS failures

A policy that isolates egress can block DNS, so separate name lookup from the application request. Existing connections and traffic involving nodes can have implementation-specific behavior or exceptions. Start fresh connections from known clients and make one change at a time. That gives you a reproducible result to explain.
