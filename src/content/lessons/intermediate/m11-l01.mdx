## <span id="mental-model-establish-identity-then-evaluate-the-requested-action" aria-hidden="true" />How the API identifies and authorizes a caller

A reporting app needs to list Pods in the `learning` namespace. It should be able to read their status, and that is the extent of its job. When it sends a request, the API server first authenticates it. **Authentication** establishes who is calling using a credential the server trusts. **Authorization** evaluates what that identity is allowed to do for this particular request.

A **ServiceAccount** is a namespaced Kubernetes identity that a Pod can use. The Pod chooses it with `spec.serviceAccountName`. In a modern cluster, a Pod that mounts the standard API credentials receives a projected, time-limited token. The kubelet refreshes it before expiration. Projected tokens have an intended audience and are typically bound to the Pod. In the first scene, trace the credential to the resulting name `system:serviceaccount:learning:pod-reader`.

## <span id="walkthrough-bind-one-narrow-role-to-one-workload-identity" aria-hidden="true" />Grant read access in one namespace

**Role-based access control**, or RBAC, describes permitted API actions. The example Role allows `get`, `list`, and `watch` on `pods` in its namespace. The empty API group means the core API. The RoleBinding grants those rules to the `pod-reader` ServiceAccount in `learning`. A ClusterRole can describe permissions for cluster-scoped resources or be reused via bindings. A RoleBinding limits the grant to its own namespace. A ClusterRoleBinding can grant applicable permissions cluster-wide.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: pod-reader
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-pod-state
rules:
  - apiGroups: [""]       # Empty group is the core API group.
    resources: [pods]
    verbs: [get, list, watch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-state
subjects:
  - kind: ServiceAccount
    name: pod-reader
    namespace: learning
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: read-pod-state
```

RBAC permissions are additive. A second binding can grant an action that this Role omits. In the scene, try listing Pods, deleting one, and accessing a resource governed by a different rule. Check the verb, resource, namespace, and identity for every request.

## <span id="practice-verify-permissions-without-printing-credentials" aria-hidden="true" />Test allowed and denied operations

Create `learning` if needed in your disposable cluster. Save the manifest as `pod-reader-rbac.yaml` and run the checks with a lab user allowed to impersonate the ServiceAccount. Expect listing Pods to succeed, deletion to be denied, and reading Secrets to be denied with only the grant shown. If an action returns an unexpected answer, inspect other bindings and check that the command targets the right identity and namespace.

```bash
kubectl apply -n learning -f pod-reader-rbac.yaml
# These impersonation checks need permission to impersonate the subject.
kubectl auth can-i list pods -n learning \
  --as=system:serviceaccount:learning:pod-reader
kubectl auth can-i delete pods -n learning \
  --as=system:serviceaccount:learning:pod-reader
kubectl auth can-i get secrets -n learning \
  --as=system:serviceaccount:learning:pod-reader
```

In the [permissions lab](/labs/#m11), record the allowed and denied results. Add only a documented permission if the application needs a new API operation, then repeat the original checks.

## <span id="pitfalls-unnecessary-credentials-enlarge-the-boundary" aria-hidden="true" />Mount credentials only where needed

If a Pod only serves HTTP and never calls the Kubernetes API, set `automountServiceAccountToken: false` where appropriate. The app still runs under its workload configuration and no default API token is mounted. Keep credentials out of diagnostic output. Authorization checks can demonstrate the grant without reading the token.

<summary>The reporting job moves to a namespace called reports and uses a ServiceAccount also named pod-reader. Does the existing binding apply?</summary>

The namespace is part of the identity. `system:serviceaccount:reports:pod-reader` differs from the existing subject in `learning`. If the job still needs to list Pods in `learning`, bind the new subject to the intended Role in that namespace.
